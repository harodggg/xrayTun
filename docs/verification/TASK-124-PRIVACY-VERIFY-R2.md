## 3. ⚠️ 新发现（需报 Lead）：**域名紧贴字母**是**第三种**覆盖不到的形态

* 现象：`当前节点「Xray<域名>」`（合成节点，域名是 RFC 文档域名）**没被抹掉**；
* 原因（读码）：修的是「名字里**任何位置的 IP 字面量**」（`parse_ip_at` 扫描）+ 「按 `-`/`_` 再切一次」；
  **域名条目仍要求左边界**（commit 自己写了理由：否则 `xnode-example.xyz` 会被误伤）。
  于是「域名**紧贴字母**」既不在切分段里、也过不了左边界 ⇒ 漏。
* **危害与概率**：真实节点的名字来自订阅，用户/机场完全可能写 `HKGjp1.example.com` 这种无分隔符形式；
  一旦出现，**节点域名就会进报告**（节点域名 ≈ 用户服务器）。
* **与陈述冲突（`Logs.tsx`）**：现在写的是「覆盖不到的形态有**两种**（base64 + 不以主目录开头但带用户名的路径）」
  —— **实际至少三种**（多这条）。⇒ **陈述比实现弱/窄**，按卡面报 Lead，**不改 UI**。
* **建议改后措辞**（供参考）：
  > 「仍覆盖不到的形态有三种：① **base64 载荷**；② **不以主目录开头、但带用户名的路径**（如 `/var/folders/…`）；
  > ③ **域名紧贴字母的节点名**（如 `Xray<域名>`，没有 `-`/`_` 分隔）—— 贴出去前请在报告里搜一下自己的节点域名。」
* **边界**：这条是在**合成节点**上测到的（真实两个节点都是 IP 形态）⇒ 真实日志里**没有**这条的实例，
  所以 §1 的「0 命中」**不受影响**；但「节点名里嵌域名」这一类**只被部分覆盖**。

* M1：节点 IP 是**公网 IP** ⇒ 即使判据集合为空，**公网分支**照样把它们抹掉 ⇒ 真实日志仍 0；

⇒ 这两条现在是**冗余防御**（好事），但意味着**它们不再是可被这两条突变击穿的判据** ——
  要击穿得改成「字符串匹配也要求左边界」，那才是有行为差异的突变。
