# 05 · 界面规格

---

## 1. 设计原则

代理工具的界面有一个特殊性：**大多数时候用户不看它**。
窗口关着、人在浏览器里，只有出问题的时候才回来。

由此得出三条设计原则：

1. **托盘是主入口，不是附属品。** 模式切换、延迟测试、退出都必须能从托盘完成。
2. **「连接成功」必须精确表达。** 这里有一个真实的中间态：
   隧道建好了但默认路由还没接管。把它显示成「已连接」会直接摧毁用户信任
   —— 因为那时流量其实还没走代理。
3. **不做隐形决策。** 前端不猜测后端状态，不自己推断「应该没问题了」；
   所有状态都来自后端快照，每个异常都在界面上有对应的说明文字。

## 2. 信息架构

```
┌─────────────┬──────────────────────────────────────────────┐
│ XrayTun     │  仪表盘        [直连|系统代理|TUN]  ●  [连接]  │  ← 顶栏常驻
│             ├──────────────────────────────────────────────┤
│ 仪表盘       │                                              │
│ 节点    128 │                                              │
│ 订阅      3 │                 页面内容                      │
│ 规则        │                                              │
│ 拓扑        │  ← 入口 / 规则链 / 出口 + 实测流量            │
│ 地球仪      │  ← 本机与出口节点的位置、大圆航线            │
│ 日志        │                                              │
│ 设置        │                                              │
│             │                                              │
│ v0.2.0      │                                              │
└─────────────┴──────────────────────────────────────────────┘
```

顶栏始终显示三件东西：当前页面名、模式切换、连接开关。

**模式与连接是两个独立的概念**，这一点必须让用户能分辨：

* **模式**决定「流量怎么被接管」（直连 / 系统代理 / TUN）；
* **连接**决定「代理核心是否在运行」。

所以直连模式下「连接」按钮是禁用的 —— 那里的正确操作是切模式，
而不是启动一个不会有任何作用的进程。

## 3. 各页面职责

### 3.1 仪表盘

回答三个问题：现在通不通？走的哪个节点？有问题吗？

| 区块 | 内容 |
|---|---|
| 四个统计卡 | 下行速率 / 上行速率 / 当前节点 / 运行状态 |
| 快速操作 | 测试全部延迟、更新全部订阅、打开数据目录、查看日志 |
| 环境自检 | 核心路径与版本、helper 状态、配置文件路径、配置变更时间 |
| 提示条 | 见下节，条件出现 |

「环境自检」这一块是刻意的：TUN 模式依赖两个**外部**条件（够新的核心、
已授权的 helper），任何一个不满足都会失败。把这些条件直接展示出来，
比让用户点一次「连接」看报错要友好得多。

### 3.2 节点

列表 + 搜索 + 延迟测试 + 手动添加。

每行显示：选择指示点、名称、`协议 + 传输 + 安全` 摘要、`地址:端口`、
来源标记（手动/订阅）、SNI、延迟徽标、删除按钮。

延迟徽标分三档着色（<150ms 绿 / <400ms 黄 / 其余红），未测与失败都不着色
而是显示文字。**不把「未测」显示成 0ms** —— 那会让用户以为节点很快。

「测试延迟」按钮会带上当前筛选条件：搜索之后点测试，只测筛选出来的节点。
这符合直觉，也避免在大订阅上做无谓的等待。

### 3.3 订阅

添加入口 + 订阅列表。

* 添加时会**立刻拉取一次**，用户不用再点「更新」。
* URL 输入框下方明确说明：日志里只记 host，完整 URL（含 token）不会出现在任何输出中。
* 用量条只在服务器返回 `subscription-userinfo` 响应头时显示；
  超过 70% 变黄、90% 变红。
* 解析失败时把错误挂在订阅行上，而不是只弹一个转瞬即逝的提示 ——
  用户回来排查时还能看到原因。

### 3.4 规则

预设选择（四选一）+ 自定义规则预览 + 配置落盘位置。

自定义规则的界面编辑是下一步计划，当前版本直接展示只读列表，
并明确告诉用户在哪个 JSON 字段里改。**比做一个半成品的规则编辑器更好** ——
一个不能正确表达优先级顺序的编辑器会制造更多问题。

页面里给出了复现命令：
```
xray run -c ~/Library/Application Support/com.xraytun.desktop/runtime/config.json
```
这是「配置变更走重启」这个取舍的额外好处：现场总是可复现的。

### 3.5 日志

级别过滤 + 关键字过滤 + 自动滚动 + 复制 + 诊断报告。

* **自动滚动默认开启，但用户往上翻时应该关掉。** 当前实现是显式复选框 ——
  自动检测「用户是否在底部」需要监听 scroll 事件，
  而在这个数据量下收益不大。
* 「诊断」按钮生成一份报告并**就地展开**（不是弹窗），
  因为用户接下来大概率要选中复制。
* 报告生成在**后端**完成脱敏：订阅 URL 只留 host、UUID 替换成 `<uuid>`。
  指望用户在贴到 issue 之前手动删敏感信息是不现实的。

### 3.6 设置

分六段：代理入口 / TUN 模式 / DNS / Fake-IP / 内核 / helper / 其他。

**采用「草稿 + 显式保存」而不是即时生效。** 设置项之间有约束
（端口不能重复、必须在 1024 以上、TUN 网段必须合法），
即时生效会让用户每改一个数字就撞一次校验错误。
草稿模式下可以先改完再一起保存。

有未保存改动时顶部出现提示条，带「放弃」和「保存」。

每个高风险项旁边都有解释文字，密度比一般设置页高：

| 项 | 解释的重点 |
|---|---|
| 允许局域网 | 会监听 0.0.0.0，提示确认网络环境可信 |
| 隧道网段 | 说明**主机位会被保留**（这正是 §4 那个 bug 的教训） |
| 哨兵 DNS | 解释它为什么是「假」的、为什么必须落在隧道网段内 |
| IPv6「不接管」 | 明确说会泄漏真实出口，但不会导致断网 —— 这是刻意的取舍 |
| 出站绑定接口 | 解释 `IP_BOUND_IF` 与防路由环的关系 |
| Fake-IP | 警告 + 缓存污染 + 手动刷新命令 |

### 3.7 拓扑

把「流量从哪儿进、经过哪些规则、到哪儿出」画成一张公路图。

| 元素 | 数据来源 |
|---|---|
| 入口 / 规则链 / 出口 | **运行中的真实配置**（核心实际加载的那份） |
| 每个入口与出口的字节数 | 核心的统计接口（实测） |
| 车道颜色（经节点 / 直连 / 拦截） | 各出口的实测字节**份额** |

**必须说清的边界**：核心的统计只有「按入口」「按出口」两类计数器，
**没有逐条规则的计数器**。所以：

* 车流画在**入口 ↔ 出口**之间，不把车流硬画在某条规则上；
* 连线表达「汇入同一条主干、再分流」这个**配置事实**，不声称逐条归属；
* 逐条归属由「某个地址会走哪条路」的判定给出 —— 那一层是真实的，
  且已与真实核心对拍一致（见 [04](04-routing-and-dns.md)）。

取不到流量时显示原因，不画 0 字节的假流量。

### 3.8 地球仪

从本机公网出口到出口节点的大圆弧，飞机沿弧线飞，两端标出**具体地名**。

| 项 | 真实性 |
|---|---|
| 位置（城市 / 坐标） | 真实，但来自 `ip-api.com` —— **被查的 IP 会发给第三方**，界面标注来源 |
| 大圆航线弧线 | 真实几何 |
| 飞机数量 | 由实测字节决定 |
| 大陆轮廓 | **粗略示意**：2° 分辨率的海陆位图（约 4KB），不是导航级海岸线 |
| 飞行速度 | 视觉节奏，不代表真实时延 |

默认视角：对准航线两端的中点，且**保证整个地球可见** —— 近距离航线不放大，
只有跨半球时才缩小。缩放范围 0.55–1.8 倍（上限按「球缘要看得见」定）。

位置查询**绕过隧道**（绑物理网卡）：否则请求会从节点出去、查到的是节点自己的位置。

## 4. 提示条：把中间态说清楚

提示条是这套界面里最重要的一个组件，因为它承担了「解释为什么看起来不对」
的职责。触发条件：

| 条件 | 级别 | 文案要点 |
|---|---|---|
| `runtime.running && !runtime.routes_committed` | 警告 | **隧道已建立但默认路由尚未接管，流量还没有走代理** |
| `helper.stale_session` | 警告 | 上次异常退出留下配置，可能导致网络异常 + 「立即修复」按钮 |
| `!core.path` | 错误 | 没找到核心 + 应该放哪里 |
| `core.path && !core.supports_native_tun` | 警告 | 版本不足，macOS 上会「建了卡但不配置」 |
| `notice` 非空 | 信息 | 订阅更新结果等一次性消息 |

第一条是这套设计的核心。没有它，用户会遇到「显示已连接但打不开网页」
并且完全无从下手。

## 5. 状态呈现约定

| 状态 | 表达 | 反例（不要这样做） |
|---|---|---|
| 未测延迟 | 灰色文字「未测」 | 显示 `0 ms` |
| 测速失败 | 红色「失败」，hover 显示原因 | 显示 `-1 ms` |
| 连接中 | 按钮内联转圈 + 禁用 | 全屏 loading 遮罩 |
| 已连接 | 绿点 + 按钮变「断开」 | 只改变按钮文字颜色 |
| 有错误 | 顶部提示条，可手动关闭 | toast 自动消失 |
| 有未保存改动 | 提示条 + 显式保存按钮 | 静默自动保存 |

## 6. 事件与刷新策略

前端采用**单一快照 + 全量刷新**：后端每个会改变状态的命令都返回完整快照，
前端整体替换。

只有三类高频数据走增量事件：

| 事件 | 载荷 | 频率 |
|---|---|---|
| `runtime://changed` | `CoreRuntime` + `TrafficSample` | 按需（状态变化时） |
| `core://log` | 一行日志 | 核心每输出一行 |
| `nodes://latency` | 一批 `ProbeResult` | 每次探测结束 |

好处是永远不会出现「节点列表更新了但选中项没更新」这类不一致；
代价是每次刷新重建对象 —— 在几百个节点的量级下 React 的 diff 成本可以忽略，
而一致性 bug 的成本高得多。

事件名在两处集中定义、必须一致：
`apps/desktop/src/events.rs` 与 `apps/ui/src/ipc.ts`。
之所以强调这一点：**Tauri 的事件名拼错不会报错**，只会静静地收不到。

**每个处理器的载荷都要过形状校验**（`apps/ui/src/eventGuards.ts`）。

事件推进来的是**运行时数据**，而 `e.payload as ProbeResult[]` 这类断言不做任何
校验。实测撞到过一次：载荷不是数组时处理器抛 `results is not iterable`，
**React 卸载整棵树** —— 用户看到界面凭空消失。所以形状不对时只忽略这次更新，
并（每个事件一次）在控制台留下原因。坏一个字段，不该让整个界面消失。

## 7. 交互细节

* **关闭窗口不退出应用。** 这是 macOS 菜单栏应用的预期行为；
  真正退出要走托盘菜单的「退出 XrayTun」（那里会先回滚网络配置）。
* **托盘左键单击显示窗口**，`iconAsTemplate` 让图标自动适配明暗主题。
* **列表行整行可点**，但删除按钮 `stopPropagation` —— 否则删完会顺带切节点。
* **`busy` 期间禁用按钮**，避免用户重复点击造成并发启动。
  前端的 `run()` 里有 `busyRef` 守卫，即便按钮没来得及禁用也不会重入。
* **日志默认最多 1500 行**，超出的从头部丢弃。后端也有自己的上限。

---

## 8. 可访问性

* 所有交互元素都是原生 `button` / `input` / `select`，键盘可达。
* 模式切换组用 `role="group"` + `aria-label`。
* 状态色之外都有文字（延迟有毫秒数、连接状态有文字），不单纯依赖颜色。
* 对比度按 WCAG AA 选取（正文 `#e6ecf5` on `#0f1420` 约 15:1）。
