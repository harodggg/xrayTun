### #1 `.set__tab.is-active` 用了**未定义 token**，实际渲染成**近白描边**（真 bug，实测）

| 项 | 内容 |
|---|---|
| **位置** | `styles.css:1246`（`border-color: var(--border-interactive)`）；token 定义处：无 |
| **实测现状** | `--border-interactive` 在 `:root` 里**不存在**、且 `var()` **没有兜底值** → 声明在计算值阶段失效 → `border-color` 落到 **`currentColor`**。CDP 实测设置页 `.set__tab.is-active`：`borderColor: rgb(230, 236, 245)`（= `--text`）、`borderTopWidth: 1px`；未选中 tab 是 `rgba(0,0,0,0)`（`.set__tab` 基类 `border: 1px solid transparent`）。<br>对比度：**`rgb(230,236,245)` vs 自身底 `rgb(22,29,44)` = 14.19:1**；若按意图用 `#5c7290` 则是 **3.42:1**。<br>该 token 名字来自我 task-17 给**官网**写的 `site/assets/site.css:48`（那里定义了 `--border-interactive: #5c7290`），**应用侧只抄了名字、没定义值** |
| **更简单的替代** | **删掉这一行**。理由：`.set__tab.is-active` 已经有 **3 个非颜色线索**标注选中态 —— `background: var(--bg-elevated)`、`box-shadow: inset 2px 0 0 var(--accent)`（左侧强调条）、`font-weight: 600`。少一条边框反而更贴合设计系统「层级靠留白 + 一条弱分隔线，不靠给每块画边框」的方向。<br>（若确实要控件轮廓，另一条路是定义 `--border-interactive: #5c7290` —— 但那**改变观感**，不是等价简化，且要回答「为什么选中态要加边框」。） |
| **等价性怎么验证** | 删除后 CDP 复测 `.set__tab.is-active` 的 `borderTopColor` 应等于未选中 tab 的 `rgba(0, 0, 0, 0)`，且 `background / box-shadow / fontWeight / color` 四项**逐字段不变**。删除前后各拍一张设置页截图，除那一圈 1px 边框外应无差异。 |
| **收益** | **用户可见**：现在选中 tab 上有一圈**计划外的近白描边**（14.19:1，在深色界面里相当响）。删掉即消除。<br>同时消除一处「静默失效的声明」—— 与 task-12 的 `--line`、task-46 的 `xattr -dr` 是同一族问题。 |
| **风险** | **低**。一行；无其它地方引用该 token（全项目仅此 1 处）。唯一影响是选中 tab 的边框从「白」变成「透明」。 |
| **备注** | 这条严格说是**缺陷修复**而非「简化」，但最简单的修法恰好就是删。**建议优先做。** |

### #3 `style={{ gap: 8 }}` 在 **11 处**是冗余的（宿主已有 `.row { gap: 8px }`）

### #10 小项：`border` token 被当背景用；一条分隔线用了另一种白

| 项 | 内容 |
|---|---|
| **位置** | ① `styles.css:1598` `.usage__bar { background: var(--border); }`<br>② `styles.css:2019` `border-bottom: 1px solid rgba(255, 255, 255, 0.04)`（连接列表行分隔）；全站其余 14 条分隔线都用 `var(--border)` |
| **实测现状** | ① 订阅页用量条**轨道**的实测背景 = `rgb(38, 49, 72)` = `--border`。语义上「边界色」被当成「表面色」，一旦有人为可访问性调整 `--border`，用量条会跟着变。<br>② 两条分隔线的强度不同：`--border #263148` vs `--bg` = **1.42:1**；`rgba(255,255,255,0.04)` vs `--bg` ≈ **1.12:1**（弱 21%）。全站**唯一**一处白 alpha 分隔线。 |
| **更简单的替代** | ① 给轨道起一个表面色 token（或直接内联 `#263148`，但它本来就该有名字）；② 把那条改成 `var(--border)` 或给它一个明确的「更弱分隔线」token。 |
| **等价性怎么验证** | ① 若新 token 取值就是 `#263148`，则 `background-color` 计算值**逐字节不变**（可 CDP 断言）；<br>② ②会**改变像素**（1.12 → 1.42），所以它是「统一」而不是「等价」，要单独确认那处变明显可接受。 |
| **收益** | 语义正确性 + 一致性；用户基本不可感知。 |
| **风险** | **低**。 |

## 3. 不该简化的（复杂度是必要的）

### 3.1 确定性步进的动画 —— `useFollowScroll` 与拓扑车的 rAF

`useFollowScroll` 与拓扑页的货车动画**刻意**用固定 `dt` 的确定性步进（而不是交给 CSS 动画）。
理由（本项目已付出代价换来的）：**可测性**。`topologyAnimation.test.ts` 用固定 `dt = 1/60s` 的手动时钟驱动 rAF，
才能对「连续 500 帧位移无孤立尖峰」「车只在去程循环」这类**几何不变量**做断言；
换成 CSS 动画后，位置由合成器决定，测试拿不到逐帧位置。

→ **不要提议把它们改成 CSS 动画。** 这不是「复杂实现」，是**为了可验证**而付的成本。
（task-45/47 的教训同样适用：一个「看起来更简单」的写法，可能让某类缺陷变得**不可测**。）

### 3.2 `--status-off: #566a88` 的取值（task-45 的对比度取舍）

它是五档状态色调里**最暗**的一档，实测 **3.34:1**（对 `--bg`），刚好过 WCAG 1.4.11 的 3:1。
看起来「再暗一点更极简」，但**不能**：`--border`(1.42:1)/`--border-strong`(1.78:1) 都过不了 3:1，
而这条线**承载状态信息**，属于「有意义的图形」。
→ 这是**为合规付的明度代价**，不要为了观感把它调暗。

### 3.3 五档状态色与「绿色只属于 `on`」

看起来可以合并（例如 `partial` 也用绿、「反正都是通」）。**不行**：
绿色在本产品里 = 整机受保护，系统代理只有读系统代理的应用走代理。
`topbarStatus.ts` 里那条「绿色只属于 `on`」由测试锁着（含反例）。**合并即回归已修的假陈述。**

### 3.4 媒体查询里「重复」的正常条款

`styles.css` 里 `.highway__side--right` 在基础段与 `@media (max-width: 880px)` 里各出现一次 ——
这是**合法的响应式覆盖**，不是重复。判定标准：**同一选择器、不同的声明体、且处于不同媒体条件** ⇒ 保留。
（真正要删的是 #2 那种「**同一媒体条件、同一选择器、逐字节相同**」的整段拷贝。）

### 3.5 `.sr-only` + `role="status"` + 每状态 `title`

状态线没有文字，色盲用户读不出五档色调。这是**为无障碍付的冗余**，
看起来「一个颜色而已，何必三处」（线色 / 点色 / 可读文本），但去任何一处都会削掉一类用户的可读性。

### 3.6 canvas 里的地球仪

`Globe.tsx` 用 canvas 逐帧绘制（投影、陆地、航线、飞机）。这不是「复杂实现」——
用 DOM/SVG 画 2° 分辨率的陆地位图会**更慢**，用 CSS 也画不出正交投影。**不要动。**

## 5. 一条我必须自己交代的事（与 JSON 无关，但影响本仓库的溯源）

**我在 task-47 提交 `232d5e4` 时，把 `frontend-dev` 的 `.set__tabs` / `.set__tab` 样式一起提交了。**

证据：
- `git show 232d5e4 --stat` 显示 `apps/ui/src/styles.css | 90 ++++--`，而我的改动只有 `.dash__state--*` 那一段（约 26 行）；
- 该提交的 4 个 hunk 里，后 3 个全是 `.set__tabs` / `.set__tab` / `.set__tab:focus-visible`（task-48 的两级设置结构）；
- `git log 232d5e4..HEAD -- apps/ui/src/styles.css` **为空** ⇒ frontend-dev 的 task-48 提交 `c18a5b7` **没有**包含它自己的 styles.css 改动（因为已经在我那次提交里了）。

**原因**：我当时用 `git diff src/styles.css` 审阅，那条命令比的是**工作区 vs 索引** ——
对方的改动已经在索引里，所以**没有出现在我的审阅输出里**，而 `git add <path>` 会把整个文件（含索引里已有的部分）一起提交。
**我没有在提交前用 `git diff --cached` 复核暂存内容**，这是我的流程疏漏。

**后果**：`#1` 那条 `--border-interactive`（未定义 token）在溯源上落在**我的**提交里，但它是 task-48 的代码。
**本文不据此声称是谁的错** —— 只记录事实，供 lead 决定是否需要向 frontend-dev 说明。

**我学到的**：审阅待提交内容应该用 `git diff --cached`（或 `git status` + 完整 diff），
而不是 `git diff`（它看不见已暂存的第三方改动）。
