Info Filter · Jev: filtering timeline junk on X with Jev's typed decisions

This is a Chrome MV3 extension. It screens locally, then asks Jev (TypeSafe System One) a few typed questions (which category of junk this is, plus three independent pieces of evidence — adult, off-platform solicitation, deception — and a severity score) and acts on the returned category, probability and confidence: a hit is hidden; only high-confidence categories can touch the account (mute/block), and by default it only dry-runs. It is not a keyword blocklist: the decision is made by the model, keywords only decide whether a call is worth paying for. Beyond filtering it also tidies up: β (beta) folds repeated / similar / semantically identical items into one, and α (alpha) flags a reply that clearly departs from the majority view (flag only, never hidden).

Six kinds of junk, each with its own switch

Turning a category off means it is neither hidden nor acted on (fallback paths are switched off with it). Categories are decided by the model; the local pre-screen only decides whether a call is worth paying for. Whether an account can be touched is a property of the category, not of a threshold.

Category Typical shape Can it touch the account?
Adult / sexual solicitation local hookups, premium-content promos, "contact via profile", suggestive bait posts Yes at high confidence
Scam / gambling / stock tips guaranteed returns, insider tips, pig-butchering, deposit bonuses, betting groups Yes when the deception evidence clears
Ad / traffic spam "DM me", "link in bio", group recruitment, affiliate and agency spam, coupon bait Yes with strong solicitation and high severity
Clickbait / outrage bait "you will not believe", "share before it is deleted", fake urgency No — hidden only
Low-quality AI / rewritten filler empty platitudes, copy-paste rewrites, keyword stuffing, AI boilerplate No — hidden only
Repeated-text farm one line copied by several accounts within minutes (structural signal, no model call) No — hidden only

How it decides: four tiers, increasingly expensive

A decision is not a single model call. Cheap layers run first, expensive ones only when needed, and no single layer is sufficient to touch your account.

Tier What it does Cost
Local pre-screen Readable regex over the text, the display name, card text and image alt; emoji inserted inside keywords (处🐕男) are stripped before matching; whitelisted accounts, your own posts and too-short posts without media are skipped 0 requests
Triage (model first) Posts the keywords missed are still asked one cheap question ("is this junk: spam, scam bait or filler?"). At ≥0.75 it escalates to the full five questions; at ≥0.65 it is only hidden as "needs review" one single-question call (≈ 1/5 of the full set)
Repeated-text farm The same content-free line copied by ≥2 different accounts within 30 minutes → all of them hidden (including earlier ones that were let through). Normalisation strips emoji, punctuation and case 0 requests
Jev typed questions Which category? Is it adult? Is it off-platform solicitation? Is it deceptive? How severe? — questions are written in English; the post itself is never translated one call

Three invariants (documented in code and covered by unit tests): ① an account action needs an account-eligible category plus category confidence, severity and at least one piece of hard evidence (adult / deception / strong solicitation); the pre-screen, the skin-tone heuristic, the farm detector, the vision model and the triage probe on their own can reach "hidden" or "needs review" but never block; ② uncertainty is downgraded, never patched; ③ every band states its reasons, visible in the filter bar and the audit log.

What happens on a hit is entirely your choice. The default is dry-run: it only records "who would have been muted" in the audit log and clicks nothing. To make it act you must explicitly enable "auto mute" (and optionally "mute hidden-band accounts too") in the popup. Blocking always requires the high-confidence action band.

Beyond filtering: β folds duplicates, α flags outliers (new in v0.4.0)

Filtering removes noise; these two organise what is left. Both are presentation only: they never change the hide decision or any account action, and each can be switched off.

ConceptWhat it doesBoundaries
β · beta Repeated / similar / semantically identical items are folded so the timeline shows them once. Not string equality: local near-duplicate screening picks up to six candidates (3-gram similarity, same thread or same farm cluster), then one batched Jev call asks whether they carry the same information or claim (paraphrase, translation and rewrite all count). Folds collapse to a thin bar: same content as @… · N more similar · [expand]. The first item stays; only “the same thing” folds — different opinions in one thread do not
α · alpha In reply threads, a reply whose view clearly departs from the majority and still makes a substantive point gets an α · differs from the majority badge. Flagged only — never hidden or folded; replies only by default

Cost is bounded and measurable: no local candidate means no call at all, at most one semantic call per post, measured at about 536 input tokens per call (11 semantic calls across 34 real samples: 5,898 in / 330 out). Section 1.6 of the options page exposes the thresholds, candidate count and reference count; the popup has “fold duplicates (β)” and “flag outliers (α)” switches. Over budget or a failed call only skips the tidy-up and is counted — filtering is unaffected.

v0.4.1: three real-world samples, two misses closed

X folds suspicious replies into a hidden “probable spam” section in reply threads. A user sent us three posts from it; the real model caught two and never even asked about the third (a three-character post with no media, skipped locally). This release closes both gaps:

SampleVerdict nowWhy
已老实 (3 chars, inside X’s spam section)review (hidden for confirmation, never an account action)X’s own section heading is read as a structural signal (x_spam_section)
只入身体🥦🌰不入生活 (display name “找炮友”)block (would mute in dry-run)triage + five questions (adult 0.94)
只入身体🦵💪不入生活 (same line, different emoji)hidetext farm: only 8 effective characters after normalisation, so the floor had to drop from 10 to 8

Two rules stay intact: X’s section marking is a structural signal — it can only hide as “review”, never touch an account; and the 8-character floor cannot cause false positives, because a two-account farm hit still has to pass the content-signal gate (adult / deception / solicitation / local features / triage bait). Three-character posts elsewhere in the timeline are still skipped locally to save calls.

Install and configure

There is no build step: the unzipped folder is a loadable extension directory.

# 1) download and unzip
unzip jev-x-filter-0.4.1.zip -d info-filter

# 2) open chrome://extensions → enable Developer mode
#    → "Load unpacked" → select the unzipped info-filter directory

# 3) click the extension icon → Options → section 1 "Jev access"
#    · to use your own key: keep the TypeSafe Official preset and paste the key
#    · to try it for free: switch to OpenCode Zen (jev-1.13-free, no key needed)
#    · press "Test connection" and make sure typed answers come back

# 4) pick the categories you want in section 1.5, then open x.com.
#    Watch the filter bars and the audit log, and only turn off dry-run
#    once you have seen it behave on your own timeline

Judging happens inside the extension’s service worker; the API key is stored only in chrome.storage.local and is never exposed to the page. The options page can export and import the account blocklist (JSON), one click on a filter bar adds a false positive to the whitelist, and the popup has six quick category switches.

Verification status

Every claim here is reproducible in the repository, and every real-world miss becomes a regression fixture — the project’s rule is that a lesson turns into a mechanism.

Check Command Result
Unit tests npm test 234 passing (wire contract, category gates and switches, pre-screen, farm, α/β semantics, menu matching and adversarial cases, image pixels, blocklist, audit, pipeline)
Real-Chrome end-to-end npm run verify 116 passing: load the extension over CDP → fake-X fixture page (20+ posts, six real-world traps: anti-item menu entries, a stale Dropdown, a trigger with no layout box, async menu rendering, localised menu entries, and a menu that genuinely lacks the target item) → decide → hide → α badge / β fold → click the menu (including the “mute hidden band too” boundary and “never guess-click: leave a diagnosis”)
Static self-check npm run check 21 passing: manifest references, minimum permissions, no remote code / eval, content scripts must be classic scripts
Real-model check JEV_API_KEY=… node tools/live-check.js 37 real-world samples, 0 safety violations, 0 expected hides missed; β folds 11 · α flags 1 · semantic calls 12: adult solicitation and scams are caught, clickbait and low-quality filler are hidden only, while everyday posts, moderation news, sex education, swimwear and fitness posts all pass

Real-world feedback drove four rounds of fixes, each of which left a regression fixture behind: the display-name vector (🍑真实同城约p🍑主页联系🔞免费 with harmless post text), the keyword-free suggestive brag from a gibberish account name, the reply-section text farm (one line posted by four accounts within a minute), and emoji inserted inside keywords (display name ❤️处男免费❤️, post text 处🐕男), and farm variants that each insert different junk characters (…没我骚蝎🐾… / …没我骚🐾💩…). Two of them were architectural misses: as soon as keyword matching decides whether the model is asked at all, phrasings outside the table are unreachable for the model — which is exactly why the model-first triage tier exists. The emoji case then led to symbol-stripping matches and to dropping the farm threshold to two accounts; the farm variants then turned exact-match farming into near-duplicate clustering and exposed that MV3 worker recycling clears runtime state (including rate limits) — now restored via chrome.storage.session. v0.3.0 turned the adult-only gate into a category-based one: whether an account can be touched is decided by the category. v0.4.0 caught two more live-site traps: β never fired at all (window entries had no tweet id, so every β candidate anchor was skipped — now a stable author+text hash stands in when the id is missing) and auto-actions failing with menu_item_not_found:mute (root cause: the extension hides the post first and only then clicks ⋯, which therefore had a 0×0 bounding rect, so X’s menu layer had no anchor and never rendered). Both got regressions: disabling the fix turns the relevant end-to-end scenarios red immediately.

Known limits (read before you arm it)

  • It will hide things it shouldn’t. The decision is probabilistic: sex education, art, fitness, edgy jokes, local slang, ordinary advertising and serious news headlines can all be caught or missed. Every hit can be restored with one click or added to the whitelist; treat the default dry-run as an observation period.
  • Auto mute/block are real account actions (performed by clicking the UI menus, not by calling private APIs) and carry platform rate-limit risk. The extension rate-limits, de-duplicates and dry-runs by default, but it cannot promise immunity.
  • Jev cannot see images. Image-only content relies on the local skin-tone heuristic plus the "image-only post" shape and is hidden as "needs review"; it will not mute an account because of a picture. A vision endpoint can be configured separately for stronger image judgement.
  • It depends on X’s DOM. A redesign can break the menu automation; failures are logged as action_failed in the audit log instead of silently mis-clicking: the failure note names the menu entries that were actually present (hover to read it), which is what you need when a selector drifts. All selectors live in one file so they can be updated quickly.
  • You pay for your own model quota. Candidates and triage each cost one call; rate limits and daily budgets are built in, and going over the budget degrades to "needs review" rather than hiding everything.
  • It is for your own timeline hygiene only. There is no bulk reporting and no ability to target other people’s accounts.

FAQ

What are β (beta) and α (alpha)?

β folds repeated / similar / semantically identical items so the timeline shows them once (a translation, a rewrite or a paraphrase of the same thing counts as identical; the judgement is made by the model, not by string equality), and the thin bar can be expanded. α flags a reply that clearly departs from the majority view — flag only, never hidden, so you do not miss the minority report. Both are presentation only: they never change hiding or account actions, and each has its own switch.

Can auto-mute / auto-block fail, and what happens then?

Yes — an X redesign, a different UI language, or a menu you already opened on another post can all make the automation fail to find its target. When that happens it gives up and leaves a trace: the filter bar says “action failed … click ‘mute now’ to retry”, hovering shows the menu entries that were actually present, and the same diagnosis goes to the audit log. It never guesses at an ambiguous entry — clicking “unmute”, or acting on someone else’s account, is worse than failing. v0.4.0 fixed the most common cause (hidden post → ⋯ trigger had no box → the menu never rendered).

Which kinds of information can it filter?

Six, each individually switchable: adult and sexual solicitation, scam/gambling/stock-tip fraud, ad and traffic spam, clickbait and outrage bait, low-quality AI and rewritten filler, and repeated-text farms. The first three can mute or block an account at high confidence; the last three are hidden only.

Will it hide normal content?

Yes, sometimes. Any filter is probabilistic, so the design keeps the cost of a mistake low: a hidden post can be restored with one click, marking it a false positive whitelists the account, and account actions are recorded without being executed by default.

Can auto-mute or auto-block get my X account suspended?

Automatic actions are real account operations performed by clicking the UI menus — the same effect as doing it by hand — so platform rate-limit risk exists. The extension defaults to dry-run, spaces out actions and acts on each account only once; watch the audit log for a few days before turning dry-run off.

Does it cost anything to use?

The default preset is the TypeSafe official gateway, which needs your own Jev API key; you can also switch to OpenCode Zen’s free tier (model jev-1.13-free, no key required) to try it at zero cost. Rate limits and daily budgets are built in, and exceeding them degrades decisions to "needs review" instead of calling the model anyway.

Which browsers are supported?

Chrome 120 and later in its Manifest V3 environment; Edge, Brave and other Chromium-based browsers can load it too. Firefox and Safari are not supported because their content script and extension APIs differ from MV3.

Why is image judgement weaker than text?

Because Jev is a text-only decision model: its input can only be text, and it cannot see pictures. Images therefore go through a local skin-tone pixel heuristic that is only used to hide image-only posts as "needs review", and it never triggers an account action on its own. For stronger image judgement you can configure a vision model endpoint in the options page.

Where does my data go?

Only post text and a little metadata (author, position, alt text, card text, local skin-tone ratio) are sent to the Jev gateway you configure. The API key stays in chrome.storage.local and is used only by the background service worker; images stay local by default; the optional audit webhook is off by default and posts one event per decision when enabled.
