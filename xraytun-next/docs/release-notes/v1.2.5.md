# xraytun-next v1.2.5 —— 助手不再拒绝合法 daemon：audit token 失败的两个真因

> 你装上 v1.2.4 再点「启动」，这一屏换成了：
> `permission_denied: 对端不是已安装的 XrayTun 组件（cdhash 绑定, uid=501 pid=…）:
> SecCodeCopyGuestWithAttributes 失败（OSStatus -67049）`
>
> **这不是你装错了，也不是配置错了。** 这是把 v1.2.4 的两个 TUN 拦截点修掉之后，
> 下一条真正会挡路的链路：**特权助手在验证 daemon 的身份**。

## 一、这一屏在说什么

`-67049` 是 Security.framework 的 `errSecCSBadObjectFormat`。helper 是 root 守护进程，
它在接受 daemon 的任何指令之前，必须先证明「对端确实是那个已安装的 XrayTun daemon」。
它的做法是：从 AF_UNIX socket 取对端 audit token → 用 audit token 取出对端 `SecCode` →
把对端 cdhash 与 `/Applications/XrayTun.app/Contents/Resources/xt-daemon` 的 cdhash 比对。

这次挂在**第一步取 `SecCode`**，根本没走到 cdhash 比较。我们查出来三件事：

1. **旧路径只有一条**：自己拼 `{kSecGuestAttributeAudit: CFData}` 再调用
   `SecCodeCopyGuestWithAttributes`。这条路径在真机现场返回 `-67049`，而旧测试只断言
   `Unauthorized`、没有断言失败点 —— 所以它从未被真正的正路径覆盖过。
2. **即使取到 SecCode，旧比较也可能误判 universal 二进制**：只比
   `kSecCodeInfoUnique` 的单个哈希时，静态文件与正在运行的进程可能选到不同架构切片。
3. **helper 是独立 launchd 服务，App 升级不会自动替换已安装的 helper**。
   不提示用户更新助手，就会出现「装了新版 App、跑的还是旧 helper」——
   这也是为什么 v1.2.4 这一屏看起来像「新版本又坏了」。

## 二、改了什么

| # | 改动 | 判据 |
| --- | --- | --- |
| 1 | helper 首选 `SecCodeCreateWithAuditToken`（`securityd` 自己用的入口）；失败才回退到旧的 `SecCodeCopyGuestWithAttributes`，再失败才按 `LOCAL_PEERPID` 做最后一次兼容回退。每次失败都保留真实 OSStatus | macOS CI 真机测试：ad-hoc 签名的裸 Mach-O 对端通过真实 AF_UNIX socket 连接，`peer_guest` 必须成功返回 SecCode |
| 2 | cdhash 绑定改为**每个架构一个 cdhash**（`kSecCodeInfoCdHashes` + `kSecCodeInfoUnique`），安装文件与对端进程的集合**有交集**才算同源 | 同一条测试：对端运行切片的 cdhash 必须与磁盘已签名文件的集合相交；`cdhash_reader_rejects_unsigned_file` 仍拒绝未签名文件 |
| 3 | 设置页检测「已安装助手与 App 包内助手是否逐字节不同」，不同就显示「版本与当前 App 不一致（需要更新）」并给出「更新助手」按钮 | UI：`helper-install.test.tsx` 新增「update_available ⇒ 文案 + 更新按钮 + 真的调 install_helper」；本机 `npm test` / `tsc --noEmit` / `npm run build` 全绿 |

**安全口径没有放宽成「信任任何人」**：audit token 仍是首选；最后的 pid 回退会留下 warn，
并且仍然要求对端 cdhash 与已安装文件逐字节相同；未签名文件仍然拒绝。

## 三、证据（这一版新增的真机级测试）

macOS CI 新增 `ad_hoc_signed_peer_is_located_by_audit_token_and_cdhash_matches`：

- 把**当前测试二进制**复制到临时目录，`codesign --force --sign -` 做 ad-hoc 签名；
- 以子进程执行这个副本（不是 `/bin/sleep` 那类可能由 dyld shared cache 提供的内核系统二进制）；
- 通过真实 `AF_UNIX` socket 连接，父进程用 `LOCAL_PEERTOKEN` 取 audit token；
- 断言 `SecCodeCreateWithAuditToken` / cdhash 集合交集整条链路成功。

这比旧测试强的地方：旧测试只要求「不受信对端被拒」，无论失败发生在取 token、取 SecCode
还是校验签名都会绿；新测试要求**合法 ad-hoc 对端必须被认出来**，这才是生产正路径。

本机可验：`bash scripts/guard.sh` PASSED、UI 全量 `vitest` / `tsc --noEmit` / `vite build`。
Rust 编译与测试由 CI 判定；具体 run id 与结果见发布记录。

## 四、请你这样再试一次（顺序很重要）

1. 装 v1.2.5 的 DMG（覆盖旧 App）。
2. 打开 App → **设置**。如果「特权助手」卡显示「**已安装，但版本与当前 App 不一致（需要更新）**」，
   先点「**更新助手**」并给一次管理员授权。**不要只重启助手**：重启不会替换旧的 helper 二进制。
3. 节点页导入/选择节点 → 仪表板「启动」。
4. 如果还失败：把错误框原文（含 `code` 与 OSStatus）或
   `~/Library/Logs/XrayTun/xt-daemon.log` 最后几十行发我；helper 侧日志在
   `/Library/Logs/XrayTun/helper.log`，如果能一起取到更好。

## 五、仍然没有做到的（不许含糊）

- **TUN 真机接管（utun / 路由 / DNS）仍然没有验收**。这一版修的是「helper 连合法 daemon
  都认不出来」这个可复现的拦截点，不是「TUN 已经能用了」。
- 未公证、Gatekeeper 首次打开仍以你真机为准。
- 订阅没有定时自动刷新；托盘「退出」只退界面，隧道继续跑。
