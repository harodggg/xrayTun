# xraytun-next v1.1.5 · 打包链路：dmg 从**已签名**的 app 重新打

**应用代码与 v1.1.4 完全相同**（含那一版修掉的侧栏导航缺陷）。这一版只动打包链路，
因为 v1.1.4 的 dmg 没能产出。

> 顺带说明 v1.1.4 的发布说明里列了 `XrayTun_1.1.4_universal.dmg`，但那次 dmg 打包失败、
> 资产里只有 `.app.zip` —— 说明与资产不一致是我的错。这一版把资产写成「存在什么就是什么」。

## 为什么 dmg 需要重做

**缺陷**：dmg 是在 `tauri build` **内部**打好的，而 ad-hoc 签名发生在打包**之后** ——
所以 **dmg 里装的 app 是未签名的**，而 CI 校验的是 `bundle/macos/XrayTun.app`。
也就是说：**我们验的东西，和用户从 dmg 拿到的东西，不是同一个。**

**为什么改起来不只是调顺序**：把 dmg 改到签名之后自己打，两次都死在

```
could not access /Volumes/XrayTun/XrayTun.app/Contents/Resources/xray - No space left on device
hdiutil: create failed - No space left on device
```

而 tauri 自己的 dmg 也在另一次运行里失败（`error running bundle_dmg.sh` +
`diskimages-help` 孤儿进程）。把这些拼起来看，指向同一个真因：
**runner 的 SSD（约 14 GB）被构建中间产物塞满了**——两个架构的 `target/`、合并后的
universal `target/`、`node_modules`、universal 二进制，而 dmg 恰恰是最后一个要写盘的步骤。

**修法**：

1. `tauri build --bundles app` —— 只出 `.app`，不再让 tauri 打 dmg；
2. ad-hoc 签名 → 校验 → 打 `.app.zip`（顺序在打包**之前**完成签名）；
3. **腾磁盘**：删掉两个架构的 `target/`、universal 的 `deps/build/.fingerprint/incremental`、
   `node_modules`、`binaries/`（`.app` 保留），前后各打一次 `df -h` 留证据；
4. 用 `hdiutil` 从**已签名的** `.app` 打 dmg（参数照抄 tauri 的 `-fs HFS+ -fsargs`，
   避免镜像尺寸被估小），**并把它挂起来 `codesign --verify --strict` 里面的 app**。
