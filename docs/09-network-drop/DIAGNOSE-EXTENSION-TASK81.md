## 1. 为什么要加（症状 → 缺口）

用户症状：**有时**连不上 deepseek / **有时**连不上本机 `127.0.0.1:3080` / 国内不通国外良好。
lead 在取证那一刻**复现不到**（国内国外全通） ⇒ 必须**在故障当下**把现场抓住。
而当时的脚本会**漏掉**三类东西：回环只测 `.1`、多 VPN 栈没有证据、国内外没有同一时刻对照。

**为什么必须「当下」跑**（已写进脚本头部注释）：间歇性故障事后跑只能看到「已恢复」的样子；
路由表 / 活动 DNS 解析器 / utun 数量 / 旁路表只在那一刻是证据。

## 3. 敏感性验证（本卡存在的理由）：**两条原始输出**

判读逻辑是纯函数 `judge_loopback_routes`（读 `netstat -rn -f inet` 文本），
`--self-test` 就是拿**逐字现场样例**与**健全形态**各跑一次。原始输出（`bash scripts/diagnose-network-drop.sh --self-test`，退出码 0）：

```
=== --self-test 1/2：lead 现场样例（**必须**报「异常」）===
127        192.168.0.1   UGSc   en0
127.0.0.1  127.0.0.1     UH     lo0
---- 判读 ----
  [异常] 127/8 的回环路由指向**非 lo0** 的出口：dest=127 gateway=192.168.0.1 flags=UGSc netif=en0
         ⇒ 除 127.0.0.1（自带 /32 → lo0）以外，其它 127.x.x.x 会被送到 192.168.0.1。
判读退出码=1（0=正常，1=发现异常）
✓ 符合预期：抓到「127 路由指向非 lo0 网关 ⇒ 异常」

=== --self-test 2/2：健全形态（**必须**报「正常」）===
127.0.0.1  127.0.0.1  UH  lo0
---- 判读 ----
  [正常] 回环路由形态健康（127.0.0.1/32 → lo0，且没有 127/8 via 网关）
判读退出码=0（0=正常，1=发现异常）
✓ 符合预期：健全形态判成正常

self-test：双向敏感性**通过**（异常样例报异常 / 健全样例报正常）
```

> 样例来源：第 1 组是 **lead 现场 `netstat -rn -f inet` 输出行本身**（卡面里跟在后面的
> 「← ⚠️ 127.0.0.0/8 被静态路由指到局域网路由器」是他的**注解**，不是命令输出，故不录入）；
> 第 2 组是卡面指定的健全形态。**没有为了凑出「红」而伪造输入。**

## 4. 回环那条路由：是什么、**归属是谁**、修了没

**实测事实（2026-09-21 19:2x，机器上仍能读到）**：

```
$ netstat -rn -f inet | grep -E '^127'
127                192.168.0.1        UGSc                  en0
127.0.0.1          127.0.0.1          UH                    lo0
$ ping -c 1 127.0.0.2
ping: sendto: Can't assign requested address
$ for a in 127.0.0.1 127.0.0.2 127.0.0.3; do nc -z $a 3080; done
127.0.0.1:3080 → rc=0（curl http=401，DSH GUI 正常）   127.0.0.2:3080 → rc=1   127.0.0.3:3080 → rc=1
```

**归属 = XrayTun 自己装的**（代码证据，**不是**按进程名猜的 —— 这一点我先前猜错过，已更正）：

1. **修复前**（`63b84dc^`）`crates/xt-proto/src/lib.rs` 的 `default_bypass_networks()` **含 `"127.0.0.0/8"`**；
   去掉注释后与连接态实读的旁路集合逐条吻合：`10/8、100.64/10、127/8、169.254/16、172.16/12、192.168/16、224/4`。
2. `crates/xt-tun/src/plan.rs` 把**所有 IPv4 旁路网段一律指向物理网关**（`PlannedRoute::bypass(..., bypass_via(&physical, ...), ...)`）——
   于是 `127/8` 也被指向 `192.168.0.1`。
3. **修复已在 HEAD**：`63b84dc`「fix(tun): 回环绝不经由物理网关 —— 127/8 移出旁路列表 + 规划层防御（task-83 一）」，
   改的正是这两个文件；修复后的 `default_bypass_networks()` 里**没有** `127.0.0.0/8`，
   `plan.rs` 还加了「**回环网段不装路由**」的规划层防御。
4. ⇒ 机器上**仍**看到这条路由，最合理的解释是：**这台机器上跑的是已安装的旧版 App**
   （实测运行中的核心来自 `/Applications/XrayTun.app/Contents/Resources/xray`），
   新代码还没上机；旧会话装下的路由在没有回滚/重连的情况下会留在表里。

## 5. 一处必须留下的**方法学**教训（我自己犯的）

我第一次跑 §8.7 时看到：
`SOCKS → www.baidu.com` 报 `rc=35 SSL_ERROR_SYSCALL`（而 SOCKS → google/github 正常），
就把它写成了「**这正是用户症状的活体形态**」。lead 复测 4 轮全部 200，**未能复现**。

我把脚本改成 **3 轮**后再跑，本轮实测：

```
轮1：SOCKS 国内 baidu=200  国外 google=204
轮2：SOCKS 国内 baidu=200  国外 google=204
轮3：SOCKS 国内 baidu=200  国外 google=204
3 轮中失败次数：国内 baidu 0/3；国外 google 0/3
  [正常] 经代理国内外都通（国内失败 0/3、国外 0/3）
```

⇒ **正确口径**：那是**单次采样**，4 轮/3 轮复测未能复现，**疑为瞬态**，**不是**稳定现象。
**单次采样 + 结论性措辞 = 假红**，而假红和假绿一样会把人引到错方向
（与「按 80 行就断言重复够了」「880 断点 125 行」是同一类错误）。
脚本因此固定：**经代理这一路跑 3 轮，报「几轮中几轮失败」**，
只有**多数轮**失败才升格为异常，单轮失败一律输出成「**可疑·瞬态，不下结论**」。

顺带一条口径：`SOCKS → qq.com` 返回 `501` 是**源站返回的 HTTP 501**，不是网络失败，不计入「国内不通」。

## 6. 判据强度（诚实清单）

**确定性判据**（可以直接当异常、不需要人再判）：
* §3c `127/8` 未落在 `lo0`（本次实跑命中，且 `--self-test` 双向验证过）；
* §2c `.1` 通而 `.2` 不通（本次实跑命中：`ping` 直接报 `Can't assign requested address`）；
* §8.7 国内外**同一时刻**对照（按多数轮）；
* §8.8 「隧道已不在但 DNS 仍指向哨兵 198.18.x」。

**只能提示可疑**（需要人判断、不能据此定性）：
* §6b 的 `utun` 数量与第三方栈共存（现场 7 个 utun，本次报「可疑」）；
* 代理旁路表内容（它只能说明「谁装了什么」，不能说明「它现在是故障原因」）。

**本工具没有覆盖**：
* 真机 App 安装/更新流程、GUI 是否卡住；
* **回环路由是不是「旧版本遗留」**：本工具只能报「现在表里有这条路由」，
  要判断它是否由**当前**运行的连接安装，得在连接/断开的前后各跑一次（lead 已做，按引用记录）；
* IPv6 一侧（`::1`、`fe80::/10` 的旁路）本轮只列不判；
* 内核扩展/系统代理的其它来源（只列旁路表与代理设置，不追溯谁写的）。

## 7. 用法

```bash
./scripts/diagnose-network-drop.sh                 # 现场取证（报告默认落 ~/Desktop）
./scripts/diagnose-network-drop.sh --out /tmp/x.txt
./scripts/diagnose-network-drop.sh --self-test     # 离线自检：只跑判读逻辑，不联网、不写报告
```
