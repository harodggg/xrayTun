# xraytun-next v1.1.3 · 修 v1.1.2 引入的缺陷 + 让壳代码也受不变量判据约束

> **v1.1.2 有一个自己引入的缺陷，请不要使用它**（该版本的 Release 已撤下）。
> v1.1.3 是它的修正版，包含 v1.1.2 的全部修复。

## 一、v1.1.2 的缺陷：序号闸门被「每次 hello」归零，把恢复按钮变成了自杀按钮

**症状**：正常用着，一旦传输出过问题，点「重新连接」反而让界面**永久**卡死 ——
而且比点之前更糟（点之前还有可能恢复）。

**根因**：v1.1.2 给桥加了序号闸门，规则写成「收到 UI 的 `hello` 就把序号归 1」。
但 UI 侧的期望序号（`tauri.ts` 的 `expectedSeq`）是**每个页面会话**从 1 开始的闭包
变量，它**只在页面重建时**才回到 1。于是：

- 页面重载：两边都归 1 → 一致 ✓（这是 v1.1.2 想修的）
- 用户按「重新连接」（同一个页面里第二次 `hello`）：桥归 1，UI 还在 N →
  下一条事件被判「跳号」→ `fail()` 把客户端**永久钉死**（`closed = true`，
  之后每个请求都立刻 reject）→ 再按也无效 ✗

**修法**：把「归零」这件事**只留给页面开始加载**（`on_page_load`）这一个信号；
同一个页面会话里的第二次 `hello` 不再改动序号，两边始终对齐。
即：归零的是页面会话，不是 `hello`。

## 二、`guard.sh` 从此也扫壳代码

不变量守卫（I1 禁 sleep/轮询、I2 禁回落/重试/降级、禁占位、非测试源码禁 `.unwrap()`）
的扫描范围一直只覆盖 `crates/`，**从不包含 `apps/desktop/src/`** —— 也就是说壳里的
等待、超时、命名从来没有被机器判据覆盖过，「提交前跑一遍 guard」对壳是一句空头承诺。

现在扫描范围含 `apps/desktop/src`，汇总行也改为报**实际被扫**的数量
（`rust=53`，而不是只数 `crates/` 的 48），免得数字与范围不一致再误导人。
本次改动在这套判据下 0 违规。

## 三、v1.1.2 带来的三项修复（本版继续包含）

1. **冷启动竞态**：壳先建主窗口、再起 daemon，页面脚本可能抢在 daemon `bind()` 之前
   发出引导链那**唯一一次** `hello`，那一次必然失败且不会重发 → 界面永久停在错误态。
   现在 daemon 在 `bind()` 成功后往 stdout 报一行就绪信号，壳**等它**再建主窗口
   （事件驱动等待，不是轮询）。
2. **界面没有任何恢复路径**：传输错误框现在有「**重新连接**」，用同一条引导链重新
   握手；仍然**没有任何自动重试**。
3. **WebView 重载后事件序号错位**：桥按页面加载关闸归零、按 `hello` 开闸补发滞留
   事件，重载后界面收到的第一帧不再被判「跳号」。
