# `scripts/net-metrics.py`：把「改前 / 改后」的三组数字固化成一条只读命令（task-101）

> 为什么要有它：`task-97`（v6 改写）与 `task-98`（看门狗判据）都会在 **v0.8.34** 上到用户机器，
> 而「修好没修好」此前只能靠**临时 Python 片段** —— 那东西只活在某个人的会话里。
> 本项目栽过「不可复制的现场只存在于临时目录 = 等于不存在」，也栽过「CSS 规则数的口径不对」。
> 所以：**口径写进脚本 + 自测 + 敏感性**，以后任何一次「改前 vs 改后」都用同一条命令。

## 1. 用法

```bash
python3 scripts/net-metrics.py                       # 默认定位 macOS 应用日志目录；全部记录
python3 scripts/net-metrics.py --since 00:00         # 只算今天
python3 scripts/net-metrics.py --until 13:42:30      # **固定到某个时点 ⇒ 数字可复现**
python3 scripts/net-metrics.py --json                # 机器可比对
python3 scripts/net-metrics.py --self-test           # 自测（只写 /tmp，不联网）
```
只读：**不修改/移动/删除日志**，不联网，不跑 cargo，不碰 `site/**`、`scripts/check.sh`、`scripts/diagnose-network-drop.sh`。

## 2. 三组指标各自回答什么

| 组 | 回答的问题 | 关键口径 |
|---|---|---|
| **① task-97** | 「v6 改写」与「连接失败」的**相关性**：按 session id 归并连接 → 全是 v6 / 全是 v4 / v6+v4 三类，各给条数、`failed to open connection` 条数与百分比；另给两行行级计数 | 一律**按行内 session id `[…]` 归并**；`replace destination with tcp:[…]` 判 v6、`…tcp:<v4>` 判 v4 |
| **② 探针** | 探针判据可靠吗：连接数 / 成功 / **失败·有 `failed` 行** / **失败·无结局行**（按目标拆）、轮数、成功耗时 中位/p90/p95/p99/max、**>6s 才成功的条数** | 连接 = `proxy/socks: TCP Connect request to tcp:<目标>`；分轮 = 相邻间隔 **>5s**；耗时才用**消息内微秒时间戳** |
| **③ 自愈** | 误判的**代价**：`已作废` / `物理出口已变化` / `隧道已自动恢复` 逐条时间，以及两种空档口径 | **口径A** = 作废 → 下次 core 启动；**口径B** = 最后一条流量证据 → 下一条流量证据（task-95 口径） |

**去重（必须）**：按 `(ts_unix, message)` 去重。`app.jsonl` 与 `app.1.jsonl` **有重叠** ——
本次实读 **286,061 行 → 保留 242,283 条，丢弃 39,934 条重复**（另有 7 行坏 JSON）。不去重会把同一件事算两遍。

## 5. 与卡片基线**逐项对齐**（这一段是「口径对不上要说明原因」）

卡片基线是 **13:42 左右的一次快照**（我用 `--until 13:42:30` 复现该时点）：

| 指标 | 卡片基线 | 我 `--until 13:42:30` | 差异 |
|---|---|---|---|
| `replace …tcp:[240e…` 行数 | 534 | **540** | +6（+1.1%） |
| `failed to open connection` 行数 | 47 | **45** | −2（−4.3%） |
| v6-only 连接 / 失败 | 42 / 40 = **95.2%** | **41 / 38 = 92.7%** | 条数几乎一致，百分比差 2.5pp |
| mixed 连接 / 失败 | 199 / 0 | **201 / 0** | +2（+1%） |
| **v4-only 连接 / 失败** | **408 / 0** | **480 / 0** | **+72（+17.6%）← 未解释** |

**差异原因（分三类说清楚）**：
1. **窗口**：卡片写「2026-09-22 全天」。若不加 `--since 00:00`，脚本会把 **09-21 21:35** 的记录也算进来
   （`app.1.jsonl` 起于 09-21 20:59）—— 那会把每个数都抬高（v6-only 41 → 43、v4-only 480 → 487，且多出一条 09-21 的「已作废」）。
   **所以引用时必须写明窗口。**
2. **日志在增长**：同一份日志，13:42 时 `[240e` 行数 540、现在（14:00）**727** —— 数字是**时点值**，脚本会打印文件大小/mtime 作快照标识。
3. **v4-only 的 +72 我解释不了**：我试过「是不是把单行 session 算进去了」（480 条**全部**只有 1 行替换目标）、
   「是不是某个行数桶正好 72 条」（轨迹行数分布是 6/8/9 行，**没有 72 的桶**），都对不上。
   ⇒ **这是一条未解释的口径差异**，我**不猜**是谁对；从 v0.8.34 起，**改前/改后都用本脚本的显式规则**，就不会再有这个问题。

## 6. 诚实清单：这个脚本**测不到**什么

1. **不做因果**：① 只给相关性（v6 改写 vs 失败、tun 错误 vs 重建窗口）。「v6 改写导致了用户的失败」不在这里证。
2. **探针失败 ≠ 用户当时上不了网**：它只证明「这一个 URL 经 SOCKS 的这一次请求没成」；端到端体验要另外的证据。
3. **看不到应用侧超时**：探针的 6s 超时**不落盘** ⇒ 「某条探针在 6s 被放弃」无法直接观测，只能用「>6s 才成功」的条数**间接**量化误杀。
4. **`app.jsonl` 不是完整应用日志**：`push_log()` 只进内存环形缓冲（`state.rs:319`），只有 `state.log()`（`state.rs:386`）落盘
   ⇒ 看门狗的过程行（「隧道连续 N 次不通」「正在自动重建」）**不在文件里**，所以探针**逐轮**成败读不出来。
5. **真机行为不可见**：安装/更新/重装 helper、Gatekeeper、UI 表现，本脚本一概看不到。
6. **依赖日志格式**：核心日志格式变化（例如 session id 格式、`replace destination` 文案）会让指标失真；
   `--self-test` 只能证明**逻辑**对，不能证明**格式**没变。
7. **口径A/口径B 不是同一件事**：两者今天相差 6s 左右（2665 vs 2657），引用时必须写明用哪个。
