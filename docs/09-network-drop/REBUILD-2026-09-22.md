## 2. ★ Q2（核心）：每次「已作废」时，隧道到底是不是真的不通？—— **不是。看门狗误判。**

**判据**：该时刻 ±60 秒内，核心自己的日志里还有没有真实流量行
（`proxy/vless/outbound: tunneling request` / `proxy/freedom: connection opened`）。

| 已作废时刻 | ±60s 内 tunneling_request | connection_opened | 作废**前**最后一条流量证据 | 距作废 |
|---|---|---|---|---|
| 11:14:51 | **52** | 28 | `11:14:43.421675 proxy/freedom: connection opened to tcp:wsdexpri.coinall.ltd:443` | **8s** |
| 12:16:26 | **59** | 17 | `12:16:21.221086 proxy/freedom: connection opened to udp:210.2.4.8:53` | **5s** |
| 12:30:12 | **90** | 30 | `12:30:00.580566 proxy/vless/outbound: tunneling request to tcp:www.google.com:443 via 45.207.…` | **12s** |
| **13:28:16** | **243** | **84** | `13:28:10.101958 [3314281142] proxy/vless/outbound: tunneling request to tcp:cp.cloudflare.com:…` | **6s** |

**结论（明确）：是误判。** 四次「已作废」发生的那一刻，隧道**都在正常转发流量**，
最近的一条证据距离作废只有 5–12 秒；其中 13:28 那次，作废前 6 秒**刚刚**有一条
`tunneling request to cp.cloudflare.com`（**正是看门狗自己的探针目标**）成功进了代理出口。

**为什么可以断定是「探针失败」而不是「流量也停了」**：从代码路径看，
`invalidate_after_failure(…, FailureExit::WatchdogRebuild)`（tag `core.rs:898`）**只在看门狗重建失败时**执行，
而看门狗开始重建的前置条件是 `failures >= FAILURES_BEFORE_REBUILD = 2`（tag `core.rs:605-606`、`1477`）。
⇒ 那一刻探针**至少连续失败 2 次**（≥2×10s 窗口），而**同期真实流量仍在走** —— 即**探针假阴性**。

# 附录 A（task-99）：探针假阴性是不是「国内域名被改写成 IPv6」造成的？

**结论：部分成立**（三条分述见 §A.6）：

* 该机制**真实存在**，而且是 **`www.baidu.com` 探针唯一的失败模式**（32 次失败**全部**如此；96 次无 v6 改写的 baidu 探针**零失败**）；
* 它**完整解释了 13:28:16 那一次作废**（前置两轮都是它）；
* 但「v6 改写 ⇒ 必失败」**被证伪**：有 v6 改写的 baidu 探针 **154 次里 122 次成功**（失败率 **21%**）；
* 它也**解释不了另外三次作废**（11:14:51 / 12:16:26 / 12:30:12）—— 那三次前置两轮失败的是 **cloudflare** 探针，与本假设无关（另一种机制）。

## A.0 口径与修订绑定

* 去重口径：`(ts_unix, message)`，两文件合读。**本轮日志是活跃的、边跑边追加** ⇒ 下面的「连接总数」是**某一时刻的点数**（两次采样 660 / 666，差 6，不是算错，是日志在长）。
* 修订：**`tag v0.8.33`（`4aee1d88`）**，探针集合**只有 2 个**：`http://cp.cloudflare.com/generate_204` + `http://www.baidu.com/`（`supervisor.rs:160-165`）。
  **第二次独立确认**：`strings -a /Applications/XrayTun.app/Contents/MacOS/xraytun-desktop | grep -c 'http://223.5.5.5/'` = **0**，
  而 `http://cp.cloudflare.com/generate_204http://www.baidu.com/` 相邻出现 ⇒ 装的那版确实是 2 目标版（3 目标是 task-92，发布之后）。
* 探针连接识别：`proxy/socks: TCP Connect request to tcp:{cp.cloudflare.com,www.baidu.com}:80`，连接 ID 取行首 `[NNNNNNNNN]`。
* 结局判定（按连接 ID 的完整轨迹）：成功 = 轨迹里出现 `proxy/freedom: connection opened` 或 `proxy/vless/outbound: tunneling request`；
  失败分两种 = 出现 `failed to process outbound traffic` / **完全没有后续行**。

**探针轮**（>5s 分轮）⇒ **365 轮**：**全成功 330 轮**、**含失败 35 轮**（baidu 失败 26 轮 / cloudflare 失败 9 轮）。

**32 条 baidu 失败的轨迹形状完全一致**（19 行）：

## A.3 ★ 对照组：成功的连接里**也有** v6 改写 —— 「v6 改写 ⇒ 必失败」不成立

| 成功 | 1 | **无** | 3 ← **唯一反常项，见 §A.5** |

**失败率**：有 v6 改写 **32/154 = 21%**；无 v6 改写 **0/96 = 0%**。

**⇒ 两条同时成立**：
1. **v6 改写是 baidu 探针失败的必要条件**（0 次纯 IPv4 失败）；
2. **但远不是充分条件**（79% 的 v6 改写照样成功）—— 成功那些在若干次 v6 尝试后**回退到了 A 记录**。
   典型成功轨迹（cid `1805052460`，11:06:37）：

```
dialing TCP to tcp:www.baidu.com:80
```

## A.4 ★ 与「重建/作废」的对应：每次作废**之前的两轮**探针

`FAILURES_BEFORE_REBUILD = 2`（tag `core.rs:605-606`、`1477`）⇒ 需要**连续两轮**至少一个目标判死。

| 已作废 | 前一轮 | 再前一轮 | 失败的是谁 | 与 v6 假设的关系 |
|---|---|---|---|---|
| 11:14:51 | 11:14:37 cp **无后续行** | 11:14:21 cp **无后续行** | cloudflare ×2 | ❌ 无关（末行＝拨节点） |

⇒ 假设在 **13:28:16** 这条事件上成立且可逐步复原：两轮前置探针恰好是「baidu 探针 5 次 v6 尝试后失败 + cloudflare 成功」

（13:29:49、13:30:31、13:34:40、13:37:04、13:38:48、13:44:24、13:45:16、13:45:48、13:46:29、13:47:12、13:49:07），
但它们彼此隔了 30s–3 分钟，**凑不齐「连续两轮（~10s 间隔）」** ⇒ `failures` 永远到不了 2 ⇒ 不再作废。

## A.5 诚实清单（本附录）

1. **3 条「成功但无 IPv4 回退」的 baidu 探针**（v6 改写 1 次，却有 `connection opened`）：**原因未定** ——
   可能那一刻 v6 真的通了，也可能这 3 条轨迹不完整（轮转/丢行）。**我不猜。**
2. **连接总数是时点值**：日志在被持续追加（我两次采样 660 / 666）。所有比例都是「当次快照」的，不当作全天终值。
3. **「轮」依赖阈值**：>5s 分轮 = 365 轮（task-95 里我用 >3s 得 336 轮）。两种口径**结论一致**，但引用时必须写明口径。
4. **本附录回答不了「为什么有时回退、有时不回退」** —— 那是核心侧拨号策略（task-97 的范围）；我只给「回退成功 119 次 / 未回退失败 32 次」这个事实。
5. **cloudflare 那 9 次失败**（无 v6、末行＝拨节点）**我没有继续定位**（超本卡范围），只标为「另一种机制」。
6. 本附录**没有**把「探针失败」写成「用户当时上不了国内网站」：探针只证明**这一个 URL 经 SOCKS 走 direct 失败了**；
   用户浏览器当时的体验需要端到端证据（本卡没有）。

## A.6 结论：**部分成立**

1. **成立的部分**：`http://www.baidu.com/` 探针经 `[preset-cn-domain] → detour [direct]` 后**确实**被改写成 IPv6（AAAA）；
   在**本机没有可用 IPv6** 的前提下，若 5 次 v6 尝试后**未回退**到 A 记录，整轮探针就判死
   —— 32 次失败**全部**是这个形状，**且没有一次**纯 IPv4 失败（96/96 成功）。这条链与 **13:28:16 作废**的前置两轮**逐条吻合**。
2. **被证伪的部分**：「v6 改写 ⇒ 必失败」。**154 次 v6 改写里 122 次成功**（失败率 21%）——
   因为核心**常常会回退到 IPv4**（119 条成功轨迹里有 v4 replace）。⇒ v6 改写是**风险因子/必要条件**，**不是充分条件**。
3. **范围上不成立的部分**：它**不是**今天四次作废的**共同**根因 —— 另外三次（11:14:51 / 12:16:26 / 12:30:12）是
   **cloudflare 探针**失败（9 次 cloudflare 失败**无一**带 v6 改写，末行＝拨节点）⇒ 需要**另一条**根因。
   ⇒ **task-97（配置层修 IPv6 改写）能治 13:28 那一类；要治另外三次，得同时看 cloudflare 探针 / 节点侧。**
