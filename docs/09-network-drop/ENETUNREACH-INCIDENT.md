# 国内直连 `ENETUNREACH` 现场审计（`task-172`）

> **来源**：第一份真实现场包 `INC-20260923-123641-af29`（App 0.8.36，窗口 20:27:52 → 20:36:29）的**只读副本**。
> **本页做了什么**：静态推演（读码 + 现场包只读证据 + 本机只读命令）。**没有**改路由 / 改 DNS、没有连接或断开 App、没有装卸助手。
> **标注**：`[实测]` = 现场包或本机只读命令的原始观测；`[读码]` = 带 `file:line` 的可复算推演；`[推断]` = 结论，附**判别方法**。
> **脱敏**：本页不写现场包原文、不写节点地址、不写用户访问的域名；网关/子网用 `<GW-窗口期>`、`<GW-现在>` 代指。

## 0. 一句话结论

**`[推断]` 这次「物理网络正常、境外节点拨号正常、但国内直连全部 `ENETUNREACH`」的形状，与一个具体缺项吻合：**
**这次会话里 en0 上的「作用域默认路由」（`default … UGScIg en0`）不在路由表里。**
`direct` 出站绑了物理网卡（`sockopt.interface`），绑卡后的系统调用（`IP_BOUND_IF`）要求**最具体的可用路由落在该接口上**；TUN 会话里最具体的那条是 `0/1 → utunN`，它不在 en0 上 ⇒ 绑卡查找**不回落**到普通默认路由，直接 `ENETUNREACH`。节点出站**不绑卡**（`sockopt: null`），走的是 `/32` host 路由 ⇒ 不受影响。

**直接证据**：现场包的网络快照（窗口结束后 6 秒采集，会话仍在线）里只有**一条** `default … UGScg en0`（系统默认路由），**没有**我们装的那条 `default … UGScIg en0`；而仓库自己的健康基线（`docs/09-network-drop/LOOPBACK-ROUTE-BASELINE.md:27-32`，2026-09-21）里**两条都在**。

**为什么它不见了**——`[无法从本包判定]`：现场包**没有 helper 侧日志**（下略 §4 的四个候选与判别方法）。

**排除的候选（有证据）**：
* 物理断网 ⇒ **排除**：同窗口节点拨号正常，且 `default`（系统）路由一直在（`[实测]`：现场快照）。
* DNS 挂掉 ⇒ **排除**：失败发生在 `connect` 阶段（`network is unreachable`），且部分是 IP 字面量目标（不需要 DNS）；同一窗口哨兵 DNS 仍在（现场 `scutil --dns`：`nameserver 198.18.0.2`，scoped 到 en0）。
* v6 相关 ⇒ **排除**：`v6_rewrite_lines = 0`。
* 捕获路由缺失 ⇒ **排除**：`0/1 → utun6` 在现场快照里**在**（而且没有它反而直连更容易成功）。

## 2. 取路模型（`[读码]`）

### 2.1 两条出站，两种取路

1. **`direct` 出站**：显式写 `streamSettings.sockopt.interface = <物理网卡>`（`crates/xt-core/src/xray/config.rs:512-521`；
   接口名来自 `supervisor.rs:507/512` 的 `default_route().interface`，经 `:516/:525` 传给配置）。
   ⇒ 出站 socket 用 `IP_BOUND_IF` 绑定 en0 ⇒ **内核做「作用域查找」**。
2. **节点出站**：**没有** `sockopt.interface`（`sockopt: null`，见 `config.rs:473-476` 的注释）
   ⇒ 走**普通（不限定接口）**查找 ⇒ 命中 `/32` 旁路 host 路由（现场快照里两条 `… UGHS en0`）。
   ⇒ 这解释了「境外节点正常、国内直连全灭」。

### 2.2 绑卡查找为什么必须有一条「en0 自己的」默认路由

* TUN 会话安装 `0/1` + `128/1` 捕获路由，指向 utun（`plan.rs:227-244`，`RouteKind::DefaultCapture`、`critical: true`）。
* 对任意目标（例如国内直连目标），**最具体的匹配**是 `0/1 → utunN` —— 但它在 utun 上，**不在被绑定的 en0 上**。
* 本项目自己记过这条内核行为并为之写下补丁注释（`supervisor.rs:886-901`）：
  > 「`IP_BOUND_IF` 会把路由查找**限定在该接口上**。而我们的 `0.0.0.0/1` 接管路由挂在 utun 上 …… scoped 查找直接失败，返回 `ENETUNREACH`。」
* 所以「任意目标 + 绑 en0」这条路，**依赖 en0 上存在一条可用的作用域默认路由**：
  `default <GW> -ifscope en0`，由 `plan.rs` 的「2c 物理网卡的作用域默认路由」安装（`plan.rs:207-224`，装着 `RouteVia::ScopedInterface`，
  展开成 `route -n add -net 0.0.0.0/0 <GW> -ifscope en0`，见 `route.rs:191-203`；`route.rs:196-197` 明确「网关必须给」）。

### 2.3 这条路由的**安装是「非关键」的** —— 装不上会被跳过（`task-172` 的关键线索）

* `PlannedRoute::scoped_default(..)` 的 `critical: false`（`plan.rs:81-93`，注释：「装不上不会让整次建立失败，但**直连分流会失效**」）。
* 安装点：`controller.rs:118-128`（阶段 1b）→ `install_route_or_skip`：**非关键路由装失败只 `warn!` 然后继续**
  （`controller.rs:187-194`）。
* ⇒ **存在一条静默路径：会话建立成功、界面显示已连接、但直连那条路从第一秒起就是死的。**
* 另外 `plan.rs:214-224` 还有一条**提前跳过**：`physical.gateway` 不是 IPv4（例如探测那一刻没有默认网关）时，
  直接 `warn!`「物理出口没有 IPv4 网关，跳过作用域默认路由（直连分流可能不可用）」并**不安装**。

## 4. 主假设与四个候选机制（逐条给判别方法）

**主假设 H0**：窗口期 en0 上没有可用的作用域默认路由（无论「从未装上」还是「装上后消失」）⇒ 绑卡直连全灭。
判别（任一成立即 H0 成立）：`netstat -rn -f inet | grep '^default'` **只有一条**（无 `UGScIg`）；或
`route -n get -ifscope en0 <国内目标>` 落到 utun/不返回 en0。

| # | 候选机制 | 支持证据 | 反证/判别 |
|---|---|---|---|
| **H1** | **安装时失败被静默跳过**：`route add -net 0.0.0.0/0 <GW> -ifscope en0` 因「同前缀已存在（EEXIST）」/其它错误失败 ⇒ 非关键 ⇒ `warn!` 后继续 | `critical: false` + 静默跳过路径（`plan.rs:91`、`controller.rs:187-194`）；机器上同时有 6–7 个别的 utun/工具，路由表**不是干净的** | 需要 **helper 日志**（本包没有）里那句「非关键 bypass 路由安装失败」；或故障当下 `netstat` 看有没有**别人的** `UGScIg`（若存在过又被对方删掉，就形成「装不上→后来也没有」） |
| **H2** | **网络事件把它删了**：Wi-Fi 漫游 / DHCP 续约 / 接口状态变化时 macOS 清掉 ifscope 路由，而**没有任何人重装**（App 无网络变化监听） | 本机**确实在换网**：窗口期网关是 `<GW-窗口期>`，今天只读查到的系统默认网关已变成 `<GW-现在>`（不同子网）；现场快照里两条 `/32` host 路由**仍指向旧网关** ⇒ 旧路由确实会残留 | 时间线关联：窗口前后是否有漫游/DHCP 事件（`log show --predicate 'subsystem == "com.apple.network"'`、`scutil --nwi`）；故障当下系统默认路由的网关是否变过 |
| **H3** | **旧会话迟到/重复的回滚删了它**（`task-118` F-4 家族）：回滚按「目的前缀 + via」删除，键相同就会删掉**当前会话**那条 | 现场快照里**两条** `/32` 节点 host 路由（含旧节点残留）⇒ 残留与迟到清理在本机是**已发生的事实** | 查 helper 的会话快照目录（`/Library/Application Support/XrayTun/*.json`）+ 是否有 `TunDown`/`restore` 与安装时刻重叠；判别点：故障前后路由表的**键级 diff** |
| **H4** | **接口身份变化**：en0 的 ifindex 变了（Wi-Fi 重连/USB 网卡切换），挂在旧接口上的 ifscope 路由被清掉，而 Xray 的绑卡是按**启动那刻**解析的名字/索引 | 本机在换网（见 H2 证据） | 故障当下 `ifconfig en0` 的 index 与 App 启动时的是否一致；`scutil --nwi` 的接口列表；重连事件时间线 |

**不作为主因**：探针集合只有 1 个国内目标 ⇒ 1/3 失败不到门槛 ⇒ **不重建**（这是「没自愈」的原因，不是故障原因）—— 见 §7。

## 5. 下次故障当下的判定清单（**只读**，照抄即可；任何一条都不要改路由）

> 前提：故障正在发生（国内直连报 `network is unreachable`），App 仍处于连接态。
> **判据的关键**：`route get -ifscope` **不等于**绑卡 socket 的查找（今天只读验证过：在没有捕获路由时两者返回同一个普通默认路由）
> ⇒ 真正的判据必须用**绑卡拨号**那一条（第 2 项）。

```bash
# 1) en0 有没有「我们那条」作用域默认路由（期望两条 default：UGScg + UGScIg）
netstat -rn -f inet | grep -E '^default'
# 2) ★ 真正的判据：绑到 en0 能不能出去（direct 出站走的就是这条路）
curl -sS --interface en0 --max-time 3 -o /dev/null -w 'bound-en0 http=%{http_code} exit=%{exitcode}\n' \
     http://223.5.5.5/ ; echo "curl_exit=$?"
#    对照：不绑卡应当成功
curl -sS --max-time 3 -o /dev/null -w 'unbound  http=%{http_code}\n' http://223.5.5.5/
# 3) 捕获路由 + 节点 /32 旁路（看主机路由指向的网关是不是**当前**网关）
netstat -rn -f inet | grep -E '^(0/1|128)' ; netstat -rn -f inet | awk '$3 ~ /H/ || $4 ~ /H/'
# 4) 当前接口/网关/NWI（换网与 ifindex 变化）
route -n get default ; ifconfig en0 | head -3 ; scutil --nwi | head -20
# 5) 与现场包同一口径的快照（可直接对比本文 §3 的两张表）
bash scripts/incident-bundle.sh   # 或只手工跑上面几条
```

**判读规则**：
* `default` 只有一条（无 `UGScIg`）且第 2 项失败、第 2 项对照成功 ⇒ **H0 成立**（就是这条路由缺失），修法见 §6-①②。
* `UGScIg` 在、但网关不是第 4 项的当前网关 ⇒ **H2/H3**（stale 网关）⇒ 修法见 §6-③④。
* `UGScIg` 在且网关正确、可第 2 项仍失败 ⇒ **本页模型被推翻**，需要重新采集（`tcpdump`/`sysctl`/Xray 的 `sockopt` 日志）——**不许**直接把本页结论当答案。
* 现场快照里出现两条 `default`（一条带 `I`）**且**国内直连正常 ⇒ 健康基线，与本页 §3 第一张表对照。

## 6. 修法建议（**本卡不改代码**，逐条给代价）

| # | 建议 | 代价 / 风险 |
|---|---|---|
| ① | **把「直连那条路」变成可自愈的不变量**：在已有看门狗 tick 上做一次**只读**校验 —— `netstat` 里有没有一条「en0 的 ifscope 默认路由且网关=当前网关」；没有就触发一次**路由修复**（重装该条，或整体重建会话） | 需要一个 helper 操作或走现有重建路径；频率要低（例如 30–60 s）；好处是**同时覆盖 H1–H4**，且判据就是本节第 1 项那条命令 |
| ② | **不让它的安装失败静默**：当「系统存在默认路由」而「我们的 scoped add 失败」时，把它升为**关键失败**（或至少在 App 状态里显示「直连分流不可用」） | 现在刻意非关键（点对点链路没有网关也要能用 TUN）⇒ 判据要写成「系统有默认路由却装不上才失败」；否则会把可用环境变不可用 |

| ④ | **清掉上一条会话的残留**（`task-118` F-4）：新会话建立时清理「我们自己的、已不在本次快照里的 host 路由」；回滚严格按**会话 id** 校验 | 删错别人工具的路由是硬风险 ⇒ 只删「有我们快照记录 + 目标是我们装过的」那类；建议单独开卡，别和本卡混 |
| ⑤ | **修探针盲区**（`task-106`）：国内目标只有 1 个 ⇒ 「国内全灭」只有 1/3，永远不到重建门槛 | 见 §7；这条是**本次没自愈的直接原因**，且改动最小 |

## 7. 与 `task-106` 的关系（本窗口是它的真实实例）

App 侧原文「境内 全灭 1/1、境外 0/2 死 ⇒ 未到 2 个的门槛，**只记账、不重建**」正是 `task-106` 要修的形状：
**探针集合里国内目标只有 1 个 ⇒ 「国内整侧不通」最多只贡献 1 个失败 ⇒ 永远触发不了重建。**
如果当时触发了重建：`bring_up` 会重新走 §2.2 的 2c 安装（并可能清理中间态），**直连那条路很可能当场恢复** —— 也就是说 ①/⑤ 两条修法是互补的：
**① 治本（不变量 + 自愈）**，**⑤ 治「没发现」（探针覆盖）**。两卡应交叉引用各自的判据与验收。
