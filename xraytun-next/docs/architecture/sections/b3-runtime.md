# B3 · 运行时与组合根（daemon / datapath / stats / probe）

## 为什么 daemon 是独立进程

UI 崩溃或热重载不牵连隧道；业务逻辑能脱离 WebView 在 CI 里跑真实验证（本轮 E2E 就是
在无 UI 的情况下用真 xray 跑通的）；CLI 与 UI 走同一份契约，所以「UI 能做的无头也能做」；
崩溃被限制在一个进程里，错误归属清楚。代价是多一次 AF_UNIX 往返和一条 socket 生命周期 ——
只有当收益大于代价才引入进程边界，本轮只有这一处，不引入跨 TCP 的微服务。

## 为什么就绪判定不用 sleep

「端口可连」是唯一与版本无关的就绪信号（日志格式随版本变），但**何时去试**决定了
最坏等待与失败原因的准确性。定时轮询有两个坏处：平均多等半个周期；进程已经死了还要等到
下一个周期甚至 deadline 才发现，并把「它自己退出了」报成「没等到」。这里的做法是：
核心每输出一行 stdout/stderr 就对上**尚未就绪**的地址各试一次连接，全部可连才算就绪；
两条输出流都 EOF 就是「它不会再说话了」的确定性事件，此刻立刻报 `CoreExitedEarly` 并带
真实退出码与最后几行输出。`deadline` 只是失败上限，不参与节奏。

必需地址包含 SOCKS **与 StatsService 的 api 入站**：xray 的各个入站不是同一个就绪事件。
只等 SOCKS 就宣布「已连接」，随后一次性建立的统计连接会撞上 `Connection refused`，
整段会话只能显示「未采样」—— 那是「明明能知道却一直说不知道」，同样违反 I3。

## 为什么采样由消费者驱动

`StatsService` 只在 `Status` 请求时被查一次，100ms 内的重复请求复用上一次样本（缓存闸门，
不是定时器）。周期性采样会自己制造两个谎言：没人看界面时也在产生网络流量（每次查询都真实
经过 api 入站），空闲机器也能读出几十字节；定时器一旦和核心重启撞上，就会把一个刚归零的
读数展示成「流量掉了」。采样失败就是 `stats: None`（界面显示「未采样」）；真实的 0 是样本，
不采样不是。连接被停掉时同时清掉样本与 api 地址：下一个会话的 api 端口是那个会话的事实。

## 为什么切节点走重启而不是热更新

配置变更 = 停旧核心、起新核心，走与首次连接**完全相同**的一条路径。热更新需要维护与内核
版本耦合的 proto/gRPC 调用面，而桌面客户端的换节点频率是分钟级、xray 冷启动是百毫秒级，
用户感知不到差别。更重要的是语义：热更新天然引入「旧的还活着、新的已生效」的重叠态，
失败时很容易变成「退回旧节点」—— 那正是 I2 要消除的回落。所以 `SwitchNode` 与 `Connect`
共用同一条「选择就用」路径：切过去失败就停在失败，带真实 `last_error`。
