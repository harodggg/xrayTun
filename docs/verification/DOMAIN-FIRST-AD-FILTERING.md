# 先判域名 → 再判内容（MITM 验证）：两层流程与各自边界

> 用户原话：**「jev 判定不了吗，先判定域名，再判定内容去验证」**。
> 这句话把主次定对了：**域名（确定性规则）先判，内容（MITM）用来验证** ——
> 不让模型当主语（模型判域名的增量实测是 **0**，见 `INTENT-ANSWER-DIAGNOSIS.md`）。
>
> 本文只描述两层流程、命令与**边界**。工具是新文件 `scripts/ad-candidates.py`；
> 内容层证据来自仓库外的一次性探针（命令见 §3）。
> **隐私**：`ad-candidates.py` 的输出含域名，只能写仓库外（默认 `/tmp`）；
> 本文只有聚合数字与脱敏描述（具体候选在 `/tmp/ad-candidates.md` 里）。

---

## 0. 两层各回答什么

| 层 | 判据 | 确定性 | 回答的问题 | 不回答 |
|---|---|---|---|---|
| **① 域名层** | 域名的**标签边界**是否命中已知投放/追踪标签 | 完全确定、离线、可复算 | "哪些域名**名字上**就是投放基础设施" | 名字里没有 ad 的投放端；内容里的广告位 |
| **② 内容层** | 一次真实响应里有没有**机器可读的广告标记** | 依赖网络与响应形状 | "这个端点的响应里**有没有** `is_ad`/`ad_type`/`promoted`/`sponsored`" | "这条内容是不是广告"（标记不是规范、缺失≠干净） |

两层的关系是**漏斗 + 验证**，不是串行定罪：域名层给出候选（含大量漏检），
内容层只对**拿不准的少数候选**做一次验证，用来**精修规则**。

---

## 1. 域名层：`scripts/ad-candidates.py`

### 1.1 匹配规则（**标签边界**，不是子串）

一个主机名按 `.` 拆成标签，标签再按 `-` / `_` 拆成段。只有两种命中：

1. **段完全等于**已知广告/追踪标签（`ad` / `ads` / `analytics` / `tracker` /
   `beacon` / `pixel` / `sponsor` / `badjs` / `ogads` / `doubleclick` …）；
2. **整个标签以**已知广告**前缀**开头，且后面是空/数字/分隔符
   （`adserver1`、`tracker-cdn`）。**`ad` 不放前缀表** —— 那会把 `adobe`/`admin`/
   `address` 全捞进来，精度直接崩掉。

刻意不做宽松子串匹配。`--include-weak` 会额外列出宽匹配层（子串命中），
用来对照"宽匹配为什么不能用"：`polkadot.js.org` 里的 `ad`、`adobe` 这类都会进来。

### 1.2 复跑（本机实测）

```bash
LOGS="$HOME/Library/Application Support/com.xraytun.desktop/logs"
python3 scripts/ad-candidates.py --corpus "$LOGS" --out /tmp/ad-candidates.md
# 只看出现 >=5 次的；并把误伤层列出来对照
python3 scripts/ad-candidates.py --corpus "$LOGS" --min-count 5 --include-weak
```

本机结果（聚合）：扫 5 个日志文件 / **713,888 行**（sniffed 行 30,884、
accepted 连接行 82,969）→ **观测域名 447 个 → 候选 11 条（2.5%）**。
输出表里每条都带**命中理由**（哪个标签、哪个段、或前缀），并按三种计数口径
同时打印：`sniffed`（`sniffed domain:` 行数）/ `paired`（产品 `ConnectionLog`
的时序配对：上一条 sniffed 被 200ms 内下一条 accepted 消费）/ `mentions`
（任意位置出现）。

**与 Lead 那份"4 条"的关系**：那 4 条都在本工具的 11 条里；多出来的 7 条是同一
家族的投放基础设施（`googleadservices`、`doubleclick` 的若干子域、
`analytics.google.com` 等）—— 本工具的词典更宽。**计数不可直接比**：Lead 报的
每域名次数（几百量级）与本工具三种口径都对不上，说明那份用的是另一种归属算法
（很可能把"最近一条 sniffed 之后的连接"都算给该域名、且不消费）。工具把三种口径
都打出来，就是为了避免"数字对不上却看不出是口径问题"。

### 1.3 纪律：**不自动下发**

* 工具只出候选表；**不改任何配置、不生成规则、不联网**（文件里没有网络 import）；
* `--out` 指到仓库里会**直接拒绝**（退出码 3）——输出是浏览记录；
* 用户勾选后，自己把域名抄进「自定义规则」或静态名单。

### 1.4 域名层**漏什么**（和命中等价重要）

1. **名字里没有广告字的投放端全漏**：自建投放服务、第一方广告 API
   （`youtubei.<…>`）、CNAME 伪装成 `metrics.<大站>` 的追踪域；
2. **内容里的广告位**（接口 JSON 的 `promoted` / `is_ad`）看不见；
3. **日志里没出现过的域名**漏（没有观测就没有候选）；
4. **会误报**：公司自建的 `ads.<自己域名>`、内部投放后台名字像广告但不是用户
   想拦的 —— 所以候选必须**人工确认**。

## 2. 内容层：用**现有 MITM** 抓一次真实响应（验证，不定罪）

### 2.1 用途（写死，避免被滥用）

* 只用于**域名层拿不准**的候选 —— 也就是"名字不像广告，但怀疑是投放位"；
* 一次抓取的结论只有两种：**"响应里出现了某个机器可读标记"** 或
  **"没出现"**。前者是**线索**，后者**不是清白证明**；
* **不许**把"看到 `promoted` 字段"变成全局拦截规则。它最多是"把这个域名
  放进候选表 / 调整 opt-in 名单"的依据，且要人工复核。

### 2.2 怎么复跑（仓库外的一次性探针，不动产品）

现有 `xt-mitm` 的代理是**TLS 终结 + 经 SOCKS 回连**（生产里回连的 TLS 由 Xray 的
`mitm-upstream` 出站负责）。所以复跑需要三样仓库外的东西：

1. 一个把 `xt-mitm` 当库用的探针（`serve(cfg, ca, PassAll)`，`upstream_socks`
   指向本地 SOCKS 端口），把 CA PEM 写到 `/tmp`；
2. 一个最小 SOCKS5 + **TLS 出站**的中继（代替 Xray 的 outbound）；
3. 客户端以 **TLS 直连**代理（不是 HTTP CONNECT）：`curl --cacert <ca.pem>
   --connect-to <host>:443:127.0.0.1:<mitm_port> https://<host>/<path>`。

### 2.3 实测证据（真实响应）

| 抓取 | 结果 | 读法 |
|---|---|---|
| 机制对照：`api.github.com`（无广告名、有 Content-Length 的 JSON） | **HTTP/1.1 200，12,233 字节**，本地 CA 证书链验证通过，ALPN 协商到 `http/1.1` | **内容层通路成立**：TLS 终结 → SOCKS 回连 → h1 读响应全链在工作。响应里没有任何广告标记（负对照） |
| 域名层候选 A（名字命中广告标签，根路径 GET） | **HTTP/1.1 404，`Content-Length: 0`，无标记** | "名字像广告"与"内容有投放标记"是**两种证据**；一次根路径 GET 既不能定罪也不能洗清 |
| 域名层候选 B / C（分析类、社交广告 API） | **空应答**（客户端 `curl(52)`） | 多半是 **chunked** 或需要 POST —— 见下节边界 |

### 2.4 内容层**验证不了什么**（这次实测撞到的边界）

1. **只吃 GET、且不带 body**：`xt-mitm` 明确拒绝带 `Content-Length` 的请求
   （`本版不处理带 body 的请求`）。而 `promoted` / `is_ad` 这类字段最常出现在
   **POST 的 timeline/GraphQL 响应**里 —— 那类响应**这套通道根本到不了**；
2. **只吃 `Content-Length` 应答**：`chunked` 会被明确拒绝（返回错误并关连接），
   客户端看到的是"空应答"。现代端点大量用 chunked；
3. **拿不到就什么都验证不了**：本机对多个广告域直接不可达（`http=000`）、
   部分候选返回空应答 —— 这些都不构成"它不是投放端"；
4. **标记不是规范**：`is_ad`/`ad_type`/`promoted`/`sponsored` 只是**猜想词表**；
   各家命名不同（`isPromoted`、`adSlots`、`data-text-ad`、`adPlacements`…），
   没有标记 ≠ 没有广告；
5. **看不到服务端决策**：个性化广告位、按 geo/账号投放、客户端注入的广告
   （同一 URL 对不同人返回不同内容）不在响应文本里，或根本不在这次请求里；
6. **不能对着没点名的域名拆 TLS**：内容层只在用户**已经点名**（opt-in）的域名上
   工作 —— 否则就是"为了验证去 MITM 用户没同意的东西"。

## 3. 两层怎么配合（闭环）

```text
日志/观测
   │  ① 离线、确定性：标签边界筛候选（ad-candidates.py）→ 人工确认
   ▼
候选域名（用户勾选）
   │  写进：自定义规则（block）/ opt-in 名单
   ▼
   │  ② 对**拿不准的少数**：MITM 抓一次响应，找机器可读标记
   ▼
标记出现？ ── 是 → 作为"这个端点确实是投放位"的**线索** → 人工精修规则
           └─ 否/抓不到 → **什么也没证明** → 回到人工判断（别自动定罪）
```

* **确定性优先**：域名层不需要网络、不受模型影响、结果可复算；
* **内容层只做验证**：它的输出是证据，不是规则；
* 模型（Jev）不在这条链路的主语位置上 —— 它判域名的增量实测为 0。

## 4. 本次**没有**做（明确的边界）

* 没有把模型重新扶成"判域名"的主语；
* 没有为内容层去拆用户没点名的域名；
* 没有生成/下发任何规则（工具只出候选表，`--out` 只允许仓库外）；
* 没有改动任何产品默认值。

## 5. 我没能验证的

* **没有拿到一条带广告标记的真实响应**：能到的端点没有标记，有标记的端点
  （Google 广告域）本机不可达；候选 B/C 因 chunked/POST 拿不到。所以
  §2.3 里"标记出现 ⇒ 是投放位"这半边的**正例**仍是待补的（需要一台能访问
  目标端点、且目标返回 `Content-Length` GET 的环境）；
* 域名层的 11 条**没有人工逐条确认**（工具明确要求人工勾选）——"候选"不是"已确认"；
* 本文所有域名级数字来自**一份正在写入的日志**（713,888 行），换时间/换机器会变。
