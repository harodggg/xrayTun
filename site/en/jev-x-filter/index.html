Porn-tweet Filter · Jev: filtering adult promotion on X with Jev's typed decisions

This is a Chrome MV3 extension. It screens locally, then asks Jev (TypeSafe System One) a few typed questions (yes/no, single choice, scale) and acts on the returned probability and confidence: a hit is hidden, and only high-confidence adult content or adult solicitation can touch the account (mute / block) — and by default it only dry-runs. It is not a keyword blocklist: the real decision is made by the model, keywords only decide whether a call is worth paying for.

How it decides: four tiers, increasingly expensive

A decision is not a single model call. Cheap layers run first, expensive ones only when needed, and no single layer is sufficient to touch your account.

Tier What it does Cost
Local pre-screen Readable regex over the text, the display name, card text and image alt; whitelisted accounts, your own posts and too-short posts without media are skipped 0 requests
Triage (model first) Posts the keywords missed are still asked one cheap question (“is this bot-driven adult bait or suggestive self-promotion?”). At ≥0.75 it escalates to the full four questions; at ≥0.65 it is only hidden as “needs review” one single-question call (≈ 1/4 of the full set)
Repeated-text farm The same content-free line copied by ≥3 different accounts within 30 minutes → all of them hidden (including earlier ones that were let through). Normalisation strips emoji, punctuation and case 0 requests
Jev typed questions Adult? Off-platform solicitation? Category (one of five, with confidence)? Severity (four-level scale)? Questions are written in English; the post itself is never translated one call
Image signal Jev is a text-only model and cannot see images: images go through a local skin-tone pixel heuristic (OffscreenCanvas inside the service worker, no network) and only ever corroborate thumbnail download only

Three invariants (documented in code and covered by unit tests): ① account actions require Jev’s strong category plus both confidence gates; triage, the farm detector, the skin-tone heuristic and the optional vision model on their own can reach “hidden” or “needs review” but never block; ② uncertainty is downgraded, never patched; ③ every band states its reasons, visible in the filter bar and the audit log.

What happens on a hit is entirely your choice. The default is dry-run: it only records “who would have been muted” in the audit log and clicks nothing. To make it act you must explicitly enable “auto mute” (and optionally “mute hidden-band accounts too”) in the popup. Blocking always requires the high-confidence four-question verdict.

Install and configure

There is no build step: the unzipped folder is a loadable extension directory.

# 1) download and unzip
unzip jev-x-filter-0.2.0.zip -d jev-x-filter

# 2) open chrome://extensions → enable Developer mode
#    → "Load unpacked" → select the unzipped jev-x-filter directory

# 3) click the extension icon → Options → section 1 "Jev access"
#    · to use your own key: keep the TypeSafe Official preset and paste the key
#    · to try it for free: switch to OpenCode Zen (jev-1.13-free, no key needed)
#    · press "Test connection" and make sure typed answers come back

# 4) open x.com. Watch the filter bars and the audit log, and only turn off dry-run
#    once you have seen it behave on your own timeline

Judging happens inside the extension’s service worker; the API key is stored only in chrome.storage.local and is never exposed to the page. The options page can export and import the account blocklist (JSON), and one click on a filter bar adds a false positive to the whitelist.

Verification status

Every claim here is reproducible in the repository, and every real-world miss becomes a regression fixture — the project’s rule is that a lesson turns into a mechanism.

Check Command Result
Unit tests npm test 131 passing (wire contract, gate invariants, pre-screen, farm, image pixels, blocklist, audit, pipeline)
Real-Chrome end-to-end npm run verify 71 passing: load the extension over CDP → fake-X fixture page → decide → hide → click the menu (including two traps: Unmute/Unblock entries inside the menu and a pre-existing confirmation button reusing the same test id)
Static self-check npm run check 21 passing: manifest references, minimum permissions, no remote code / eval, content scripts must be classic scripts
Real-model check JEV_API_KEY=… node tools/live-check.js 22 real-world samples, 22/22 as designed (0 safety violations): adult spam is caught while everyday posts, moderation news, sex education and swimwear posts all pass

Real-world feedback drove three rounds of fixes, each of which left a regression fixture behind: the display-name vector (🍑真实同城约p🍑主页联系🔞免费 with harmless post text), the keyword-free suggestive brag (比我好看的没我骚🔧👏 from a gibberish account name), and the reply-section text farm (one line posted by four accounts within a minute), and emoji inserted inside keywords (display name ❤️处男免费❤️, post text 处🐕男). Two of them were architectural misses: as soon as keyword matching decides whether the model is asked at all, phrasings outside the table are unreachable for the model — which is exactly why the model-first triage tier exists.

Known limits (read before you arm it)

  • It will hide things it shouldn’t. The decision is probabilistic: sex education, art, fitness, edgy jokes and local slang can be caught or missed. Every hit can be restored with one click or added to the whitelist; treat the default dry-run as an observation period.
  • Auto mute/block are real account actions (performed by clicking the UI menus, not by calling private APIs) and carry platform rate-limit risk. The extension rate-limits, de-duplicates and dry-runs by default, but it cannot promise immunity.
  • Jev cannot see images. Image-only adult spam relies on the local skin-tone heuristic plus the “image-only post” shape and is hidden as “needs review”; it will not mute an account because of a picture. A vision endpoint can be configured separately for stronger image judgement.
  • It depends on X’s DOM. A redesign can break the menu automation; failures are logged as action_failed in the audit log instead of silently mis-clicking. All selectors live in one file so they can be updated quickly.
  • You pay for your own model quota. Candidates and triage each cost one call; rate limits and daily budgets are built in, and going over the budget degrades to “needs review” rather than hiding everything.
  • It is for your own timeline hygiene only. There is no bulk reporting and no ability to target other people’s accounts.

FAQ

Will it hide normal content?

Yes, sometimes. Any filter is probabilistic, so the design keeps the cost of a mistake low: a hidden post can be restored with one click, marking it a false positive whitelists the account, and account actions are recorded without being executed by default.

Can auto-mute or auto-block get my X account suspended?

Automatic actions are real account operations performed by clicking the UI menus — the same effect as doing it by hand — so platform rate-limit risk exists. The extension defaults to dry-run, spaces out actions and acts on each account only once; watch the audit log for a few days before turning dry-run off.

Does it cost anything to use?

The default preset is the TypeSafe official gateway, which needs your own Jev API key; you can also switch to OpenCode Zen’s free tier (model jev-1.13-free, no key required) to try it at zero cost. Rate limits and daily budgets are built in, and exceeding them degrades decisions to “needs review” instead of calling the model anyway.

Which browsers are supported?

Chrome 120 and later in its Manifest V3 environment; Edge, Brave and other Chromium-based browsers can load it too. Firefox and Safari are not supported because their content script and extension APIs differ from MV3.

Why is image judgement weaker than text?

Because Jev is a text-only decision model: its input can only be text, and it cannot see pictures. Images therefore go through a local skin-tone pixel heuristic that is only used to hide image-only posts as “needs review”, and it never triggers an account action on its own. For stronger image judgement you can configure a vision model endpoint in the options page.

Where does my data go?

Only post text and a little metadata (author, position, alt text, card text, local skin-tone ratio) are sent to the Jev gateway you configure. The API key stays in chrome.storage.local and is used only by the background service worker; images stay local by default; the optional audit webhook is off by default and posts one event per decision when enabled.
