# xraytun-next v1.1.2 · 修复：冷启动竞态 + 界面没有任何恢复路径

v1.1.1 修掉了真机上那条 `invalid_request: hello 只能发一次`。这一版处理**同一个真机
运行里暴露出来的另外两件事** —— 它们会独立产出**一模一样的症状**（daemon 版本/pid 全
「未知」、设置页「设置未加载，无法编辑」），所以只修 v1.1.1 那条是不够的。

## 一、冷启动竞态：界面可能永远停在「连不上」

**症状**：第一次启动（或 daemon 还没起来的那一次），界面直接是错误态，而且**永远不会
自己好**。

**根因**：壳的启动顺序是「先建主窗口 → 再 spawn daemon」。主窗口里的页面脚本会在几毫秒
内跑完并发出引导链的**第一次** `hello`，而那时 daemon 可能还没 `bind()` 完成 ——
这一次必然以 `io` 失败。而 UI 的引导链**只跑一次、失败不重发**（那是刻意的：本项目禁
自动重试），于是界面就永久停在错误态。首次启动时 macOS 还要对新下载的可执行文件做一次
Gatekeeper 校验，那个窗口会被拉得更长。

**修法**：`xt-daemon` 在 `bind()` 成功后往 stdout 写一行就绪信号；壳读那一行，
**确认 daemon 已经在监听之后才建主窗口**。这是**事件驱动**的等待（`read_line` 挂在那
里等对端写），不是轮询 —— 不变量 I1 禁 sleep/轮询，这一点没有被绕过。等不到（默认
20 秒）也照样建窗口，界面会如实报出连不上的原因，壳不伪造连接。

## 二、界面没有任何恢复路径

**症状**：任何传输层失败之后，界面就是死的 —— 没有重发、没有重新挂载、也没有任何用户
可点的动作。

设计文档里预期的恢复方式是「**等用户显式动作**（重新挂载新 client）」，但界面从来没有
实现它（`components/ErrorBox.tsx` 原本只显示 code 与 message）。

**修法**：传输错误框上多一个「**重新连接**」按钮，点它就用同一条引导链重新握手。仍然
**没有任何自动重试**，唯一触发路径是用户点击。

如实说明它治不了的那一类：如果客户端已经进入致命态（`tauri.ts` 的 `fail()` 把实例钉死在
`closed`），这一按救不回来，错误会原样再显示一次。页面上真正会制造这种致命态的那条路径
（下面第三条）已在壳侧修掉。

## 三、WebView 重载后事件序号必然对不上（桥侧）

桥推给界面的事件带一个从 1 开始的序号，界面按序号做连续性检查。但那个计数器是**进程级**
的，而界面的期望序号是**每个 WebView 会话**从 1 开始的 —— 一旦页面重载，界面收到的第一帧
就会被判「seq 跳号」并进入**不可恢复**的致命态。

**修法**：桥的序号闸门按会话边界工作 —— **页面开始加载**（`on_page_load`）时关闸并归零，
**界面发来第一条 `hello`** 时开闸并把期间滞留的事件按序补发。滞留上限溢出时会如实补一条
`Notice`，不让丢帧变成静默。
