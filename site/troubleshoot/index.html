确认是崩溃 找 panic.log 发给我们 先别改网络
中文 English

双击打不开怎么办

这一页给的是「App 根本起不来」时的步骤 —— 也就是界面帮不上忙的那种情况。 先按顺序做三件事：确认它是不是崩溃 → 找到 panic.log → 发给我们。最后一条同样重要：不要为了排障去改系统 DNS 或路由。

如果你看到的是一句「Apple 无法检查它是否包含恶意软件」的弹窗，那不是崩溃，是 Gatekeeper 拦截 —— 放行方式在首页的安装小节（按 macOS 版本三选一）。

1. 先确认：是崩溃，还是被 Gatekeeper 拦下

  • 被 Gatekeeper 拦下：会有一个弹窗，告诉你无法验证开发者。这种情况 App 其实没运行过 —— 按首页安装小节放行即可。
  • 崩溃：没有任何弹窗，或者图标在程序坞里跳一下就消失；进程撑不过一两秒。 这时系统会留下一份崩溃报告。

macOS 的用户级崩溃报告在这里（`*` 是时间戳）：

~/Library/Logs/DiagnosticReports/xraytun-desktop-*.ips

在「访达 → 前往 → 前往文件夹」里粘贴上面这段路径（`~` 会展开成你的用户目录）， 或者在「启动台 → 其它 → 控制台」里左侧选「崩溃报告」。 报告里能看到这几字样，它们就是崩溃的判据：

  • "abort() called"（出现在崩溃报告的 asi 字段里）
  • Abort trap: 6 / SIGABRT

如果崩溃报告里没有符号与位置，只有 __pthread_kill → pthread_kill → abort，那是正常的：发布版被 strip 过。 位置信息在下面那份 panic.log 里。

2. 找到 panic.log（最重要的一份）

XrayTun 自己在崩溃时会把「文件:行号 + 原因 + 调用栈」写成一个文件。默认路径是：

~/Library/Application Support/com.xraytun.desktop/logs/panic.log

最快的打开方式是把这行粘进「终端」：

open -R ~/Library/Application\ Support/com.xraytun.desktop/logs/panic.log

文件的第一行就带着位置，形如：

[unix=…] PANIC apps/desktop/src/lib.rs:178:17
<崩溃原因>
backtrace:
…

默认路径可能被 XRAYTUN_DATA_DIR 覆盖。 如果你（或某个脚本）给 App 设过这个环境变量，数据目录就整体换了地方，日志会落在 $XRAYTUN_DATA_DIR/logs/ 下，默认路径里什么都没有。

所以「默认路径没有」并不等于「没写日志」。先看变量，再让系统帮你找：

echo "$XRAYTUN_DATA_DIR"
find ~ -name panic.log 2>/dev/null

如果这两条都找不到：说明那次崩溃发生在日志钩子装上之前（例如更早的版本）， 这时只能拿上面那份系统崩溃报告 —— 它没有符号，但仍然能证明「它崩了、崩在 abort」。 把两份里你有的那份发给我们即可。

3. 把它发给我们

开一个 issue 就行： github.com/harodggg/xrayTun/issues/new

贴这几样，足够定位绝大多数「起不来」：

  • panic.log 的开头几行（第一行 PANIC 文件:行号 加调用栈；整份太大就只贴前 30 行）
  • 崩溃报告（*.ips）里含 abort() called 的那一段
  • 你的 macOS 版本与芯片（Intel / Apple 芯片）
  • 你是怎么启动的：双击 App、还是命令行；如果是命令行，把命令也贴上

贴之前先扫一眼。日志与崩溃报告里可能带有你的节点域名、订阅地址或配置片段 —— 不想公开的行删掉再贴，不影响定位问题。

4. 不要为了排障去改系统 DNS / 路由

三条理由，都跟「别把现场弄乱」有关：

  • 起不来的那个进程什么网络都没改。它连自己的启动都没走完， 所谓的「接管路由 / 改 DNS」只在 App 正常跑起来之后才发生。所以网络配置与这次崩溃 多半无关，改它不会让它能启动。
  • App 只回滚它自己做的改动。它对网络的每一处改动都先落盘成快照、 退出或崩溃后按快照回滚；你手动敲的 networksetup / route 不在任何快照里，不会被自动恢复，可能让机器停在断网状态。
  • 它会把诊断变难。下一个看到日志的人无法区分「App 的问题」与 「排障时手动改的东西」。所以我们可能需要先让你把改动还原，多绕一圈。

正确的顺序是：什么都别改 → 把上面两份日志发给我们 → 我们需要时会给 可回滚的具体命令（改之前能记下原值、之后能改回去的那种）。

如果你已经手动改过：不要继续叠加改动。把「改了什么」写进 issue（命令与它影响的网络服务名）， 我们一起把它还原回原值。

5. 顺带：还有这些日志

  • startup.log：与 panic.log 同一个 logs/ 目录。它记的是「启动失败」这类可读原因（覆盖写，只留最新一次）。
  • App 内的「日志」页：能起来的话，侧栏「日志」里有运行日志， 那一页也会告诉你 panic.log 在哪。
