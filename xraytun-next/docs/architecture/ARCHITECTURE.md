# xraytun v1 架构原理 —— 从零推导的记录

> 这份文档回答一个问题：**为什么长这样**。
>
> 它不描述"我们写了什么"（那是代码和 `docs/verification/` 的事），也不重复契约字段表
> （那是 `00-CONTRACT-FREEZE.md` 与 `crates/xt-contract/`）。它记录的是**推导过程**：
> 从物理约束出发，一步步推出必须存在的边界、必须放弃的方案、以及每一步的代价。
>
> 阅读方式：每一节都写成「现象 → 可选方案 → 选择 → 代价 → 判据」。
> 如果你只关心结论，读每节的表格；如果你要挑战设计，读"被否决的方案"那一栏。
>
> 证据分级（沿用旧仓库的规矩，违反即返工）：
> **✅ = 本机跑过并留下命令与输出**；**📄 = 有文档/提交为据**；
> **🧠 = 推理，尚未验证**。没有 ✅ 的结论不许写成"已验证"。

---

## 0. 一句话结论

> 这是一个**跑在用户机器上、必须动系统网络、且要在用户面前说真话**的程序。
> 这三个限定词决定了它的全部形状：动系统网络 ⟹ 必须有特权边界；
> 跑在用户机器上 ⟹ 不能引入网络微服务；要在用户面前说真话 ⟹ 不能有回落、
> 不能有假控件、不能让"未知"看起来像"0"。

---

## 1. 从物理约束推导，而不是从"最佳实践"推导

任何架构都有前提。先把前提写清楚，后面的选择就不再是口味问题。

### 1.1 约束清单

| # | 约束 | 来源 | 推论 |
| --- | --- | --- | --- |
| C1 | 创建 `utun` 必须 root（内核 `com.apple.net.utun_control` 带 `CTL_FLAG_PRIVILEGED`） | 📄 旧仓库 `docs/01-architecture.md` §1 | 必须存在一个特权进程；且它越小越好 |
| C2 | 数据面要解析来自互联网的**不可信字节**（TLS 记录、代理协议握手） | 📄 同上 §2.2 | 解析器不许以 root 运行 ⟹ 数据面与特权面必须分离 |
| C3 | 用户装的是**桌面应用**，不是集群 | 产品事实 | 服务之间的"独立伸缩/独立部署"不需要；跨 TCP 只增加端口、延迟、打包负担 |
| C4 | 用户会盯着界面问"现在到底通不通" | 📄 旧仓库 `docs/09-network-drop/UX-AND-HISTORY.md`、`docs/incidents/` | 状态必须可解释：卡在哪一步、失败的真实原因是什么，都要能显示 |
| C5 | 用户已经明确否决过"替我兜底"的行为 | 📄 旧仓库提交 `0ef7ac3`、`928b76d`、HANDOFF §1.2 | 回落/自动重连不是"贴心"，是被用户判定为不可接受 |
| C6 | 只有一台开发机，没有本地 Rust/真机 macOS | 本机环境 ✅（`uname` = Linux x86_64，无 cargo → 已装 rustup 1.98.1） | 平台无关的部分必须能在 Linux 上端到端验证；macOS 专属部分不许写"已工作" |

### 1.2 由 C1+C2 推出的第一条边界

```
疑问：既然 helper 已经是 root，顺手把 xray 也拉起来岂不是更简单？
答案：不行。那意味着整个代理内核以 root 解析互联网来的不可信数据。
```

这一条推导得出本项目的第一个结构性事实：**特权面与数据面是两个进程，且特权面不认识"代理"这个概念。**
它只接受一组封闭指令（建卡、配地址、装路由、改 DNS、交 fd、按快照回滚），
不接受任意命令、任意路径。

> **代价（必须写出来）**：多一次 IPC、多一个需要安装的守护进程、以及
> "helper 崩了而网络配置留在半残状态"这类问题必须自己处理（这就是快照机制存在的原因）。
> **判据**：特权侧代码里不出现任何协议解析；所有外部命令用绝对路径 + argv，永不过 shell。

### 1.3 由 C3 推出的"不要网络微服务"

用户要的是"尽可能微服务"。这条要求在本项目里**不能字面执行**，理由是 C3：

```
网络微服务的收益 = 独立伸缩 + 独立部署 + 故障隔离（跨机器）
桌面端的现实   = 只有一个用户、一台机器、一次安装
跨 TCP 的代价  = 端口冲突、防火墙弹窗、延迟、打包体积、更多崩溃面
```

于是把"微服务"翻译成**在收益真正存在的地方保持离散**：

| 需求 | 桌面端正解 | 不是 |
| --- | --- | --- |
| 故障隔离 | **进程边界**（UI ↔ daemon ↔ helper ↔ xray） | 一台机器上开 6 个 daemon |
| 单一职责 | **crate 边界 + 单向依赖**（编译期强制） | 用 HTTP 把函数调用变成网络调用 |
| 可独立验证 | **纯函数 + 可无头运行**（`xt-cli` 与 UI 同一契约） | 每个服务一套部署配置 |

**判据**：`cargo tree` 无环；新增进程边界时必须回答"它隔离了什么故障/权限"；
回答不出来就不加（这条写进了 `00-CONTRACT-FREEZE.md` §1）。

### 1.4 由 C4+C5 推出"界面只说真话"

旧仓库用一整轮事故史换来三条界面规则（📄 `docs/incidents/`、HANDOFF §3）：

1. **删了功能就必须删掉控件** —— 界面上留着按不动的按钮，就是在暗示能力还在。
2. **没有成功证据不许写"正常/成功"** —— "没有证据 ≠ 干净"。
3. **失败要原样显示**，不要翻译成"请稍后重试"——我们并不打算重试。

这三条在 v1 里被提升为**类型层面的约束**，而不是评审时的纪律：

```rust
ConnectionView {
    stage: Stage,                 // 只有 Connected 才允许界面写"已连接"
    phase: Option<ConnectPhase>,  // 卡在哪一步，可显示
    stats: Option<StatsView>,     // None = 从未采样成功 → 界面必须写"未采样"
    last_error: Option<ErrorBody>,// 真实失败，不被后来的成功擦掉
}
```

未知与 0 在类型上就是两件事（`None` vs `Some(0)`）。这是 I3 的实现方式：
**不让"撒谎"成为一个容易写出来的代码**。

## 2. 五条不变量：每一条都有一个真实的伤疤

不变量不是口号，是"踩过的坑"的压缩。每条都给出反例、代价与机器判据。

### I1 · 没有等待

**现象**：旧版本的启动路径里有一条 50ms 轮询（等 SOCKS 端口可连），重试里还有 700ms/500ms 的固定停顿。
**伤疤**：轮询让"启动慢"和"核心其实已经崩了"看起来一样；固定停顿在快机器上纯浪费，在慢机器上仍可能不够。📄 提交 `d6c492e`。

| 方案 | 结论 |
| --- | --- |
| 固定 sleep 后检查 | ✗ 慢且不可复现，掩盖真实失败 |
| 固定间隔轮询 | ✗ 同上，且引入"多久算超时"的玄学参数 |
| **事件驱动就绪** | ✅ 核心每输出一行就试一次非阻塞连接；进程提前退出 → `CoreExitedEarly`（带真实退出码与最后几行输出） |

**代价**：核心"沉默但不退出"时不会自己变好 —— 所以允许**一个 deadline**，
但它只作为**失败上限**，超时必须产出一个具体的 `ErrorBody`，不许用来循环重试。
**判据**：`bash scripts/guard.sh` 扫 `sleep|interval|setInterval|setTimeout|poll_interval`。

#### I1 的一课：**"就绪"必须覆盖所有必需能力**（真实事故）

第一版实现把"SOCKS 端口可连"当成了唯一的就绪信号，然后**一次性**去连 StatsService
的 api 入站。这在多数时候能跑通，但 `xt-stats` 与 api 入站之间是竞态：
xray 的 socks 入站先 accept、api 入站后 accept。

后果很微妙，也很值得记下来：**它不是"把未知显示成 0"（I3 的正面守卫拦住了），
而是反向的——明明能知道，却整段会话一直显示「未采样」。** 两种都是让界面说假话。

| 方案 | 结论 |
| --- | --- |
| 连不上 stats 就重试几次 | ✗ I2；而且掩盖了"我们的就绪定义不完整"这个真问题 |
| 放弃第一次采样，后面再说 | ✗ 会话内一直 `stats: None`，"未采样"变成噪音 |
| **就绪 = 所有必需端口都接受**（socks + api） | ✅ 每读到核心一行输出，对**尚未就绪**的地址各试一次连接；全部就绪才算 Ready |

发现方式值得单独说：这条缺陷**不是**写代码的人自查出来的，是 ux 在真机活体验收里
用真 daemon + 真 xray 反复跑、统计命中率（5 次中 2 次）钉出来的
（📄 `docs/ux/LIVE-EVIDENCE.md` §4）。**"我实现了" 与 "它在真实时序下成立" 是两件事**，
这就是为什么本项目的验收要求"独立的人 + 真进程 + 可复跑的判据"。

**而且第一版修法不够**：只把 api 端口的 **TCP accept** 纳入就绪，仍然复现（一批 8 次里 2 次）。
继续追下去，根因其实是两条**"发布状态的时机"**问题，都不是靠重试能解决的：

1. daemon 先提交并发布 `Connected`，**之后**才建立 stats 客户端 ——
   于是存在一个"状态说已连接、统计链路还没装好"的窗口。而 UI 的采样是消费者驱动的，
   它一看到 `Connected` 就会问 `Status`，正好落在这个窗口里。
2. h2 握手成功 ≠ gRPC 服务已能应答。TCP 层可连只是必要条件。

**最终修法（两条，都仍然没有 sleep / 重试 / 回落）**：

* **顺序即语义**：先在内部把统计链路装好，再发布 `Connected`。
  状态一旦说出口，它隐含的东西就必须已经成立。
* **就绪判据升级成"能力可用"**：把「能真的查到一次计数」并入就绪判定；
  没成功就等核心的**下一条日志**再试（事件驱动，核心每次被查询都会打日志），
  用 `timeout_at` 兜住"核心一声不吭"的情况（失败上限，不是等待手段）。
  窗口内始终不通 → 如实发 Notice + 保持「未采样」，绝不用 0 顶替。

**回归证据**：修后 `e2e_real_xray` **连续 20 次全绿**（此前一批 8 次里失败 2 次）。
📄 `docs/verification/FINAL-VERIFY.md` §4 记录了完整的时间线（含"第一版没修好"这一段）。

### I2 · 没有回落

**现象**：旧版本切节点时会"失败就自动换下一个"，启动时会自动重连，还有看门狗在监视网络。
**伤疤**：① 用户看到的最终节点和点的不一样，却不知道发生过什么；
② 错误归属消失（失败被自动路径吃掉了），界面上一切正常；
③ 测试从"验证行为"变成"验证兜底"，删机制时要删掉 30+ 条断言已删机制的测试。📄 提交 `0ef7ac3`、`fd4e83f`、`550eaf8`、`928b76d`。

| 方案 | 结论 |
| --- | --- |
| 失败自动换下一个节点 | ✗ 用户裁决否决：这是"我替你决定" |
| 失败自动重连 / 看门狗 | ✗ 同上，且把真实故障掩盖成"偶发" |
| 降级到直连保命 | ✗ 用户以为在受保护，其实没有 —— 最危险的一种谎 |
| **选择就用，失败就停并如实报错** | ✅ |

**代价**：一次失败=一次用户可见的中断，用户必须自己再点一次。
我们认为**可解释的中断**优于**不可解释的"正常"**。

**保留的例外（唯一一个）**：崩溃/退出时把已改的本机状态**还原**（helper 快照、遗留清理）。
那是清理，不是"换一条路成功"——它不改变"意图只有一个结果"这个语义。

**判据**：`ErrorCode` 是封闭枚举，里面没有 `Retry`/`Fallback`/`Degraded`（类型层面不可能）；
guard 扫源码里的 `fallback|retry|backoff|回落|兜底|降级`。

### I3 · 没有假话

**现象**：展示型软件习惯把未知渲染成 0、把连接中渲染成已连接、把没有的能力留一个灰按钮。
**伤疤**：旧仓库把它总结成一句"界面不许有假控件；没有成功证据不许写正常"（HANDOFF §3）。

| 场景 | 错误做法 | v1 的做法 |
| --- | --- | --- |
| 流量还没采样到 | 显示 `0 B` | `stats: None` → 界面写「未采样」 |
| 核心版本未知 | 显示写死的版本号 | `datapath.version: None` → 不显示这一行 |
| 延迟没测过 | 显示 `--` 或 0ms | `ProbeResult` 恰好是 `ttfb_ms` 或 `error` 二选一，没有"含糊态" |
| 能力未实现 | 渲染禁用按钮 | 能力不在 `Capabilities` 里 → 界面不渲染入口 |

**判据**：guard 扫运行时 UI 代码里的 `preview*/mock/fake/dummy`；ux 的
`truthfulness.test.tsx` 逐条断言"改注入值 → 界面跟着变"（防写死）与"未采样 ≠ 0"。

### I4 · 单向依赖

**现象**：UI 直接对齐 Rust 内部类型、底层 crate 反向依赖上层。
**伤疤**：改一个字段要人肉找所有调用方；"谁有权改系统网络"变成需要读代码才能回答的问题。

**做法**：分层 + `Cargo.toml` 强制（见 §3），跨进程的词汇只有一份（`xt-contract`）。
**判据**：guard 检查每个 crate 的依赖是否落在分层表允许的集合里；`cargo tree` 无环。

### I5 · 权限最小面

**做法**：只有 helper 改系统网络，且它只认识封闭指令集；数据面以普通用户运行。
**本轮状态**：helper 未实现（§8 明说），因此**任何"TUN 已工作"的说法都是假话**。
这条不变量提醒的是：**没做的事，要写成没做**。

## 3. 服务分解：每个切分点都要回答三个问题

切分不是越多越好。每加一条边界，我们就多付一次"跨边界成本"（序列化、异步、错误转换、
版本漂移）。所以 v1 的规则是：

> **只有当"这个组件能被单独验证"或者"它必须被隔离权限/故障"时，才切开。**

### 3.1 进程图（谁跟谁说话）

```
        ┌───────────────────────────────────────────────┐
        │ UI（React，apps/ui）                            │
        │  只做两件事：把事件画出来、把意图发出去            │
        └───────────────────┬───────────────────────────┘
                            │ AF_UNIX · 长度前缀 JSON 帧
                            │ （xt-contract 定义的唯一词汇）
        ┌───────────────────▼───────────────────────────┐
        │ xraytund —— 控制面（普通用户）                   │
        │  settings · subs · nodes · state · datapath     │
        │  stats · probe · bus · ipc-server               │
        └───────┬───────────────────────────┬───────────┘
                │ spawn/monitor（父子进程）    │ 封闭指令（本轮未实现）
        ┌───────▼──────────┐        ┌───────▼──────────────┐
        │ xray（数据面）     │        │ xraytun-helperd(root) │
        │  真实字节从这里来   │        │  utun/route/DNS/快照   │
        └──────────────────┘        └──────────────────────┘
```

**为什么 daemon 是独立进程**（切分前三问）：

| 问题 | 回答 |
| --- | --- |
| 它隔离了什么？ | UI 崩溃/重载不牵连隧道；业务逻辑脱离 WebView 就能验证；崩溃归属清楚 |
| 谁拥有它的状态？ | 唯一所有者是 daemon；UI 只是订阅者（订阅者不许做第二份真相） |
| 它能被单独验证吗？ | ✅ 能：`xt-cli` 用**同一份契约**驱动真 daemon，E2E 不需要 GUI |

**被否决的方案**：

| 方案 | 否决理由 |
| --- | --- |
| 逻辑放在 Tauri 进程里（v0.9.2 的做法） | WebView 与核心生命周期绑死；业务逻辑只能靠 UI 测试覆盖；无法无头验证 |
| 每个能力一个本地 daemon（真·本地微服务） | 收益（隔离）与"多进程"不成比例；打包、启动、日志聚合成本陡增；C3 |
| 用 gRPC 替代 AF_UNIX+JSON | 唯一消费者是本机 UI/CLI；JSON 能被 `nc` 与用户直接看懂（可排查性 > 编解码性能）；引 protoc 会污染构建链 |

### 3.2 crate 分层（编译期强制的单向依赖）

```
L0  xt-contract ─────── 类型 / 错误 / 事件 / 帧（无 IO、无 tokio、无 unsafe）
      ▲
L1    ├── xt-state      连接状态机（纯函数，可穷举）
      ├── xt-bus        进程内事件总线（watch/broadcast）
      ├── xt-settings   设置（单文件 + 原子替换）
      ├── xt-subs       订阅解析（纯函数）
      └── xt-xrayconf   配置生成（纯函数）
      ▲
L2    ├── xt-ipc        AF_UNIX 帧传输（client/server）
      ├── xt-nodes      节点目录 + 选择
      ├── xt-stats      真实字节数（StatsService）
      ├── xt-probe      真实 TTFB
      └── xt-datapath   xray 进程生命周期
      ▲
L3    ├── xt-daemon     组合根：装配 + 对外 IPC
      └── xt-cli        无头客户端（与 UI 同契约）
```

三个设计决定值得单独说明：

1. **契约里不放 trait**。只有一个实现者的抽象接口是仪式，不是边界。
   本项目真正的边界是进程边界，它已经被 `Frame`/`Request`/`Event` 类型表达了。
   （什么时候才该加 trait：当同一抽象真的有两个实现，且它们的差异会被测试覆盖。）
2. **纯函数尽量下沉**。`xt-state` / `xt-subs` / `xt-xrayconf` 都不做 IO，
   所以它们可以在毫秒级被穷举测试。**能纯的地方纯掉，是"可验证"最便宜的来源。**
3. **组合根只有两个**（`xt-daemon`、`xt-cli`）。L3 是唯一允许"知道一切"的地方；
   它把依赖装配起来，别的 crate 之间不允许横向乱连。

## 4. 数据流：事件驱动的一天

### 4.1 连接（proxy 模式，本轮唯一完整实现的路径）

```
UI 点「连接」
  │  Request::Connect{node_id, mode=proxy}   ──────────────► daemon
  │  ◄── Response::Accepted（受理，不含结论）                  │
  │                                                          │
  │   Event::State{stage=connecting, phase=preparing_config} ◄┘
  │        │ 生成配置落盘（xt-xrayconf，纯函数）
  │        │ xray run -test 预检 ── 失败 → ConfigInvalid（不进子进程）
  │   Event::State{phase=starting_core}      ← spawn 真进程，拿到真实 pid
  │   Event::State{phase=awaiting_ready}     ← 每读到核心一行输出就试一次连接
  │   Event::State{stage=connected, connected_since_ms=<真实时钟>,
  │                datapath={pid, version, ready_at_ms}}
  ▼
界面写「已连接」——因为只有这一刻才有证据
```

**为什么"受理"和"结论"要分开**：如果 `connect` 同步返回结论，那么调用方只有
两个选择——阻塞（UI 卡住）或轮询（I1 违例）。分开之后，**结论自己会到**，
客户端不需要"等一会儿再看看"，这类代码就没有存在的理由。

### 4.2 断开

```
Request::Disconnect → Accepted
  → SIGTERM 核心 → （deadline 仅作失败上限）→ SIGKILL → reap 真进程
  → helper.TunDown（本轮未实现，proxy 模式无此步）
  → Event::State{stage=disconnected}
```

**顺序理由（继承旧架构）**：必须先停数据面再撤网络配置，因为核心还持有隧道 fd。

### 4.3 切节点（"选择就用"）

```
Request::SwitchNode{node_id} → Accepted
  → 生成新配置（outbound tag = node-<新 id>）→ 预检 → 重启核心 → 等就绪事件
  → 成功：Event::State{connected, node_id=新}
  → 失败：Event::State{disconnected, last_error=真实原因}   ← 到此为止，不换下一个
```

**为什么重启而不是热更新**：Xray 的 API 支持动态增删 outbound，但热更新会引入
"旧连接还在旧出口上"的中间态，而中间态正是最难解释、最难测试的东西。
切换是分钟级操作，重启的 ~300ms 代价可接受。
（**被否决的方案记在这里**：未来若要消除重启停顿，正确路径是 API 热更新 + 明确
定义"旧连接如何处理"的语义，而不是加一条回落。）

### 4.4 流量统计：**消费者驱动采样**（本版新增的设计）

问题：Xray 的 `StatsService` 是**拉**模型，没有推送。于是"界面上的实时速度"天然需要节拍。
传统做法是 daemon 里放一个定时器（`interval`）——那就违反了 I1 的字面要求。

```
消费者（UI）渲染完上一帧 → 立刻请求 Status → daemon：
   ├─ 缓存样本年龄 < 100ms → 直接返回缓存（不打扰核心）
   └─ 否则 → 向 StatsService 采一次真实字节 → 返回并更新缓存
```

于是**节拍来自消费者**：界面在渲染，采样就在跑；界面隐藏/停住，采样自动停止。
daemon 里没有任何定时器，也就没有"后台空转"和"采样周期该设多少"的玄学参数。

**代价**：如果没有任何消费者，daemon 不会自动刷新缓存 —— 这正是我们想要的
（没有观察者就没有观测）。**判据**：daemon 源码里不出现 interval/定时器；guard 扫。

## 5. 错误模型：用错误码反推界面文案

错误是一个**封闭枚举**（`ErrorCode`），每个成员都对应"我们知道自己该做什么"：

| 错误码 | 谁产生 | 界面应该说什么 | 不该说什么 |
| --- | --- | --- | --- |
| `config_invalid` | 配置预检 | 配置非法 + 核心原话 | "请重试" |
| `core_exited_early` | 数据面 | 核心在就绪前退出 + 退出码 + 最后输出 | "连接不稳定" |
| `datapath_unavailable` | 数据面 | 找不到/无法执行 xray + 路径 | "网络异常" |
| `helper_unavailable` | 特权面 | helper 未安装/版本不符 | "权限问题（请重试）" |
| `conflict` | 状态机 | 当前状态不允许这个操作 | 静默忽略 |
| `permission_denied` | 特权面 | 被拒绝的真实原因 | "设置失败" |
| `not_found`、`invalid_request`、`io`、`internal` | 各处 | 原样 + 上下文 | 任何"已经帮你处理好了" |

**为什么不用"其他/未知错误"兜底**：那会让所有未分类的 bug 看起来像"偶发网络问题"，
正是旧仓库事故报告里反复出现的失败模式。**没有兜底类，才会有人去分类。**

## 7. 迁移与不做什么

### 7.1 为什么是平行重写而不是原地重构

| 方案 | 结论 |
| --- | --- |
| 原地重构 v0.9.2（已发布、有 CI、有用户） | ✗ 每次提交都要同时满足"新架构"与"旧行为不回归"，两套约束互相拖拽 |
| **平行重写 `xraytun-next/`** | ✅ 旧版冻结可发布；新架构可以按"先契约后实现"重排；两者用同一套验证口径比较 |

**代价**：一段时间的重复代码；迁移期要明确"哪些能力已经在 v1 里可用"（见 product 的范围表）。

### 7.2 本轮**不做**（每一项都写清楚为什么）

| 不做的事 | 为什么 | 用户会失去什么（诚实说法） |
| --- | --- | --- |
| macOS TUN + 特权 helper | 开发机不是 macOS；没有真机就没有证据，而"没有证据"不等于"能用" | v1 本阶段只有 SOCKS 代理模式，不能接管全系统流量 |
| 自动重连 / 回落 / 看门狗 | 用户已明确否决（📄 `0ef7ac3`、`fd4e83f`） | 失败后需要用户手动再点一次 |
| 审计上传 / 地理可视化 / 拓扑图 | 与"最小可用"无关；旧仓库的过度建设清单已证明其复杂度收益比 | 没有这些面板 |
| 兼容 v0.9.2 的旧设置/旧协议 | 兼容分支正是 I2 要消灭的东西；版本不符直接拒绝 | 旧用户需要重新配置 |

（产品侧的完整"不做清单 + 收益放弃"见 `docs/product/SCOPE.md`。）

## 8. 决策索引（ADR）

| # | 决策 | 一句话理由 | 被否决的替代 |
| --- | --- | --- | --- |
| D1 | 特权面与数据面分进程 | 不让 root 解析不可信字节（C1+C2） | helper 里直接跑 xray |
| D2 | 控制面独立 daemon | 隔离 UI 崩溃 + 无头可验证 | 逻辑放 Tauri 进程 |
| D3 | AF_UNIX + 长度前缀 JSON | 可排查性 > 编解码性能；无 protoc | gRPC / 网络微服务 |
| D4 | 契约层只放数据不放 trait | 只有一个实现者的抽象是仪式 | 全套 service trait |
| D5 | 事件驱动就绪 | sleep/轮询掩盖真实失败（I1） | 50ms 轮询（旧版） |
| D6 | 选择就用，失败即停 | 用户裁决；可解释的中断 > 不可解释的正常（I2） | 自动换下一个节点 |
| D7 | 统计由消费者驱动采样 | 去掉定时器与玄学周期参数 | daemon 内 interval 轮询 |
| D8 | 未知用 `None` 而非 0 | 界面说谎的最主要来源是"把未知画成 0"（I3） | 默认值/占位值 |
| D9 | 平行重写 | 两套约束互相拖拽 | 原地重构已发布版本 |
| D10 | 切节点走重启 | 避免"旧连接在旧出口"的中间态 | API 热更新（留待后续，且必须先定义旧连接语义） |
