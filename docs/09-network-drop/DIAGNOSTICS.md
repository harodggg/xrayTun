# 断网现场取证：脚本用法与判读

> 配套阅读：`ROOT-CAUSE.md`（根因分析）、`SELF-HEAL-GAPS.md`（兜底为什么救不回来）。
> 本文件只讲三件事：**怎么取证**、**每条证据对应哪个假设**、**中国大陆可达性我们能测到哪一步**。

---

## 0. 一条命令

在**断网发生时或刚断开之后**，用户只需要跑这一条：

```bash
cd <仓库目录>
./scripts/diagnose-network-drop.sh
```

产出**单个文件**并打印路径：

```
~/Desktop/xraytun-diag-<YYYYmmdd-HHMMSS>.txt
```

桌面不可写时依次退到 `~` 与 `/tmp`（**不写仓库目录**，避免污染工作区）。
把这个文件发回来即可 —— 需要发回的只有它一个。

常用选项：

```bash
./scripts/diagnose-network-drop.sh --minutes 30        # 日志回看窗口（默认 10 分钟）
./scripts/diagnose-network-drop.sh --socks-port 10808  # 手动指定本机 SOCKS 端口
./scripts/diagnose-network-drop.sh --node 1.2.3.4:443   # 手动指定节点（做 TCP 握手对照）
./scripts/diagnose-network-drop.sh --redact-ip --redact-node   # 连 IP 与节点地址也打码
```

SOCKS 端口与节点 `address:port` 由脚本从本机 `runtime/config.json` **只提取这两个字段**得到；
提取不到时可用上面的选项手动给（脚本会在报告开头写明来源）。

## 1. 采集了什么，每节对应哪个假设

| 节 | 采集内容 | 用来验证 / 排除的假设 |
|---|---|---|
| **1 系统与电源** | `sw_vers`、`uname`、`pmset -g`、`pmset -g assertions`、睡眠/唤醒日志 | 断网是不是发生在**睡眠/唤醒**之后（唤醒后隧道路由没恢复） |
| **2 网卡与地址** | `ifconfig -a`、Wi-Fi 关联、物理口 IPv4、utun 及其地址 | 物理链路是否还在；utun 是否**有路由但没有地址**（黑洞风险） |
| **3 路由表** | 全量 `netstat -rn`、`route get default`、`route get 1.1.1.1`、`0.0.0.0/1`、`128.0.0.0/1`、`198.18.x` | 默认路由是否被 TUN 接管；**断开后是否没回滚**（残留拆分路由） |
| **4 DNS** | `scutil --dns`、`networksetup -getdnsservers <服务>`、`/etc/resolv.conf` | 解析器是否仍指向**隧道内哨兵**（198.18.x）→「连接期间连域名都解析不了」 |
| **5 helper** | 进程、`launchctl list`、二进制 / plist / socket、`launchctl print` | 断开时的**回滚**是否可能根本没执行（helper 不在 → 路由/DNS 残留） |
| **6 应用与核心** | 进程、数据目录与 runtime 清单 | 核心是否还在跑；**配置/订阅文件只列清单不读内容**（见 §3） |
| **7 日志（脱敏）** | 应用日志尾部 200 行 + `log show`（最近 N 分钟） | 断开/恢复/回滚/看门狗的**实际时序** |
| **8 三态对照** | 见 §2 | **决定性证据**：区分整机断网 / 协议被墙 / 代理正常 |
| **9 自动判读** | 把上面事实缩成几条**推断** | 省得在千行输出里翻找（明确标注「不是结论」） |

## 2. 决定性证据：三态判定（第 8 节怎么读）

四组探测：

1. **8.1** 本机 SOCKS 是否在监听（`nc -z 127.0.0.1:<socks_port>`）；
2. **8.2** `curl --interface <物理口>`（**绕过隧道**）vs 默认路由（经隧道）—— 同一目标；
3. **8.3** 到**节点 `address:port`** 的 **TCP 三次握手**（`nc -z`，**不经代理**）；
4. **8.4** **经本机 SOCKS 的真实 HTTP 请求**（境外目标 + 境内 `www.baidu.com`）。

判读表（与 `ROOT-CAUSE.md` §六 一致）：

| 节点 TCP 握手 | 经 SOCKS 真实请求 | 直连（物理口） | 结论 |
|---|---|---|---|
| 通 | **失败** | 正常 | **B 态**：TCP 通、代理协议握手被阻 —— 用户症状「国外可以、国内断掉」最像的机制 |
| 通 | 失败 | **也失败** | **A 态**：整机断网（默认路由已接管且黑洞） |
| 通 | 通 | 正常 | **C 态**：代理正常，问题在别处 |
| **不通** | — | — | 不是「协议被墙」，而是链路/节点不可达 —— 那时本该由 `tcp_reachable` 拦住，需另查它为何没拦住 |

**curl 退出码怎么读**（报告里每行都带 `rc=`）：

* `0` 成功（再看 `http=` 是否 2xx/204）；
* `7` 连不上 —— 多半是**本机 SOCKS 没起**或端口不对（不是网络问题）；
* `28` 超时；**`35` TLS 握手失败**；**`52`/`56` 空响应 / 连接被重置**
  —— 后三者是「TCP 通、协议层被干扰」的典型形状，请连同 `connect=` / `total=` 时间一起看；
* 同时对照 **8.2 的直连**那一行：直连正常而默认路由异常 → 问题在隧道/代理侧。

## 3. 脱敏与隐私（本项目红线）

**被替换掉的**：

* UUID → `<UUID>`；
* URL 路径 → `scheme://host/<REDACTED>`（**只留 host**）；
* `password` / `token` / `secret` / `api_key` 的值 → `<REDACTED>`；
* 40 字符以上的 base64/blob（订阅内容、公钥等）→ `<REDACTED-BLOB>`。

**明确不读内容的**：`nodes.json`、`settings.json`、`runtime/config.json`
—— 只列**文件名与大小**。脚本仅从中提取**两个字段**：本机 SOCKS 端口、
当前节点 `address:port`（后者只用于 §8.3 的 TCP 握手）。

**仍然保留的**：内网/公网 IP（路由与 DNS 判读必需）、当前节点地址、
日志尾部（已按上面规则脱敏）。

若连这些也不想提供，加 `--redact-ip --redact-node` 重跑：
IP 会打码（**保留** 127/10/172.16-31/192.168/198.18，否则路由与 DNS 就没法判读了）。

报告结尾还会做一次**全文兜底脱敏**：即使某一节漏了单独过滤，也不会把凭据带出去。
（`--redact-ip` 只处理 IPv4；IPv6 未打码 —— 见 §7 诚实清单。）

## 4. 「只读」是怎么验证的

**代码层**：脚本只调用读命令（`netstat` / `ifconfig` / `scutil` / `networksetup -get…` /
`ps` / `pgrep` / `launchctl list|print` / `log show` / `pmset` / `sysctl` / `dig` / `curl` /
`nc` / `ping` / `traceroute`）。**没有** `networksetup -set*`、`route add|del`、
`ifconfig up|down`、`kill`、`launchctl load|unload`；除了写出报告，不改任何文件。

**实测层**（本机 macOS 26.6.2，XrayTun 应用**正在运行**）：对「路由表 + 接口 + DNS」取指纹，
比较两个 90 秒窗口：

| 窗口 | 差异行 | 其中 ARP(`UHLWI`) 行 | 路由 / 接口 / DNS 相关差异 |
|---|---|---|---|
| **控制组**（什么都不做，等 90s） | 115 | 103 | **0** |
| **实验组**（跑本脚本） | 124 | 112 | **0** |

`scutil --dns` 的内容哈希与最初快照**完全一致**。结论：脚本运行带来的输出变化与
「什么都不做」**同量级、同性质**（ARP 邻居缓存的过期计数器），**没有任何路由/接口/DNS 改动**。

## 5. 「断网也能跑」

* 每个联网探测都有**短超时**并单独容错：`curl --max-time 6..8`、`nc -G/-w 3..4`、
  `dig +time=3 +tries=1`、`traceroute -m 5 -w 1`、`log show`（30s 上限）；
* **任一项失败都不影响后续**（脚本不用 `set -e`，失败只留输出）；
* **不下载任何东西**、不依赖 `python`/`node` 装包（脱敏用系统自带 `sed`）；
* 输出是**单个文件**，便于在断网环境下用 AirDrop / U 盘 / 手机拍照带走。

## 6. 中国大陆可达性：我们能测什么、测不到什么

canonical 站点是 `https://xraytun.top`（Cloudflare Pages + 代理）。
**公开且长期存在的现象**：Cloudflare 的 IP 在中国大陆经常被限速、丢包或干扰。

### 6.1 我们能测的（本环境实测值）

| 量 | 值 |
|---|---|
| `dig +short xraytun.top`（系统解析器） | `172.67.205.101` / `104.21.61.28` |
| `dig @223.5.5.5 xraytun.top` | 同上 |
| `dig @1.1.1.1 xraytun.top` | 同上 |
| `curl -sI https://xraytun.top/` | **200** |
| 本机默认路由 | `en0 → 192.168.0.1`（**不经隧道**） |

也就是说：**从本环境（非中国大陆）看，域名解析与 HTTPS 都正常**。

### 6.2 我们**测不到**的（诚实清单）

* **无法实测中国大陆的访问质量**：本机不在国内，也没有任何国内拨号/机房环境；
* **无法复现 GFW 行为**：限速、丢包、RST、SNI 阻断都发生在运营商链路，本环境构造不出来；
* **无法区分**「Cloudflare 侧限速」与「运营商侧干扰」；
* 因此**不能**下结论说「官网在国内可用/不可用」—— 只能说「从本环境看返回 200」。
* 同理，**本文不给出任何中国大陆的实测数字**；下面 §6.3 是给**用户**在自己网络里跑的方法。

### 6.3 用户可自行验证的步骤（在国内网络下跑）

```bash
# 1) 解析是否正常（三个解析器对照）
dig +short xraytun.top
dig +short @223.5.5.5 xraytun.top
dig +short @1.1.1.1 xraytun.top

# 2) 443 端口是否通（TCP 层）
nc -z -G 3 -w 3 xraytun.top 443

# 3) HTTP 层真实请求（看退出码与各阶段耗时；失败时加 -v 看卡在哪一步）
curl -sS -o /dev/null \
  -w 'http=%{http_code} connect=%{time_connect}s tls=%{time_appconnect}s total=%{time_total}s\n' \
  --max-time 15 https://xraytun.top/

# 4) 对照：同机测 Cloudflare Pages 的直连域名（用来区分「CF 全域」还是「这个域名/接入点」）
curl -sS -o /dev/null -w '%{http_code}\n' --max-time 15 https://xraytun.pages.dev/

# 5) 对照：换网络（手机热点 / 公司网）各测一次，并各测「开代理 / 不开代理」
```

**怎么解读**：

* 解析正常但 `nc -z` 不通 → 到 CF 接入点的 **TCP 层**就不通（运营商或 CF 侧）；
* `nc -z` 通、`curl` 在 TLS 阶段失败或超时（`rc` 35 / 52 / 56 / 28）→ 典型的**链路层干扰**；
* 只有 `xraytun.top` 不通而 `xraytun.pages.dev` 通 → 差异更可能在**域名/接入点**，而不是整条 CF；
* 只有某一家运营商不通 → 指向**该运营商链路**，不是全球性故障；
* 换网络或开代理后立刻恢复 → 强烈指向**本地网络/运营商**。

### 6.4 建议（**是建议，不是已确认的原因**）

若**多个不同省份、不同运营商**的用户都报告 `xraytun.top` 打不开，可以考虑（按成本排序）：

1. **保留 GitHub Pages 作为备用入口**（当前已在运行）—— 它与 Cloudflare 是两条独立链路，
   至少不会同时同因故障；站点自己的 canonical 仍然只指 `xraytun.top`；
2. 增加一个**国内可直连的镜像**（对象存储 + CDN），canonical 保持不变；
3. 更换 Cloudflare 的接入方式/套餐（例如自有 IP 接入）—— 成本最高，且**不保证**效果。

⚠️ **这些都不是「已确认的根因」**：我们没有任何中国大陆的实测数据支撑其中任何一条。
在拿到用户按 §6.3 自查的结果之前，**不要**把它们写进发布说明或官网文案当结论。

## 7. 本文件的诚实清单

* 脚本「只读」是**代码检查 + 本机对照实验**得出的，**未在其它 macOS 版本**上验证；
* §2 的三态判读表是**推理**，需要用户现场数据确认；表里「TCP 通/不通」的边界
  （例如丢包率很高时 `nc -z` 时通时不通）可能需要重复测几次；
* §6 除 6.1 的五个本机实测值外，**其余都是方法与建议，没有实测支撑**；
* `--redact-ip` 只处理 IPv4，**IPv6 未打码**；
* 日志尾部靠 `log show` 与文件尾部采样，**不保证覆盖断网那一刻的全部日志**
  （环形日志可能已经滚动掉）。
