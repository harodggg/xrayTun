## 0. 一句话原则

**官网复用应用的 token，但不用应用的排版。**

- **复用**：颜色、表面层级、边框、圆角、语义色、动效时长 —— 否则是「同一个产品、两副面孔」。
- **不复用**：字号、行高、行宽、间距节奏 —— 应用是**密集信息界面**（13px 正文、636px 视口塞 40+ 个数据），
  官网是**阅读界面**（17px 正文、一屏一个观点）。直接抄应用字号当正文会**读不动**。

本文只写**差异**。颜色值不重复列出，全部引用 `DESIGN-SYSTEM.md` §2 的 token 表。

## 1. 首屏

### 1.1 内容与顺序（视觉规格，文案由 `docs/site/CONTENT.md` 决定）

```
┌──────────────────────────────────────────────────────────┐
│ header:  XrayTun            [功能] [下载] [FAQ]   中文 · EN │  ← 56px 高，sticky
├──────────────────────────────────────────────────────────┤
│                                                          │
│   H1  一句话价值主张（≤ 22 个汉字 / ≤ 60 字符英文）         │  ← 40px/1.15/600
│                                                          │
│   lead  2 行补充说明（≤ 60 汉字 / ≤ 140 字符英文）          │  ← 20px/1.6/--text-dim
│                                                          │
│   [ 下载 macOS 版 (.dmg) ]   还有 .zip · 47.1 MB           │  ← CTA 行
│                                                          │
│   v0.8.26 · 仅 macOS · 通用包（arm64 + x86_64）· 44.9 MiB  │  ← 14px/--text-dim
│                                                          │
│   ┌────────────────────────────────────────────────┐     │
│   │  应用截图（拓扑页）1080 × 720 CSS px            │     │  ← 见 §4
│   └────────────────────────────────────────────────┘     │
└──────────────────────────────────────────────────────────┘
```

**首屏高度**：`min-height: 640px`（**不要用 `100vh`**）。
理由：实测常见笔记本视口高 640–800px（本机 1080×720 时应用 `.content` 可视高 **636px**）。
用 `100vh` 在 640px 高的窗口里会把截图完全挤出首屏；固定 640px 保证「H1 + lead + CTA + 截图顶部」始终可见。

**信息密度**：**首屏可见元素 ≤ 15 个**。

依据（实测对比）：应用仪表盘在同一片 636px 高的区域里渲染 **85 个可见元素**（CDP 计数，
`/tmp/xraytun-audit/probe.json`）；拓扑页 **441 个**、日志页 **558 个**。
那是密集界面的正确密度。官网首屏若照抄，读者会**找不到该看哪**。
15 个的上限大致是：header(1) + 导航项(3) + 语言(2) + H1(1) + lead(1) + 主按钮(1) + 次链接(1) + meta(1) + 截图(1) + 截图题注(1)。

### 1.2 栅格与断点

**Mobile-first，3 个断点**（应用里的 940/880/760 是临时断点，官网另立一套干净的）：

| 断点 | 目标 | 容器 `max-width` | 左右 gutter | 布局 |
|---|---|---|---|---|
| 默认 | 手机 < 640px | `100%` | `20px` | 单列；导航收成一行横向滚动（**不做汉堡菜单**，只有 3 个锚点） |
| `≥ 640px` | 大手机 / 竖屏平板 | `640px` | `32px` | 单列；导航横向展开 |
| `≥ 900px` | 平板横屏 / 小笔记本 | `960px` | `32px` | 首屏文案居中（`max-width: 640px`），截图占满容器 |
| `≥ 1200px` | 桌面 | `1120px` | `48px` | 同上；截图上限 **1080px**（= 原生宽度），两侧留白 |

```css
:root { --gutter: 20px; --container: 1120px; --measure-zh: 640px; --measure-en: 592px; }
@media (min-width: 640px)  { :root { --gutter: 32px; } }
@media (min-width: 1200px) { :root { --gutter: 48px; } }
```

**gutter 的 20px 是有依据的**：应用 `.content` 的左右内边距就是 **20px**（`styles.css:181`，
`padding: 18px 20px 32px`）。官网沿用同一个最小 gutter，视觉上与应用同源。

**为什么首屏不做两栏**（文案左 / 截图右）——**这是被截图的物理尺寸否掉的**：

- 截图里**最小的文字是 10.5px**（实测：`.highway__lane-meta` / `.highway__legend-note` 10.5px、
  `.facts__hint` 10.5px、日志页 `.log-line__src` 10.5px）。
- 缩放系数 `s` 下，这些字渲染成 `10.5 × s` px。要让 `s ≥ 0.75`（可辨认下限），
  截图显示宽度必须 `≥ 1080 × 0.75 = 810px`。
- 两栏布局在 1120px 容器里每栏只有 **~536px** → `s = 0.50` → 10.5px 的字渲染成 **5.2px**，**不可读**。

→ 所以**首屏截图必须 ≥ 810px 宽**，只能在 `≥ 900px` 断点下做**通栏单列**。
在容器不足 810px 时（手机 / 小窗），**不要缩放整窗截图**，改用**裁切细节图**（只截拓扑的扇形区域），
见 §4.4。

## 2. 阅读型排版（与应用的核心差异）

### 2.1 对照表（这是本文最重要的表）

| 角色 | **应用**（密集） | **官网**（阅读） | 倍数 | 为什么不同 |
|---|---|---|---|---|
| 正文 | `13px / 1.55` | **`17px / 1.75`** | **1.31×** | 见 §2.2 |
| 页面/区段标题 | `14px / 600` | **H2 `28px / 600`** | **2.00×** | 官网标题是「章」，应用标题是「分组标签」 |
| 主标题 | —（无此角色） | **H1 `40px / 600 / -0.02em`** | — | 应用没有 hero，只有 21px 的仪表盘状态 |
| 引导语 lead | `12px`（`page__desc`） | **`20px / 1.6 / --text-dim`** | **1.67×** | |
| 三级小字 | `10.5px` | **`13px / 1.6`** | 1.24× | 官网的地板是 13px，**不允许 10.5px** |
| **行宽** | `820px`（`.page` 固定） | **`640px` 中文 / `592px` 英文** | — | 见 §2.3 |
| 区块间距 | `24px`（`.page__sec`） | **`96px`（≥900）/ `64px`（手机）** | **4.0×** | 密集界面靠分隔线，阅读界面靠留白 |
| 段落间距 | `2px`（`.page__desc` 的 `margin-bottom`） | **`24px`** | 12× | |

### 2.2 为什么正文必须是 17px（不是应用的 13px）

1. **汉字需要更大的字号才「一样清楚」**。汉字是满格字身，笔画密度远高于拉丁字母：
   实测在 17px 下汉字前进宽度 = **恰好 17.0px（1.0em）**，而小写拉丁字母平均只有 **9.488px（0.558em）**。
   同样字号的汉字视觉权重更高，**但复杂字（覆/警/髓）在小字号下会糊** ——
   应用在 13px 下用汉字是**密集界面的必要妥协**（`styles.css:34` 的 `font: 13px/1.55`），
   在阅读界面里没有这个妥协的必要。
2. **这是一个「读一段话」而不是「扫一屏数据」的场景**。应用的 13px 服务于一份 636px 高、
   含 40+ 个数据点的界面；官网每屏只有一个观点。
3. **17px 是中文正文的舒适区下限**。低于 16px 的中文长文阅读疲劳明显。

> ⚠️ **不要**把应用 token（`--fs-md: 13px`）直接用在官网正文。
> 这是本次任务里最容易犯的错 —— 它会让官网看起来像「放大的应用界面」，而不是一个可读的网站。

### 2.3 行宽（measure）：实测支撑

在 17px 下用浏览器实测的**每行字符容量**：

| 字号 | 处宽 | 汉字/行 | 小写拉丁/行 |
|---|---|---|---|
| 17px | `640px` | **37** | **67** |
| 17px | `592px` | 34 | **62** |

- 中文最佳行宽 **25–40 字** → `640px`（37 字）**落在区间内**。✅
- 英文最佳行宽 **45–75 字符** → `640px`（67 字符）在区间上沿；`592px`（62 字符）更舒服。

→ **中文页 `max-width: 640px`；英文页 `max-width: 592px`。**

```css
:root { --measure-zh: 640px; --measure-en: 592px; }
html[lang^="zh"] .prose { max-width: var(--measure-zh); }
html[lang="en"]   .prose { max-width: var(--measure-en); }
```

**用 px 而不是 `ch`**：`ch` 单位基于 `0` 字形的宽度，汉字页里它和「汉字数」没有关系，
会给出误导性的行宽。这里直接用实测过容量的 px。

### 2.4 完整字阶（官网专用，与应用 token 并存）

| token | 值（手机 → ≥900） | 行高 | 字重 | 用途 |
|---|---|---|---|---|
| `--site-h1` | `32px → 40px` | `1.15` | 600 | 首屏主标题；`letter-spacing: -0.02em` |
| `--site-h2` | `24px → 28px` | `1.25` | 600 | 章节标题 |
| `--site-h3` | `18px → 20px` | `1.35` | 600 | 小节 / 功能卡标题 |
| `--site-lead` | `18px → 20px` | `1.6` | 400 | 引导语（`--text-dim`） |
| `--site-body` | `17px` | `1.75` | 400 | 正文 |
| `--site-small` | `14px` | `1.6` | 400 | meta、题注、按钮副行 |
| `--site-micro` | `13px` | `1.5` | 400 | 页脚、版本号（**下限**） |

**行高差异的理由**：应用的 `1.55` 服务于单行数据（行间距小才能在一屏塞更多）；
官网用 `1.75`（中文）/ `1.7`（英文）。中文行高要略大于英文 ——
汉字没有 x-height 的视觉连接，行距不足时上下行会「粘」在一起。

**字重**：只用 `400 / 600` 两档（应用用 400/500/600 三档）。
阅读界面的层级靠**字号 + 留白**表达，不靠 500 这种中间字重。

### 3.5 ⚠️ 低于 3:1 的位置（WCAG 1.4.11 非文字对比度）

| 次按钮填充 | `--surface-2` vs `--bg` | 1.19:1 | ❌ | **不修**：填充不是「识别控件所必需」——边在 3:1 已足够识别（见下） |
| 卡片轮廓 | `--border` `#263148` vs `--bg` | **1.42:1** | ❌ | **豁免**：卡片是**装饰性容器**，不承载交互，1.4.11 不适用 |

| 代码块 | `--bg-sunken` vs `--bg` | **1.05:1** | ❌ | 同上；但代码块靠**等宽字体 + 内边距**已可识别，另见下 |
| 代码块轮廓 | `--border` vs `--bg-sunken` | 1.49:1 | ❌ | 建议改 `--border-interactive`（见 §5.3） |
| 截图外框 | `--border-strong` vs `--bg` | **1.78:1** | ❌ | **豁免**：装饰性。但 1.78:1 是「能看见一条线」的最小值，**这就是选它的理由** |
| 警告块轮廓 | `--warn-border #57471f` vs `--bg` | 2.04:1 | ❌ | **豁免**：警告块的可辨识性来自**填充色差 + 左竖条 + 文字**（12.96:1），不靠外框 |

**判据说明**：WCAG 1.4.11 的原文限定是「**识别 UI 组件与状态所必需**的视觉信息」。
- **必须达标**的只有**控件轮廓**：主 CTA（`--accent` = 5.73:1 ✅）与次按钮（改后 3.15:1 ✅）。
- **卡片 / 代码块 / 截图框 / 警告块**是**内容容器**，它们的边界是排版装饰，1.4.11 不适用。
  但**必须靠别的线索可辨识** —— 卡片靠内容缩进，代码块靠等宽字体 + 内边距，警告块靠琥珀色填充。
  这些线索在下面的规范里都写明了。

### 3.6 浅色 / 深色偏好：**只做深色**（决定 + 理由 + 代价）

**决定：官网只做深色，不响应 `prefers-color-scheme`。**

依据（全部可复现）：

1. **应用本身没有浅色主题。** `grep -n 'prefers-color-scheme' apps/ui/src/styles.css` 唯一的命中是
   第 1763 行的 `.flow__highlight` **选择器名**（字符串巧合），**没有任何浅色主题规则**。
   官网出浅色版 = 官网与产品不一致。
2. **5 张营销截图全是深色**，实测主背景 `#0f1420`。把深色截图放进浅色页面，
   截图的边缘会产生 **18.40:1** 的硬边界（`#0f1420` vs `#ffffff` 实测；
   对 `#f8fafc` 是 17.59:1、对 `#f1f5f9` 是 16.80:1）。
   一屏里出现大面积 18:1 的亮度跳变，是**真正的刺眼源**。
   放进深色页面则是 **1.00–1.05:1**（`#0f1420` vs `#0f1420` / `#0b101a` / `#0a0e16`）—— 完全没有跳变。
3. **「刺眼」在深色页上的真实风险不是亮度，而是纯白文字 + 纯黑背景**
   （两者都会让眼睛持续处于高对比状态）。规范用两个措施消掉：
   - 页面底用 `--bg #0f1420`，**不用 `#000`**；
   - 正文用 `--site-text #ccd6e4`（12.54:1），**不用 `#fff`**（`#fff` 会是 17.5:1 以上）。

**代价（说清楚）**：深色页在**强光环境的 OLED/普通屏幕上**反射更明显；不响应系统偏好也意味着
一位使用浅色系统的用户会看到深色站点。**接受这个代价**，因为产品本身是深色的 ——
一致性比偏好顺从更重要。

**实现要求（深色页必须做的三件事）**：

```html
<meta name="color-scheme" content="dark">
<meta name="theme-color" content="#0f1420">
```
```css
:root { color-scheme: dark; }   /* 让原生控件、滚动条、表单渲染成深色 */
```
```css
/* 应用自绘了滚动条（styles.css:590-599, 滑块 #2a3548）—— 官网要跟上，否则是浅色亮条 */
::-webkit-scrollbar { width: 10px; }
::-webkit-scrollbar-thumb { background: #2a3548; border-radius: 5px; border: 2px solid #0f1420; }
```

**若以后要加浅色版**（现在不做）：反向的问题同样存在 —— 必须为浅色页**重做截图**
（浅色版的界面），否则就是上面第 2 条的 18:1 硬边界。所以「加浅色主题」的真实成本 =
**重出 5 张截图 + 一套浅色 token**，不是加几行 CSS。

| 项 | 规格 |
|---|---|
| 格式 | **AVIF**（主）→ **WebP**（备）→ **PNG**（回退）。`<picture>` 三段 |

### 4.4 小屏替代方案（不要缩放整窗截图）

当容器 < 810px（见 §1.2 的实测推导）时，**不要**把 2160px 的整窗图缩下去 —— 10.5px 的字会变成
5–7px 的噪点。改用**裁切细节图**：

| 图 | 裁切区域（CSS px @1x 坐标） | 出图 |
|---|---|---|
| `detail-fanout.png` | 拓扑页 `.highway` 的扇形区，约 `x=396..880, y=200..560` → 484 × 360 | 968 × 720 @2x |
| `detail-globe.png` | 地球仪球体，`.globe__canvas` = `560 × 560`（实测） | 1120 × 1120 @2x |

裁切图的**最小字号会被放大**（484px 裁切放在 360px 宽的手机容器里，`s = 0.74` —— 与整窗图
在 810px 时的可读性相同），所以细节图在手机上**比整窗图更清楚**。

### 5.1 真实资产（`gh release view v0.8.26` 实测，`isDraft: false`）

### 5.2 三级层级

| 级别 | 元素 | 视觉规格 | 对比度 |
|---|---|---|---|
| **1 主** | `下载 macOS 版 (.dmg)` | 填充 `--accent`；文字 `--on-accent` 600 / 17px；高 **48px**；圆角 `--radius` 6px；`padding: 0 28px` | **5.94:1 ✅** |

**布局**：主按钮与次按钮**同排**（`gap: 16px`），SHA256 链接单独一行在下方（`margin-top: 12px`）。

**为什么要三级而不是「两个大按钮」**：`.dmg` 与 `.zip` 是**同一个东西的两种封装**
（都含 arm64 + x86_64，实测文件名里都有 `x86_64_arm64`）。
给它们同等视觉权重会让用户以为要选。

**按钮不要写死宽度**：中文标签短、英文长（实测 `断开` 34px → `Disconnect` 86.1px，**2.53×**，见 §6.1），
写死宽度会让英文按钮文字溢出。用 `padding` 决定宽度 + `white-space: nowrap`。

### 6.1 英文比中文长多少（**实测**，不是估计）

| 断开 | 34.0px | Disconnect | 86.1px | **2.53×** |
| 测试延迟 | 68.0px | Test latency | 91.5px | 1.35× |
| 添加订阅 | 68.0px | Add subscription | 128.8px | 1.89× |
| 分流预设 | 68.0px | Routing presets | 119.6px | 1.76× |
| 自定义规则 | 85.0px | Custom rules | 100.7px | 1.18× |
| **地球仪** | 51.0px | **Globe** | **45.0px** | **0.88×（更短！）** |

**结论（用实测数字说话）**：

- **短标签最危险**：`断开 → Disconnect` 是 **2.53×**。按中文长度定宽的按钮，英文会溢出。
- **长行的膨胀只有 ~1.35×**（最后一行），因为长文案里数字、空格、标点占比高。
- **英文不一定更长**：`地球仪 → Globe` 反而**短 12%**。
- 9 个 UI 标签的**平均膨胀 = 1.64×**（2.53+1.35+1.89+1.76+1.18+0.88+1.47+2.22+1.52 = 14.80 / 9）。

**底层字宽（17px 实测）—— 这解释了为什么**：

| 字形 | 前进宽度 | 相对字号 |
|---|---|---|
| 汉字 | **17.000px** | **1.000 em**（满格） |
| 小写拉丁 | 9.488px | 0.558 em |
| 大写拉丁 | 12.186px | 0.717 em |
| 数字 | 10.277px | 0.605 em |
| 空格 | 4.350px | 0.256 em |

**同一像素宽度能装的小写拉丁字符数是汉字的 1.79 倍**（17.000 / 9.488）。
所以「英文更长」在**字符数**上成立（约 2×），在**像素宽度**上只膨胀 1.35–1.65×。

### 6.2 排版规则

| 项 | 中文页（`/`） | 英文页（`/en/`） |
|---|---|---|
| `<html lang>` | `zh-CN` | `en` |
| 正文处宽 | `--measure-zh` **640px**（37 汉字/行，实测） | `--measure-en` **592px**（62 字符/行，实测） |
| 正文字号 / 行高 | `17px / 1.75` | `17px / 1.70` |
| 断行 | `line-break: strict; overflow-wrap: break-word` | `hyphens: auto`（**标题上禁用**） |
| 两端对齐 | **禁用** `text-align: justify` | 同左 |

**理由**：
- 中文行高略大于英文（1.75 vs 1.70）：汉字没有 x-height，行距不足时上下行会「粘」。
- **中文禁用 `justify`**：中文没有词间空格，`justify` 只能拉伸字间距（`letter-spacing`），
  会造成「稀疏/密集」交替的难看效果。这条在中文页尤其重要。
- **英文 `hyphens: auto` 依赖 `lang="en"`** —— 浏览器只在该语言有断词词典时才生效。
  因此 `lang` 属性**不是可选的**（同时影响屏幕阅读器发音）。
- `word-break: break-all` **禁止使用**（会违反中文标点避头尾规则）。

### 6.3 字体栈（**必须与应用不同**）

应用用的栈是 `-apple-system, BlinkMacSystemFont, "SF Pro Text", "Helvetica Neue", sans-serif`
（`styles.css:34`）。这在 macOS 上没问题 —— `-apple-system` 会回退到 **PingFang SC** 渲染汉字。

**但官网上不行**：访问者可能是 Windows / Linux / Android。
`-apple-system` 和 `BlinkMacSystemFont` 在这些系统上**都不解析**，会一路掉到 `sans-serif`，
汉字将用系统默认字体渲染 —— 在部分 Linux 发行版上会出现**明显不同的字形和字重**，
与截图里的 macOS 渲染对不上。

```css
--font-site: -apple-system, BlinkMacSystemFont, "SF Pro Text", "Segoe UI", Roboto,
             "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", "Noto Sans CJK SC",
             sans-serif;
--mono: ui-monospace, SFMono-Regular, "SF Mono", Menlo, Consolas, monospace;
```

新增的三段（应用里没有）：
- `"Segoe UI", Roboto` —— Windows / Android 的拉丁字形
- `"PingFang SC", "Hiragino Sans GB"` —— macOS / iOS 汉字（显式声明，不依赖 `-apple-system` 的隐式回退）
- `"Microsoft YaHei", "Noto Sans CJK SC"` —— Windows / Linux 汉字

> 这一条**没有实测支撑**（我只能在 macOS 上量）—— 诚实标注。
> 依据是 CSS 字体回退规则：非 macOS 系统上 `-apple-system` 不是有效 family name。

### 6.4 语言切换器

```
header 右侧：   功能   下载   FAQ   │   中文 · EN
```

| 项 | 规格 |
|---|---|
| 位置 | header 最右，与导航之间用 `1px --border-strong` 竖线分隔 |
| 形态 | **两个普通链接**（`中文` / `EN`），**不用下拉菜单** |
| 当前语言 | `--text` / 600 / `aria-current="page"` |
| 另一语言 | `--text-dim` / 400 + 下划线（hover 时 `--text`） |
| 分隔符 | `·`（`--border-strong` 色，`margin: 0 8px`） |
| 最小点击区 | **44 × 44px**（WCAG 2.5.5 Target Size） |
| 链接属性 | `<a href="/en/" hreflang="en" lang="en">EN</a>` |

**为什么不用下拉**：只有 2 个选项。下拉会把「另一语言」藏起来，而双语站的**首要任务**
就是让说另一种语言的用户**一眼看到切换入口**。同时下拉依赖 JS，而官网要求无 JS 可用。

**URL 策略**是 `interaction-designer` 的范围（`docs/site/INTERACTION.md`），
但视觉上必须**假设** `/`（zh）与 `/en/`（en）是两个真实路径 ——
切换器的 `href` 是绝对路径 `href="/en/"`，且**在子路径部署下要改成相对路径**
（Pages 站点形如 `https://harodggg.github.io/xrayTun/`，见 task-20 的注意项）。
