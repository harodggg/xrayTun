# `scripts/net-metrics.py`：把「改前 / 改后」的三组数字固化成一条只读命令（task-101 / task-103 / 口径头 v2）

> 为什么要有它：`task-97`（v6 改写）与 `task-98`（看门狗判据）都会在 **v0.8.34** 上到用户机器，
> 而「修好没修好」此前只能靠**临时 Python 片段** —— 那东西只活在某个人的会话里。
> 本项目栽过「不可复制的现场只存在于临时目录 = 等于不存在」，也栽过「CSS 规则数的口径不对」。
> 所以：**口径写进脚本 + 口径头打在每个输出开头 + 自测钉死期望值 + 敏感性**。
>
> `task-103` 修了一个会让它**静默丢数据**的缺陷（见 §4）—— 那类工具比没有更糟。

## 0. 口径头 v2 改了什么（以及**为什么**只改这些）

| # | 改动 | 为什么 |
|---|---|---|
| 1 | 输出开头加**口径头**（六行：⓪身份/移动标记 ①切 ②解 ③匹配 ④单位 ⑤**选择内容指纹**） | 「引用数字却不引口径」是本项目反复栽的错；口径头把四个自由度 + 指纹一次说完 |
| 2 | 新增**选择内容指纹**（sha256，**分帧安全**） | 「我量的和你量的，是不是**同一堆记录**」此前无法回答 |
| 3 | **`message 含 LF 的记录数`** 行内上报（本机现测 **0**） | 写入侧的安全（`AppState::log` 转义 LF）是**前提**；把前提变成**被监控的量** |
| 4 | 「丢弃重复」拆成 **全文件扫描口径** 与 **落在本窗口内** 两个数 | 原来只有一个数 ⇒ 读者会把它当成窗口内的数 |

**这之后指纹协议在本轮冻结**：不再引入新的身份/哈希维度。目标是「能回答『修好没有』」，不是造密码学身份系统。

## 1. 用法

```bash
python3 scripts/net-metrics.py                       # 默认定位 macOS 应用日志目录；全部记录
python3 scripts/net-metrics.py --since 00:00         # 只算今天
python3 scripts/net-metrics.py --until 14:21:32      # **固定窗口右端 ⇒ 数字可复现**
python3 scripts/net-metrics.py --json                # 机器可比对（含口径头字段）
python3 scripts/net-metrics.py --export /tmp/sel.blob  # 证据子集 = 被指纹的字节
python3 scripts/net-metrics.py --self-test           # 自测（只写 /tmp，不联网）
```

**引用规则（硬）**：任何数字都要连 **口径头** 一起引用；同一个命令在不同时刻会给出不同数字（日志在追加）
⇒ 可复现的前提是**钉住 `--until`**。

只读：**不修改/移动/删除日志**，不联网，不跑 cargo，不碰 `site/**`、`scripts/check.sh`、`scripts/diagnose-network-drop.sh`。

### 2.1 哪些行是**窗口口径**、哪些是**全文件口径**（这一条必须看明白）

| 行 | 口径 | 会不会随时间移动 |
|---|---|---|
| N（命中条数）、③ 的「丢弃重复/窗口内丢弃/命中」、⑤ 指纹、① 窗口 | **窗口**（受 `--since/--until` 限制） | **钉住 `--until` 后不动** |
| ② 整行（读了多少行/对象/坏行）、③ 的「全文件扫描」那个数、⓪ 的文件大小/mtime | **全文件物理扫描** | **会动**（日志在长大） |

## 3. 选择内容指纹（本轮新增，之后冻结）

### 3.1 口径（与脚本里的实现逐字一致）

```
body = "<ts_unix>|<message>"                    ← **不含 source**
帧   = "<body 的 UTF-8 字节数>" + ":" + body + "\n"
选择内容指纹 = sha256( 按 (ts_unix, message) 排序后，逐条帧拼接 的 UTF-8 字节 )
```

* **为什么不直接拼 `<ts>|<msg>\n`**：那样**不是单射** —— 一条 message 含真实 LF 的记录
  `"C1\n3001|C2"` 与两条记录 `"C1"` / `"C2"`（ts 分别为 3000 / 3001）会拼出**完全相同的字节串**。
  把长度写进帧之后，「记录边界」不再依赖 message 的内容。
* **排序也是口径的一部分**：按 `(ts, msg)` 排 ⇒ 与文件顺序、与去重时「谁先见」都无关，同一选择集**必然**同指纹。

### 3.2 ⚠️ 它是「**选择集**指纹」，**不是日志文件指纹**

只覆盖「本次选中的记录」（窗口 + 去重之后）。日志在被追加 ⇒ **同一条命令在不同时刻给出不同指纹**，
除非同时钉住 `--until`；文件里**没被选中**的行、文件的字节布局、轮转出的 `app.1.jsonl` 都不在它的覆盖范围内。
**想要「文件指纹」是另一件事，本脚本不提供、也不假装提供。**

### 3.3 `--export`：让**不用 Python 的人**也能复算

```bash
$ python3 scripts/net-metrics.py --until 14:21:32 --export /tmp/selection-until-1421.blob
证据子集已导出：/tmp/selection-until-1421.blob（48289413 字节；内容 = 被指纹的那串字节）
  自校验：`shasum -a 256 /tmp/selection-until-1421.blob` 的第一个字段应当等于 3e7c0c61…ec5b3cb
$ shasum -a 256 /tmp/selection-until-1421.blob
3e7c0c61ef53e6d4fbb1a2f7a89c6e6fa8e43bc188fcfd53a7df14795ec5b3cb  /tmp/selection-until-1421.blob
```
⇒ 指纹**不是**「只有本脚本能算的黑盒」。导出的是**被指纹的字节本身**；原始日志**只读**，不被改动。

### 3.4 六个期望值（`--self-test` 里写死；**每个错误口径只偏一个自由度**）

| 夹具 | 钉住的自由度 | 期望值（sha256） |
|---|---|---|
| **A 正确** | 键 `(ts,msg)`、串 `ts\|msg`、分帧 | `fb823743341ac392f201f700e078604c06741c2821d076919e2bc76895566f4a` |
| **A 错误** | **仅**「帧里的串改成含 `src`」（键与排序不变） | `4119d46d0c291d3459df2da7ebeaf5b7aaa375fa26c3538a4377375e177ff484` |
| **B 正确** | 键 `(ts,msg)`、串 `ts\|msg`、分帧 | `f1648152cbbe8db8ed94452ca6a63ecea4d518682868e132a7550064e5678b79` |
| **B 错误** | **仅**「去重键改成 `(ts,src,msg)`」（串与排序不变） | `46c953690bb58b122163786a7681cbe72bed0ff10084cecd4e596fec941884b6` |
| **C 一条** | 一条 message **含真实 LF** | `72d7b49ebbc8d725bdf31e0f56ca9c0037bb15a92e201ccdb57bf698cf20d3d1` |
| **C 两条** | 两条记录（分帧后必须 ≠ 上一条） | `9e36ab5bc974241444d282109127d0a75f33efa29a4c24a6fc1b1e9f1cf88dfe` |

* 夹具 A 内部**没有**「同 `(ts,msg)` 不同 `src`」的重复 ⇒ 它对**去重键**不敏感（自测里也断言了这一点）；
* 夹具 B **故意**含这么一对 ⇒ 换键就换选择集（正确口径 3→2 条，错误口径 3→3 条）；
* 夹具 C 是**碰撞反例**：**朴素拼接**下「一条含 LF」与「两条记录」的字节串**逐字节相同**，
  分帧后不再相同。

**六个值我用 `shasum -a 256` 在 Python 之外复算过**（不依赖本脚本的哈希实现）：

```bash
printf '7:1000|A1\n7:1001|A2\n7:1002|A3\n'                    | shasum -a 256   # → fb823743…
printf '11:1000|app|A1\n12:1001|core|A2\n11:1002|app|A3\n'    | shasum -a 256   # → 4119d46d…
printf '10:2000|B-dup\n11:2001|B-uniq\n'                      | shasum -a 256   # → f1648152…
printf '10:2000|B-dup\n10:2000|B-dup\n11:2001|B-uniq\n'       | shasum -a 256   # → 46c95369…
printf '15:3000|C1\n3001|C2\n'                                | shasum -a 256   # → 72d7b49e…
printf '7:3000|C1\n7:3001|C2\n'                               | shasum -a 256   # → 9e36ab5b…
```

> **⚠️ 这条也说明为什么标签必须写死偏差维度**：我第一次在 bash 里复算「夹具B 错误」时，**顺手把 `src` 也加进了串**，
> 于是算出一个对不上脚本的值（`bb420e54…`），差点把「代码错了」记成结论 —— 实际是我**叠了两个自由度**。
> 这正是 backend-dev 同一天算错两个值的方式。

### 3.5 一个**必须诚实说**的现状

本机 2026-09-22 的日志里 **`message 含 LF` 的记录 = 0** ⇒ **今天两种口径（分帧 / 朴素）的指纹恰好一致**。
分帧安全**现在没有可观测的差异**；它的价值是：① 把「写入侧已转义」这个**前提**变成**被监控的量**；
② 将来真出现 LF（写入侧回归、或读到别处生成的文件）时，指纹**不会**把两条记录当成一条。

## 4. ⚠️ task-103 修掉的缺陷：**一行可能含两个 JSON 对象**（旧版整行丢掉）

日志里存在**一行装两个对象**的行（2026-09-22 实测 **4 行**），形状是 `…}{…`（中间没有换行）：

```
{"ts_unix":1790051357,"source":"app",…"隧道已自动恢复（第 1 次自动重建）"}{"ts_unix":1790051357,"source":"core",…"Xray 26.9.9 (…)"}
{"ts_unix":1790054534,"source":"core",…}{"ts_unix":1790054534,"source":"app",…"隧道已自动恢复（第 1 次自动重建）"}
{"ts_unix":1790054858,"source":"core",…}{"ts_unix":1790054858,"source":"app",…"隧道已自动恢复（第 1 次自动重建）"}
```

（第 1 行在 `app.1.jsonl` 里也有一份跨代副本 ⇒ 4 行、其中 3 条**互不相同**的 `隧道已自动恢复`。）

**旧实现（`json.loads(line)`）对这类行必然抛异常 ⇒ 整行被当成「坏行」丢掉**，后果：
**「隧道已自动恢复」被漏算成 0 行**（实际 3 次），`source=app` 也少算。
⇒ 已改成 `json.JSONDecoder().raw_decode` 循环解析到行尾（**一行 N 个对象全部计入**）。

「坏行」不再混成一个数，拆成四类打印：

| 类别 | 含义 | 实测量（本时点） |
|---|---|---|
| **多对象行** | 一行 >1 个 JSON 对象 | **4 行**（多解析出 4 个对象） |
| 截断·残缺行 | 解析中途失败（尾部坏） | **0** |
| 非 JSON 行 | 既非空行也非以 `{` 开头 | **0** |
| 空行 | 只有换行/空白（**不是坏行**） | **3** |

> **这类行为什么会出现**：产品侧根因见 **task-104**（backend-dev，写侧已修）；本脚本只负责**不再丢它们**。
> 脚本对**任意多个**对象都成立（循环解析），但**观测到的最多就是 2 个**。

### 4.1 我独立量到的**读侧残留**（对应 `task-107`，写侧修完 ≠ 读侧不会丢）

`Store::tail_logs`（`crates/xt-core/src/store.rs:228-249`）是**逐行** `serde_json::from_str::<T>(l).ok()`
⇒ 一行两个对象时，整行解析失败被 `.ok()` 吞成 `None`，**两条记录一起丢**。我用 `raw_decode` 循环独立复算：

```
app.1.jsonl: 行=140119  空行=1  多对象行=1  对象=140119  读侧会丢的记录=1
app.jsonl  : 行=246010  空行=2  多对象行=3  对象=246011  读侧会丢的记录=3
合计       : 行=386129  空行=3  多对象行=4  对象=386130  读侧会丢的记录=4
恒等式 对象 == 行 - 空行 + 多对象行多出的对象数: 386130 == 386130 -> True
```

**关键结论**：**3 条互不相同的「隧道已自动恢复」全部落在多对象行上**（`ts_unix` 1790051357 / 1790054534 / 1790054858
= 12:29:17 / 13:22:14 / 13:27:38）⇒ 旧版**界面上当时也看不到这 3 次自愈**。
「全天零恢复」这个错觉在**界面**与**取证报告**里**同时**出现，两边都靠**原始文本 grep** 才发现。

## 5. 三组指标各自回答什么

| 组 | 回答的问题 | 关键口径 |
|---|---|---|
| **① task-97** | 「v6 改写」与「连接失败」的**相关性**：按 session id 归并连接 → 全是 v6 / 全是 v4 / v6+v4 三类，各给条数、`failed to open connection` 条数与百分比；另给两行行级计数 | 一律**按行内 session id `[…]` 归并**；`replace destination with tcp:[…]` 判 v6、`…tcp:<v4>` 判 v4 |
| **② 探针** | 探针判据可靠吗：连接数 / 成功 / **失败·有 `failed` 行** / **失败·无结局行**（按目标拆）、轮数、成功耗时 中位/p90/p95/p99/max、**>6s 才成功的条数** | 连接 = `proxy/socks: TCP Connect request to tcp:<目标>`；分轮 = 相邻间隔 **>5s**；耗时才用**消息内微秒时间戳** |
| **③ 自愈** | 误判的**代价**：`已作废` / `物理出口已变化` / `隧道已自动恢复` 逐条时间，以及两种空档口径 | **口径A** = 作废 → 下次 core 启动；**口径B** = 最后一条流量证据 → 下一条流量证据（task-95 口径） |

**去重（必须）**：按 `(ts_unix, message)` 去重，先见者胜，跨文件顺序 `app.1.jsonl` → `app.jsonl`。
**为什么必须**：`trim_log_file`（`crates/xt-core/src/store.rs:372-398`）轮转时先 `rename` **整份**活动文件成
`app.1.jsonl`，再把保留的**尾部**写进新的 `app.jsonl` ⇒ **同一段记录同时存在于两代文件里**，
跨代读取必然重复。（该函数的注释写的是「**不做**『保留整份 + 复制尾部』」，与实现相反 —— 见 `task-105`。）
实测本窗口：丢弃重复 **39,936** 条，**全部落在这个窗口内**；因此去重不是「多余防御」。

## 9. 诚实清单：这个脚本**测不到**什么

1. **不做因果**：① 只给相关性。「v6 改写导致了用户的失败」不在这里证。
2. **探针失败 ≠ 用户当时上不了网**：只证明「这一个 URL 经 SOCKS 的这一次请求没成」。
3. **看不到应用侧超时**：探针 6s 超时**不落盘** ⇒ 只能用「>6s 才成功」的条数**间接**量化误杀。
4. **`app.jsonl` 不是完整应用日志**：`push_log()` 只进内存环形缓冲（`state.rs:319`），
   只有 `state.log()`（`state.rs:386`）落盘 ⇒ 看门狗过程行**不在文件里**。
5. **多对象行的上限未知**：脚本支持任意多个对象，但**观测到的最多 2 个**；会不会出现 3 个以上，**现有日志回答不了**。
6. **真机行为不可见**：安装/更新/重装 helper、Gatekeeper、UI 表现。
7. **依赖日志格式**：session id 形状、`replace destination` 文案、`source` 取值变化都会让指标失真；
   `--self-test` 只证明**逻辑**对，不能证明**格式**没变。
8. **口径A/口径B 不是同一件事**（今天差 ~5–8s），引用时必须写明用哪个。
9. **② 那一行是「全文件扫描」口径**（读了多少行/对象/坏行），**会随时间移动**；
   与 N/③/⑤ 的窗口口径**不是一回事**。
10. **指纹不是文件指纹**（§3.2）：它只说明「两次报告选中的是不是同一堆记录」；
    同一窗口在不同时刻**应当**给出相同指纹（已实测两次一致），但**文件本身**一直在变。
11. **分帧安全今天没有可观测差异**（§3.5）：实测 message 含 LF 的记录 = 0 ⇒ 两种口径的指纹恰好一致；
    它的作用是**把前提变成被监控的量**。
12. **读侧仍会静默丢**（§4.1）：本脚本用 `raw_decode` 看见了那 4 行，但**产品自己的 `tail_logs` 仍然逐行**
    ⇒ 界面上的日志与文件里的日志**可能不一致**（`task-107`）。
13. **`--export` 写出的是「被指纹的字节」而非原始日志行**：它是**子集 + 规范化**，
    不能当证据原件用（原件永远在 `~/Library/Application Support/com.xraytun.desktop/logs/`，只读）。
