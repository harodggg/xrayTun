It won't open — what to do

This page is for the case where the app does not start at all — the one case where the app's own UI cannot help you. Do these three things in order: confirm it crashed → find panic.log → send it to us. And the last point matters just as much: do not change your system DNS or routes to troubleshoot.

If instead you see a dialog saying Apple cannot check the app for malicious software, that is not a crash — that is Gatekeeper. The ways to allow it are in the install section of the home page (pick one by macOS version).

1. First: is it a crash, or Gatekeeper?

  • Blocked by Gatekeeper: you get a dialog about an unverified developer. The app never actually ran — allow it as described in the home page's install section.
  • A crash: no dialog at all, or the icon bounces once in the Dock and disappears; the process never survives a second or two. macOS leaves a crash report behind.

User-level crash reports live here (* is a timestamp):

~/Library/Logs/DiagnosticReports/xraytun-desktop-*.ips

Paste that path into Finder → Go → Go to Folder (the ~ expands to your home directory), or open Console.app and pick “Crash Reports” in the sidebar. Two things in the report are the actual evidence of a crash:

  • "abort() called" (inside the report's asi field)
  • Abort trap: 6 / SIGABRT

If the report has no symbols and no location — only __pthread_kill → pthread_kill → abort — that is expected: release builds are stripped. The location is in panic.log, below.

2. Find panic.log (the important one)

When XrayTun crashes it writes “file:line + reason + backtrace” to a file. The default path is: 

~/Library/Application Support/com.xraytun.desktop/logs/panic.log

The quickest way to open it is to paste this into Terminal:

open -R ~/Library/Application\ Support/com.xraytun.desktop/logs/panic.log

Its first line carries the location, in this shape:

[unix=…] PANIC apps/desktop/src/lib.rs:178:17
<why it panicked>
backtrace:
…

The default path may be overridden by XRAYTUN_DATA_DIR. If that environment variable was set for the app (by you or by a script), the whole data directory moves and the log lands under $XRAYTUN_DATA_DIR/logs/ — the default path will be empty.

So “the default path is empty” does not mean “no log was written”. Check the variable, then let the system search:

echo "$XRAYTUN_DATA_DIR"
find ~ -name panic.log 2>/dev/null

If neither turns up anything, the crash happened before the logging hook was installed (e.g. in an older version). In that case the system crash report above is all there is — it has no symbols, but it still shows that it crashed in abort. Send us whichever of the two you have.

3. Send it to us

Open an issue: github.com/harodggg/xrayTun/issues/new

These four things are enough to locate the vast majority of “won't start” cases:

  • the first few lines of panic.log (the PANIC file:line line plus the backtrace; if the file is huge, the first 30 lines are fine)
  • the part of the *.ips crash report containing abort() called
  • your macOS version and your chip (Intel / Apple silicon)
  • how you started it: double-click, or a command line — if a command line, paste the command

Have a look before you paste. Logs and crash reports can contain your node hostnames, subscription URLs or configuration fragments — delete any line you would rather not publish; it does not hurt the diagnosis.

4. Do not change your system DNS or routes to troubleshoot

Three reasons, all about not disturbing the scene:

  • The process that failed to start changed nothing about your network. It never finished starting; taking over routes / changing DNS only happens once the app is actually running. So your network configuration is almost certainly unrelated to this crash, and changing it will not make the app start.
  • The app only rolls back its own changes. Every network change it makes is first written to a snapshot and rolled back on exit or crash. Your manual networksetup / route edits are in no snapshot, so they are never restored automatically — you can end up offline.
  • It makes diagnosis harder. Whoever reads the log next cannot tell “a bug in the app” apart from “something changed while troubleshooting”, so we may have to ask you to undo it first.

The right order is: change nothing → send us the two logs above → we will give you reversible commands when we need them (the kind that record the old value first and can be put back).

If you already changed something: stop adding changes, and write down what you changed (the command and which network service it affected) in the issue — we will restore the original values together.

5. While you are here: the other logs

  • startup.log: the same logs/ directory as panic.log. It records a readable reason for a failed startup (overwritten each time, so it only keeps the latest one).
  • The app's own “Logs” page: if the app does start, the sidebar's Logs page shows runtime logs, and it also tells you where panic.log is.
