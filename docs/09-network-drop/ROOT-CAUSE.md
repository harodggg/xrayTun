# 为什么「连着应用整机断网、断开就恢复、国外正常国内必现」

> **状态**：根因已用**代码证据**定位。基于 Lead 对源码的直接阅读（行号可核对）。
> **尚未在用户机器上验证** —— 需要的现场证据见文末「怎么证实/证伪」。

## 一、用户症状（原话）

* 「**断开或退出应用后网络就恢复了**」
* 「**国外可以，国内直接断掉**」

即：连接状态下**整台 Mac 断网**（所有应用）；一断开/退出即恢复；国外正常，国内必现。

这不是「代理失效」，而是**默认路由被接管后流量进了黑洞**，且**所有自动兜底都误判为"已恢复"**。

## 二、根因：两道门禁都只验证「TCP 可达」，从不验证「代理真的能走通」

接管默认路由之前共有两道检查，**没有一道端到端**：

| 位置 | 实际验证 | **验证不了** |
|---|---|---|
| `crates/xt-core/src/xray/process.rs:203` `wait_for_port` | `TcpStream::connect(127.0.0.1:port)` —— 只证明**本机 SOCKS 端口在监听** | 代理链路是否可用 |
| `apps/desktop/src/supervisor.rs:95` `tcp_reachable` | **直连 TCP 三次握手**到节点 `IP:port` | **代理协议握手是否被墙** |

流程（`apps/desktop/src/supervisor.rs`）：

```
第 5 步 :297  wait_for_port(socks_port)        ← 只证明端口在监听
第 6 步 :316  tcp_reachable(server) [接管前]    ← 只证明 TCP 可连
        :319  CommitRoutes                    ← 接管默认路由（有副作用的临界点）
        :337  tcp_reachable(server) [接管后]    ← 只用来发现路由环
```

**在国内，「TCP 到 443 能连上、但 REALITY/TLS 握手被墙」是常态** ——
GFW 的干扰通常发生在握手阶段，TCP 层完全正常。于是：
两道检查全过 → 接管默认路由 → 实际什么都过不去 → **整机断网**。

**这也直接解释「国外可以」**：国外两种检查都真通，隧道真的能用。

## 三、为什么所有自动兜底都救不回来

项目里有三处本应救场的机制，**每一处都被同一个盲点骗过**。

### 3.1 连接后的一次性检查：只报警，不回滚

`apps/desktop/src/commands/core.rs:593` 用 `tunnel_probe`（**经本地 SOCKS 发真实请求**，
`core.rs:342`）做了一次端到端检查 —— 它**能**发现「连上了但流量出不去」。

但失败分支（`:598-629`）只做两件事：
1. 写日志 + 提示「节点『X』已连接，但流量出不去（经它访问目标超时）。请换一个节点。」；
2. **若有** `last_good_node` 就切回去。

**它从不回滚隧道。** 而国内用户常常**没有** `last_good_node`
（首次连接、或唯一可用节点、或上一个节点也没验证通过）——
于是 `fallback == None`，代码只是提示一句，**默认路由仍然被接管，用户继续断网。**

### 3.2 看门狗的「重建成功」判据，用的是同一套弱检查

`core.rs:509-511`：

```rust
if stop_core(&handle, &state).await.is_ok()
    && start_core(&handle, &state).await.is_ok()
{
    // ← 这里认为「已恢复」
    state.log(..., "隧道已自动恢复（第 {attempt} 次自动重建）");
    return;   // ← :525 直接返回，本轮结束
}
```

而 `start_core` 的成功判据正是第 2 节那两道弱检查 —— **在国内它们会再次"通过"**。

所以被墙环境下：
* 重建"成功" → 记一句「隧道已自动恢复」→ `start_core` 又**重新接管了一次默认路由**；
* 但流量仍然是黑洞 → 新看门狗 10 秒后又探测失败 → 再重建 → 再"成功"……

**形成"重建成功但从未恢复"的循环**，而 `fell_back_to_direct` 那一支
（`:528-543`，本意是「能上网但不走代理总好过什么都上不了」）**永远走不到** ——
因为它只在 `start_core` **返回 Err** 时才执行。

### 3.3 用户唯一的出路：手动断开

手动断开走 `stop_core` → `Supervisor::stop` → `rollback_tun_inner` →
`TunDown { session_id }`，**真的把路由与 DNS 回滚了**，于是网络立刻恢复。

**这正是用户说「断开或退出应用后网络就恢复了」的原因**：
它是整条链里**唯一**一条确定会回滚的路径。

## 四、一句话总结

> 门禁只问「服务器能不能连上」，而不是「代理能不能用」；
> 于是国内环境下**路由被交了出去、流量却过不去**；
> 而所有兜底（一次性检查、看门狗重建）**都复用了同一套弱判据**，
> 因此它们一致地认为"一切正常"，把用户永久留在断网状态 —— 直到他手动断开。

## 五、修法方向（需评审，尚未实施）

按**收益/风险**排序：

1. **【治本】接管默认路由之前做端到端验证**
   在 `CommitRoutes`（`supervisor.rs:319`）**之前**，复用已有的 `tunnel_probe`
   （经本机 SOCKS 发一个真实请求；此时核心已在跑、SOCKS 已监听，节点流量走 bypass host 路由，
   不依赖默认路由被接管）。
   **不通过就不接管**，并明确报「当前节点在国内不可用」，让最坏情况退化为
   **「连不上代理」而不是「整机断网」**。

2. **【安全网】`start_core` 成功后补一次端到端复检，失败即回滚**
   把 3.1 的「只报警不回滚」改成：**没有可用 fallback 节点时，回滚隧道并退回直连**。

3. **【修看门狗】重建的"成功"必须用端到端判据**
   把 `core.rs:509-511` 的 `start_core().is_ok()` 换成
   「`start_core` 成功 **且** `tunnel_probe` 通过」；否则视为重建失败，
   从而**真正走到退回直连**那一支。

4. **【可观测性】让"我已接管但流量不通"在界面上可见**
   当前用户看到的是「已连接」，于是他会去查路由器而不是先断开应用。

## 六、怎么证实 / 证伪（用户机器上的现场证据）

`scripts/diagnose-network-drop.sh`（本仓库，只读、脱敏、断网可用）会一次跑完这些对照：

* **8.1** 本机 SOCKS 是否在监听；
* **8.2** 直连对照（走物理口）vs 默认路由对照 —— 区分「整机断网」与「代理不通」；
* **8.3** 节点 `address:port` 的 **TCP 三次握手**（不经代理）；
* **8.4** **经本机 SOCKS 的真实请求**（同一目标）；
* **8.5** DNS 对照。

**判读**：

| TCP 握手 | 经 SOCKS | 直连 | 结论 |
|---|---|---|---|
| 通 | **失败** | 正常 | **本文件描述的根因**（TCP 通但协议被墙） |
| 通 | 失败 | **也失败** | 整机断网（默认路由已接管且黑洞） |
| 通 | 通 | 正常 | 代理正常，问题在别处 |

**证伪本结论的方式**：若在断网时 8.3 也失败（TCP 不通），
则根因不是「协议被墙」，而是节点 IP 在国内不可达 —— 那时
`tcp_reachable` 本应拦住，需要另查它为何没拦住。

## 七、诚实清单

* 本文件全部基于**源码阅读**；**未在用户机器上复现**，因此未验证
  「GFW 确实只干扰握手而不干扰 TCP」这一前提（该前提是**公开的普遍现象**，但本机无法验证）。
* 未测量「从接管到看门狗判定失败」的真实秒数（`tunnel_probe` 单次超时 6s、
  间隔 10s、阈值 2 次 → 理论 ≥ 约 32s，**未实测**）。
* `DEFAULT_PROBE_URL = http://cp.cloudflare.com/generate_204`
  （`crates/xt-core/src/xray/probe.rs:46`）—— 该目标在国内经隧道是否稳定**未验证**；
  若它本身不稳，会造成**误判重建**（与本根因是不同的问题，但会互相掩盖）。
* 未验证「`tunnel_probe` 在 `CommitRoutes` 之前能否正常工作」
  （理论上不依赖默认路由，但**未经实测**）—— 修法 1 的可行性依赖这一点。
