# 长期现场（**机器状态**类）：现在还开着、且**不随发版自愈**的发现

> 用途：把「**机器上留下的状态**」与「**代码里的缺陷**」分开记。前者不会因为装上新版就好，
> 而代码缺陷修完就消失。**不记下来就会随时间丢失**（本项目栽过：「现场只存在于某人的会话里」）。
>
> 复现方式统一是**只读**的：`./scripts/incident-bundle.sh` + `python3 scripts/triage-incident.py`。

## F-1（开放）：`127/8` 的回环路由被指进隧道 —— `route -n get 127.0.0.2` → `interface: utun6`

| 时点 | 采集 | 判读 | 原始证据 |
|---|---|---|---|
| 2026-09-22 19:08（本地） | `INC-20260922-190335-23f5` | `interface: utun6` | 本目录该 INC 的 `evidence/loopback-route.txt` |
| 2026-09-23 10:43（本地） | 复采（`inc-fresh.zip`） | **仍然 `interface: utun6`** | 见下 |
| 2026-09-23 10:45（本地） | 复采（`inc-hostroutes.zip`，带 HOST 路由） | **仍然 `interface: utun6`** | 见下 |

```
$ route -n get 127.0.0.2
   route to: 127.0.0.2
destination: default
       mask: 128.0.0.0
    gateway: 192.168.0.1
  interface: en0            ← 2026-09-22 早上（未连接时）
  interface: utun6          ← 2026-09-22 19:08、2026-09-23 10:43 与 10:45（TUN 在跑时）
```

**判据**（`triage-incident.py` 的 `loopback-hole`）：`interface ≠ lo0` 或路由不存在 ⇒ 命中。
健康形态是 `127.0.0.0/8 → lo0`（内核自带、on-link）。

**为什么至今还在**：用户机器**没有重启**；`task-85` 修的是「**今后不再产生**」这种空洞，
**已被旧版弄坏的机器不会自愈**（`task-88` 是给它做一个用户可点的修复入口，属另一张卡）。
**它不在本轮（v0.8.35）的修复范围内。**

**复现命令**（只读）：
```bash
route -n get 127.0.0.2
netstat -rn -f inet | grep -E '^127'
./scripts/incident-bundle.sh --out /tmp/x.zip && python3 scripts/triage-incident.py --bundle /tmp/x.zip
```

**预期何时消失**：用户重启（内核重新装回 `127/8 → lo0`），或按 `README.md` 的说明执行一条
`sudo route add -net 127.0.0.0/8 -interface lo0`。

## F-2（开放）：`falied to set interface > invalid argument` 在刷

| 时点 | 窗口 | 次数 | 每分钟 | 阈值 |
|---|---|---|---|---|
| 2026-09-22 19:08 | 1.8 分钟 | 5 | **2.78** | ≥1 ⇒ 命中 |
| 2026-09-23 10:43 | 0.3 分钟 | 22 | **73.3** | ≥1 ⇒ 命中 |
| 2026-09-23 10:45 | 2.98 分钟 | 36 | **12.07** | ≥1 ⇒ 命中 |
| **2026-09-24 18:54** | **3.0 分钟** | **18** | **6.0** | ≥1 ⇒ 命中 |

**判据**：`tun-iface-einval`（阈值是脚本里的常量，来源写在那儿）。
**口径提醒**：这是**核心自己**的拼写（`falied`），不是我们的笔误；四次采样窗口长度**都不同**，
**不能说「恶化了 N 倍」** —— 只能说**四个时点都在刷**。要谈趋势必须**同窗口长度**重采。

### F-2 根因（2026-09-24 定位，读上游源码确认）

**不是我们的配置问题。** 上游 `XTLS/Xray-core` tag `v26.9.9`
`proxy/tun/tun_darwin.go:596`：

```go
func setinterface(network, address string, fd uintptr, iface *net.Interface) error {
	var err1, err2 error
	switch network {
	case "tcp6", "udp6", "ip6":
		err1 = unix.SetsockoptInt(int(fd), unix.IPPROTO_IPV6, unix.IPV6_BOUND_IF, iface.Index)
		fallthrough                    // ← 关键：v6 也会掉进 v4 分支
	case "tcp4", "udp4", "ip4":
		err2 = unix.SetsockoptInt(int(fd), unix.IPPROTO_IP, unix.IP_BOUND_IF, iface.Index)
	}
	return errors.Join(err1, err2)
}
```

* 对 **IPv6** socket，它先设 `IPV6_BOUND_IF`（正确），再因为 `fallthrough` 去设
  **IPv4 的 `IP_BOUND_IF`** —— 而这是个 **AF_INET6** socket ⇒ `EINVAL`（"invalid argument"）；
* `errors.Join(err1, err2)` 把 `err2` 一起返回 ⇒ 调用方把它**记了一条日志**，
  而**真正生效的那个选项（`IPV6_BOUND_IF`）是成功的**（两行日志里的级别是 `[Info]`，
  不是 error/warn，与"只是记录"一致）。

**⇒ 结论：每一次 IPv6 出站拨号都会打一行，功能不受影响。**
也就是说它是**上游的噪音 bug**，不是"链路在坏"。

**为什么它仍然值得处理（运维影响，而不是功能影响）**：
它现在是本机分诊里**唯一命中的 signature**（6/min，阈值 1），
于是**每一份现场包都会被分类成它**，真实信号被它盖住 ——
这正是 `triage-incident.py` 那张信号表本想避免的事。

**三条可选处置（按推荐顺序，都待定）**：

1. **上报上游**：给出精确到行号的位置 + 复现条件（任何 IPv6 出站拨号 +
   `autoOutboundsInterface` 非空）—— 这是唯一能真正消掉它的做法；
2. **分诊侧降级为"已知上游噪音"**：但**不是静默忽略** —— 要写进 `SUMMARY.md` 的
   "已知但不判"清单，并且**当它不再出现时要能发现**（否则将来真坏了也看不出来）；
3. **不能靠关 `autoOutboundsInterface` 绕开**：它是防路由环的第三道保险
   （`docs/07` 的 R3.5），关掉等于拿一个真实风险换一行日志。

**本次仍不改判定**：F-2 保持开放，第四次采样与根因一起留档。

**第四次采样的两个额外口径（必须一起读，否则会把它与前三行错比）**：

* **窗口是退让口径**：采集时 `ps` 取不到 App 启动时刻 ⇒ 窗口退让成"最近一次核心启动"，
  `manifest.json` 里 `window_degraded=true`。前三行是不是退让口径**没有记录** ——
  在没核对这一点之前，第四行与前三行**不可直接比较**。
* **判定 `helper` 三态用的是产品口径**（协议号优先，`installed=0.8.35` / `bundled=0.8.37`
  但协议号都是 1 ⇒ `Match`），与 `helper-mismatch` 的历史误判口径一致。

**它是怎么被发现的（这条也值得记）**：用户给了一个 incident ID，但该 ID 在本机
（仓库、`~/Desktop`、app 数据目录、`/tmp`）**没有任何记录**；于是按文档流程在本地
**重新采集**了一份（`scripts/incident-bundle.sh --out /tmp/inc-abca.zip`，只读、未联网），
分诊命中 `tun-iface-einval`。⇒ 「ID 对不上现场」这件事本身要有个入口处理，
否则下一次还会卡在这里（见 F-5）。

## 这些发现与「代码缺陷」的区别（读的时候别搞混）

* 它们**不会**因为装上新版而消失（F-1 要重启/`route add`；F-2 需要看核心为什么反复 EINVAL）。
* 它们**都**是 `triage-incident.py` 的 signature，**命中只代表「现在是这样」**，不代表成因归属
  （归属问题见 `task-80` 的现场取证口径）。
* 一旦消失，请**不要删这份文件**，而是在对应行补一句「何时、怎么消失的」—— 那才是可引用的历史。

## F-5（新增，流程缺口）：给了 incident ID 但本机没有对应现场

**现象**：用户给出 `INC-20260924-104548-abca`，但本机**任何位置**都没有这个 ID
（`git grep`、`docs/incidents/`、`~/Library/Application Support/com.xraytun.desktop/`、
`~/Desktop`、`/tmp` 全都没有）。ID 的时间戳（10:45:48）与本机新采集的那份
（`xraytun-incident-20260924T110009Z`）**不是同一次**。

**为什么会发生**（三种可能，当前**无法区分**）：

1. 现场在**另一台机器**上采集的，ID 只是被口头带过来；
2. GUI 侧的「报告问题」把包产在了**别的位置**（`incident_preview` 的落点我没有核对过）；
3. 包被删除/清理掉了（默认落 `~/Desktop`，而 Desktop 上现在没有任何 incident 包）。

**建议的改法（待定，别现在就动）**：分诊工具加一条
`--lookup <INC-ID>`：先在已知的几个落点找同名现场，找不到就**明确说"本机没有这个现场"**
并给出"重新采集一份"的命令 —— 而不是让人以为 ID 存在、只是在别的地方。
**这条的价值在于把"我该去哪儿找"变成一个可执行的答案**，而不是再来一轮人肉搜索。

**顺带记一条**：本次为了不空转，直接采集了**当下**的现场。**当下的现场不等于那份 ID 的现场** ——
如果再拿它去回答"那个 ID 里发生了什么"，就会把两个时点混成一个。所以本文件只把
这次采集记成 **F-2 的第四个采样点**，**不**声称它对应那个 ID。
