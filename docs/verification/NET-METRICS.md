# `scripts/net-metrics.py`：把「改前 / 改后」的三组数字固化成一条只读命令（task-101 / task-103）

> 为什么要有它：`task-97`（v6 改写）与 `task-98`（看门狗判据）都会在 **v0.8.34** 上到用户机器，
> 而「修好没修好」此前只能靠**临时 Python 片段** —— 那东西只活在某个人的会话里。
> 本项目栽过「不可复制的现场只存在于临时目录 = 等于不存在」，也栽过「CSS 规则数的口径不对」。
> 所以：**口径写进脚本 + 自测 + 敏感性**，以后任何一次「改前 vs 改后」都用同一条命令。
>
> **task-103 修了一个会让它静默丢数据的缺陷**（见 §2）—— 那类工具比没有更糟。

## 1. 用法

```bash
python3 scripts/net-metrics.py                       # 默认定位 macOS 应用日志目录；全部记录
python3 scripts/net-metrics.py --since 00:00         # 只算今天
python3 scripts/net-metrics.py --until 13:42:30      # **固定到某个时点 ⇒ 数字可复现**
python3 scripts/net-metrics.py --json                # 机器可比对
python3 scripts/net-metrics.py --self-test           # 自测（只写 /tmp，不联网）
```
只读：**不修改/移动/删除日志**，不联网，不跑 cargo，不碰 `site/**`、`scripts/check.sh`、`scripts/diagnose-network-drop.sh`。

## 2. ⚠️ task-103 修掉的缺陷：**一行可能含两个 JSON 对象**（旧版整行丢掉）

日志里存在**一行装两个对象**的行（2026-09-22 实测 **4 行**），形状是 `…}{…`（中间没有换行）：

```
{"ts_unix":1790051357,"source":"app",…"隧道已自动恢复（第 1 次自动重建）"}{"ts_unix":1790051357,"source":"core",…"Xray 26.9.9 (…)"}
{"ts_unix":1790054534,"source":"core",…}{"ts_unix":1790054534,"source":"app",…"隧道已自动恢复（第 1 次自动重建）"}
{"ts_unix":1790054858,"source":"core",…}{"ts_unix":1790054858,"source":"app",…"隧道已自动恢复（第 1 次自动重建）"}
```

**旧实现（`json.loads(line)`）对这类行必然抛异常 ⇒ 整行被当成「坏行」丢掉**，后果：
**「隧道已自动恢复」被漏算成 0 行**（实际 3 次），`source=app` 也少算。
⇒ 已改成 `json.JSONDecoder().raw_decode` 循环解析到行尾（**一行 N 个对象全部计入**）。

**「坏行」不再混成一个数**，拆成四类打印：

| 类别 | 含义 | 实测量（09-22 快照） |
|---|---|---|
| **多对象行** | 一行 >1 个 JSON 对象 | **4 行**（多解析出 4 个对象） |
| 截断·残缺行 | 解析中途失败（尾部坏） | **0** |
| 非 JSON 行 | 既非空行也非以 `{` 开头 | **0** |
| 空行 | 只有换行/空白（**不是坏行**） | **3** |

> 旧的「坏行 7」= **4 个多对象行 + 3 个空行** —— 这正是拆开才能看见的东西。
> **这类行为什么会出现**：产品侧根因见 **task-104**（backend-dev）；本脚本只负责**不再丢它们**。
> 脚本对**任意多个**对象都成立（循环解析），但**观测到的最多就是 2 个**。

## 3. 三组指标各自回答什么

| 组 | 回答的问题 | 关键口径 |
|---|---|---|
| **① task-97** | 「v6 改写」与「连接失败」的**相关性**：按 session id 归并连接 → 全是 v6 / 全是 v4 / v6+v4 三类，各给条数、`failed to open connection` 条数与百分比；另给两行行级计数 | 一律**按行内 session id `[…]` 归并**；`replace destination with tcp:[…]` 判 v6、`…tcp:<v4>` 判 v4 |
| **② 探针** | 探针判据可靠吗：连接数 / 成功 / **失败·有 `failed` 行** / **失败·无结局行**（按目标拆）、轮数、成功耗时 中位/p90/p95/p99/max、**>6s 才成功的条数** | 连接 = `proxy/socks: TCP Connect request to tcp:<目标>`；分轮 = 相邻间隔 **>5s**；耗时才用**消息内微秒时间戳** |
| **③ 自愈** | 误判的**代价**：`已作废` / `物理出口已变化` / `隧道已自动恢复` 逐条时间，以及两种空档口径 | **口径A** = 作废 → 下次 core 启动；**口径B** = 最后一条流量证据 → 下一条流量证据（task-95 口径） |

**去重（必须）**：按 `(ts_unix, message)` 去重。`app.jsonl` 与 `app.1.jsonl` **有重叠** ——
本次实读 **303,507 行 → 解析出 303,508 个对象 → 保留 259,735 条，丢弃 39,936 条重复**。

### 5.1 与**旧口径**的逐项差异（旧版数字**已作废**）

| 项 | 旧口径（task-101） | 修正后 | 原因 |
|---|---|---|---|
| 「坏行」 | 7（混算） | 多对象 4 / 截断 0 / 非 JSON 0 / 空行 3 | 拆类 |
| **「隧道已自动恢复」** | **0 行（错）** | **3 行** | 一行两对象的 3 行被旧解析器整行丢掉 |

那不是噪音，**正是三次成功的看门狗重建**。

## 7. 诚实清单：这个脚本**测不到**什么

1. **不做因果**：① 只给相关性。「v6 改写导致了用户的失败」不在这里证。
2. **探针失败 ≠ 用户当时上不了网**：只证明「这一个 URL 经 SOCKS 的这一次请求没成」。
3. **看不到应用侧超时**：探针 6s 超时**不落盘** ⇒ 只能用「>6s 才成功」的条数**间接**量化误杀。
4. **`app.jsonl` 不是完整应用日志**：`push_log()` 只进内存环形缓冲（`state.rs:319`），
   只有 `state.log()`（`state.rs:386`）落盘 ⇒ 看门狗过程行**不在文件里**。
5. **多对象行的上限未知**：脚本支持任意多个对象，但**观测到的最多 2 个**；会不会出现 3 个以上，**现有日志回答不了**。
6. **真机行为不可见**：安装/更新/重装 helper、Gatekeeper、UI 表现。
7. **依赖日志格式**：session id 形状、`replace destination` 文案、`source` 取值变化都会让指标失真；
   `--self-test` 只证明**逻辑**对，不能证明**格式**没变。
8. **口径A/口径B 不是同一件事**（今天差 ~5–6s），引用时必须写明用哪个。
