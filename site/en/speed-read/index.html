SpeedRead: compress a whole web page into 3 items

This is a Chrome MV3 extension. It reads the body of a whole page and gives you exactly 3 items: alpha (the single most important conclusion, the thing you should know first), beta (the second key fact: supporting evidence, or the cost, risk, limit or counterpoint) and gamma (the topic the page repeats, emphasises and cites most, with high-frequency terms as evidence). Summaries come from your own OpenAI-compatible endpoint; with no key, or when a call fails, it falls back to local term frequency plus sentence scoring and still returns 3 items. And it recomputes automatically whenever the page changes — you never press a button.

XrayTun is an Xray GUI client for macOS; the two are not integrated, share no code and do not depend on each other, and neither can be used to configure the other. They sit on the same site only because the author is the same.

What the 3 items are

The panel always shows exactly 3 rows and not one word more. The division of labour is written into the prompt, so the model has to answer in these terms:

  • alpha — the most important conclusion in the page. On its own it should answer “what is this page saying”. Claims the body does not support are not allowed.
  • beta — the second key fact, and not a rewording of alpha. Preference goes to evidence or numbers that support alpha, then to cost, risk, limits, conditions, dates, or to the opposing view.
  • gamma — the topic the page repeats, emphasises and cites most. It answers “what does everyone keep talking about”, not “what matters most”, and lists high-frequency terms that really occur in the body as evidence.

Each item defaults to 60 characters (configurable 16–200) and is cut at a sentence boundary past that. Each row shows at most two lines and expands on click. If you want it even stricter, the options page can hide the footer (source and timing) and the gamma evidence line, leaving literally just the 3 rows on screen.

How to use it

Install: download the zip → unzip → chrome://extensions → enable developer mode → “Load unpacked” → pick the extracted speed-read-extension/ directory. It is not on the Chrome Web Store; the upside is that the package ships the unminified src/, so you can read it line by line first.

Configure a model: the first run opens the options page. Any OpenAI-compatible /chat/completions endpoint works, with 8 presets built in: OpenRouter, OpenAI, DeepSeek, Moonshot / Kimi, Alibaba DashScope, SiliconFlow, Zhipu GLM, Volcengine Ark, plus a custom / self-hosted option. Give the Base URL only down to /v1 (not including /chat/completions), then a model name and an API key. The “test connection” button really sends one minimal request and reports what came back.

Panel and shortcuts: Alt+Shift+S shows or hides the panel, Alt+Shift+R recomputes immediately (forced, bypassing the cache and the change thresholds). The title bar is draggable and the position is remembered. ⟳ recompute, ⧉ copy all 3 items (with title and URL), ⚙ options, – collapse, ✕ close. Clicking a row expands the full text.

When nothing appears: open the popup and read the “Diagnostics” section at the bottom. It prints a one-line conclusion plus a checklist: page type, whether the content script is injected, site access permission, blacklist, API key, whether the panel is hidden, and the last run result. Tabs that were already open before you installed the extension are re-injected automatically, and the popup has a “inject into this page” button that does not require a reload.

Auto-update: recompute whenever the page changes

There are 4 triggers and any one of them is enough; you never click anything:

  • DOM mutations: a MutationObserver watches the whole tree and recomputes once the page has been quiet for a moment, so a long list filling in item by item does not fire it over and over.
  • SPA routes: the address bar is compared once a second (a string comparison, basically free), alongside popstate / hashchange; a route change discards the old result immediately.
  • Returning to the tab: switching back in re-checks once.
  • Fallback poll: the content fingerprint is compared periodically, which rescues polling pages that fire no DOM events at all (stock tickers, scores, countdowns).

But a page that keeps changing does not mean the model keeps being called. Three gates:

  • An unchanged fingerprint sends no request. The fingerprint is built from the normalised URL, the title, samples from the head and tail of the body and the total length; tracking parameters such as utm_* are ignored, so different entrances to the same article share a result.
  • Tiny changes count as noise. If the body grows by less than both the absolute and the relative threshold, nothing is recomputed — clocks, view counters and rotating ads will not cost you anything. A same-length edit near the top is still caught, via a head sample.
  • Cache, de-duplication and rate limiting. The same content reuses its result for a while; concurrent requests for the same page are merged into one; consecutive real calls on the same tab are spaced out.

The full chain as measured by the end-to-end test: first paint = 1 call → edit the body → automatically a 2nd call (the panel updates within about 0.7 seconds) → add noise to the footer → still 2 calls → open the same content in a new tab → still 2 calls (cache hit).

How it works

Body extraction: it first scores candidate containers by “length × (1 − link density) × punctuation density × tag bonus” to throw away navigation, footers and sidebars. The container threshold adapts to page length (a short page may have only one or two hundred characters of body text, and a fixed threshold would fail to pick a container and degrade into “the whole body is the article”). Elements that impersonate nav / footer with a plain div are dropped by id/class; blocks that are almost entirely links are dropped as navigation, but a page that is nothing but links (a directory) disables that filter and recomputes rather than returning nothing; and a div whose children are all inline is treated as a paragraph — which is how it still works on div-soup sites with no <p> in sight.

Input compression (maximising information): the body is not handed to the model wholesale. Blocks are picked by information density — the opening block is always kept (ledes carry the most density, and pure score ranking lets long mid-page blocks push them out), headings get a reservation, the rest fill the head budget by score, and a slice is reserved for the end (conclusions live there). Skipped material is annotated in the prompt with how many characters were omitted.

Prompt and forgiving parsing: the division of labour, the length cap, the ban on invented numbers and the requirement to return JSON only all live in the system prompt. The answer tolerates markdown fences and surrounding chatter, and falls back to parsing a numbered list. If it still cannot be parsed into 3 items, one repair request is sent asking for just that JSON; if that fails too, it drops to the local fallback.

Panel and injection: the panel lives in a Shadow DOM, fully isolated from the host page’s CSS, and its styles are installed as a constructible stylesheet — so it keeps its looks even on strict-CSP sites with style-src 'none'. Model output is always written with textContent, never innerHTML, so a server response can never be parsed as HTML.

Verification

Every number below comes from the project’s own automated verification and can be re-run from the source. Nothing here says “it should work”.

  • 12 static checks: the manifest is MV3, permissions are minimal, every referenced file exists, shipped code contains no eval / innerHTML / remote script, content scripts really are classic scripts, and the panel’s hard constraints hold.
  • 100 unit tests (zero dependencies, offline, milliseconds): text metrics, input compression, prompt building, forgiving parsing, local fallback, the model client (with an injected fake fetch, covering 401 / 429 / timeout / non-JSON bodies), body extraction, configuration and structural consistency.
  • 52 real-Chrome end-to-end assertions: a real Chrome is launched, the real extension is loaded, and a local mock gateway is used. All actually executed.

The most important end-to-end cases:

  • A page opened before the extension is installed: after re-injection the panel appears with no reload — this reproduces and pins down the real “I installed it and nothing happens” failure.
  • A fresh install with no API key: the local fallback returns 3 items with zero network requests.
  • Editing the page body updates the panel automatically: measured at 683 ms, and the second prompt carries the new body text.
  • Footer noise causes no extra call; a second tab with the same content hits the cache (the call count does not change).
  • The prompt sent to the model contains the page’s key data and none of the navigation, footer, sidebar or page header.
  • Styles survive on a strict-CSP site (style-src 'none'); a div-soup page with no <p> still yields a body, and its top navigation stays out of the prompt.
  • Hiding the footer and evidence leaves exactly 3 rows.
  • Neither the service worker nor the page throws an uncaught exception.

The strongest single check is putting the file a user actually downloads into a real browser: the speed-read-extension-0.1.0.zip served from this site is the build artefact itself — unzip and load, with a top-level speed-read-extension/ directory, 27 files, unminified source and the MIT licence included.

Privacy and permissions

The page body is sent to the one model endpoint you configure — that address and nothing else. This has to be stated plainly: page content does leave the browser. If that is not acceptable, do not enter an API key and use the local fallback only.

The API key stays on your machine (chrome.storage.local) and is only read and sent by the extension’s service worker; neither content scripts nor page scripts can reach it. All model calls are made from the service worker (extension origin), so they are not subject to the host page’s CSP connect-src.

It asks for 4 permissions: storage (config and cache), unlimitedStorage, scripting (for re-injection) and activeTab. The extension does not modify page content, uploads no local files, has no analytics or telemetry, and loads no remote code.

Keeping it off a site: the options page has a “sites not to run on” list, one domain per line, with wildcards such as *.bank.com. Note that a bare domain is a substring match (writing example.com also catches notexample.com); use the * form for an exact match.

Known limits (read before relying on it)

  • It only handles http/https pages; local file:// pages need an explicit toggle in the options.
  • It summarises the main frame only, not iframe content, and pages browsers forbid extensions from touching (chrome://, extension pages, the Web Store) simply get no reaction at all.
  • Body extraction is heuristic (a lightweight readability approach) and will not be perfect on every site. Image-only or video-only pages, or pages with very little text, say “body too short” instead of inventing 3 items.
  • Chinese tokenisation uses bigrams, not a dictionary, so the gamma high-frequency hint occasionally contains a fragment that crosses a word boundary. Gamma itself is decided by the model; this only affects hint quality.
  • Some gateways reject response_format: json_object; the extension drops it and retries once, leaning on the prompt plus forgiving parsing instead.
  • The “local fallback” is extractive scoring over term frequency and sentences — clearly less accurate than an AI summary. The panel footer always states whether the result is AI or fallback.
  • Summary quality depends on the model you pick: the same page can produce different conclusions under different models. That is the model, not a stale cache (changing the model invalidates the cache key and recomputes).
  • It is not a reader mode: it does not reflow the page, hide ads or translate. It gives you 3 items.

FAQ

What exactly does it do?

It reads the body of a page and outputs 3 items only: alpha (the most important conclusion), beta (the second key fact) and gamma (the most-repeated, most-emphasised topic on the page). It is not a reader mode, it does not modify the page, translate it or bookmark it; it answers “what is this page saying”.

How are the 3 items divided up?

Alpha is the one item that on its own answers “what does this page say”. Beta must not duplicate alpha: it prefers evidence or numbers supporting alpha, then cost, risk, limits, dates or an opposing view. Gamma answers “what does everyone keep talking about” rather than “what matters most”, and carries high-frequency terms that really occur in the body. That division is written into the prompt.

Do I need an API key? Can I use it without one?

Yes you can. With a key it uses the large model and is at its best; with no key, or when a call fails, it drops to local term-frequency plus sentence scoring and still returns 3 items, labelling the result “local fallback” in the panel footer — clearly less accurate than an AI summary. Only that fallback path is fully offline.

Where does my page content go?

Only to the single model endpoint you type into the options page. Nothing else leaves the browser. The key is stored locally and only read and sent by the service worker; content scripts and page scripts cannot reach it. There is no analytics, and no remote code is loaded. If you do not want the body to leave the browser, do not enter a key.

The page changes constantly — will it keep calling the model and cost me money?

No. An unchanged fingerprint sends no request, tiny changes (clocks, view counters, rotating ads) count as noise, the same content reuses its cached result, concurrent requests for one page are merged, and consecutive real calls on a tab are spaced out. Measured: editing the body triggers a second call; adding noise to the footer does not; a second tab with identical content hits the cache and the call count stays put.

Which browsers are supported, and how do I install it?

Chrome 110+ or a Chromium browser on the same engine generation (Manifest V3). Installation is unzip-and-load: download the zip, unzip it, open chrome://extensions, enable developer mode, click “Load unpacked” and pick the extracted speed-read-extension/ directory.

Why does the panel only ever show 3 rows?

That is the point: you cannot maximise information until you cut everything that is merely “nice to know”. Nothing else is stacked on top — click a row to expand the full text, or copy the 3 items from the popup. For something stricter still, the options page can hide the footer and the gamma evidence line, leaving literally 3 rows.

Some pages extract badly. What can I do?

This step is heuristic and will not be perfect everywhere. Three things help: read the conclusion in the popup diagnostics (it tells you whether the body was too short, the site was excluded by the blacklist, or the content script was never injected); tune “skip pages shorter than” and “characters sent to the model” in the options; and add sites that genuinely do not suit summarisation to the “sites not to run on” list.

Why does it sometimes say “local fallback”?

Three cases: no API key configured; the endpoint returned an error (invalid key, wrong model name, rate limit, timeout, gateway without JSON mode); or the model’s answer could not be parsed into 3 items. The panel footer then says “local fallback” and the popup diagnostics show the exact reason. If you would rather see an error than a downgrade, turn the fallback off in the options.

What is its relationship to XrayTun?

Two separate projects by the same author: not integrated, no shared code, no mutual dependency, and neither can configure the other. XrayTun is an Xray GUI client for macOS; this project is a browser extension. They share a site only because they share an author.
