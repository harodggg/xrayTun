# 蓝车漂移实测证据（task-49）

> 结论先行：**在当前 HEAD 上漂移真实存在，而且是可量化的**。它的触发点是**每圈的回绕 seam**

## 5. Q5：`data-arc` 与渲染位置脱节吗？——**是，这就是护栏盲区**

| 指标 | 值 |
|---|---|
| \|渲染 − P(data-arc)\| > 1.5px 的帧 | **6,448 / 16,423 = 39.26%** |
| 其中 **P(data-arc) 仍精确在可见线上**（offI ≤ 0.5px） | **6,216 帧（37.8%）** |
| `gap` 最大 | **500.28 px**（回绕跳） |
| 滑行期间 `gap` 典型 | 60–150 px |

也就是说：**只看 `data-arc` 的护栏在 6,216 个「车已经漂到线外」的帧上都会是绿的**
——`data-arc` 指向主干上的正确位置，被插值的是 `transform`。

**一个例外要如实报告**：`offI` 在 resize 附近有少数帧达到 **31.2px**
（例：`arc=218.8, offI=31.29, t≈11,978ms`，同一时刻多辆蓝车）。
这意味着**几何变化瞬间连 `data-arc` 本身也会短暂与实际可见线不一致**。
我**没能区分**这是「guide 已更新、`data-arc` 还是旧值」的一帧错位，还是我在 rAF 里采样的时序差 ——
需要更细的时序探针（同一帧内先读 guide 再读 data-arc，或录 MutationObserver 时间戳）。**不计入主结论。**

## 7. 机制小结（代码位置）

`apps/ui/src/topology/Flow.tsx`（HEAD）：

* 一圈 = 「主干 + 一条分支」：`:403-434`（`lap = trunk + br.len`，回绕时 `branch = (branch+1) % nB`）；
* 回绕把 `st.dist` 归零 → `arc` 跳到主干起点（`:441`），而上一帧车还在**分支末端（出口）**；
* 限速器在**屏幕空间做直线插值**（`:446-461`，`cap = max(1.5 * walkRef, walk)`），
  把这一跳摊成 ~2.7s 的滑行 → 滑行期间车离开可见线，最大 33.85px；
* `data-arc` 每帧照常写入正确值（`:469`），所以「弧长护栏」量不到这次离线。

## 8. 修复方向取舍（**本卡不改代码**，供你决策）

| 方案 | 漂移 | 代价 / 风险 |
|---|---|---|
| **(a) 回绕瞬时重落位** | **0** | 每圈一次「跳」（~486px 的视觉突变）。**task-36 的连续性护栏会立刻变红**（`max/median`、`no-teleport`），必须同时把「回绕 seam」定义成允许事件（例如按 `data-arc` 骤降识别并豁免），否则测试与实现互相矛盾。语义上最诚实：这趟送到了。 |
| **(b) 滑行改为沿路径** | 0 | 要沿回程段走回主干 → **等于把 task-37 刚删掉的「走回程」又加回来**，且耗时更长（按路径长度算）。与当前不变量直接冲突。 |
| **(c) 让回绕点选在位移最小处** | 减小但不是 0 | 分支末端到入口的距离天生 ~400–500px；除非改路线形状（例如让所有分支末端先汇聚回主干再回入口），否则只能小幅优化。 |
| **(d) 把两类触发拆开：回绕 → 瞬时落位；几何变化 → 保留限速滑行** | 回绕 0 漂移、几何变化维持不瞬移 | 需要「这一帧是回绕」的显式标记（代码里已有：`st.dist >= lap` 那一刻）。可选加 120–160ms 淡出/淡入缓和视觉突变。**改动局部**（`:431-434` 处把 `capped` 对回绕豁免），且不必推翻 task-37。 |

**推荐 (d)**，其次 (a)：两者都要求**同步调整动画连续性判据**（把「回绕 seam」从「跳变」里豁免），
否则 task-36 的护栏会把修好的行为判红。(b) 不建议（与 task-37 的结论冲突）。

## 9. 诚实清单

1. **回绕判据用的是 `data-arc` 突降 >300px**；如果哪次回绕的 lap < 300px（本窗口 lap≈484–505px，没有），会漏判。
2. **滑行/正常的分界是 `gap > 5px`**（正常步长 ≈1.2px/帧，cap≈1.8px/帧），是经验阈值，不是代码里的 `capped` 标志。
3. **几何变化瞬时的 `offI≈31px` 未定因**（时序错位 vs 真实不一致），见 §5；需要更细探针。
4. 采样只有 **25s / 3.6 圈/车**，且只覆盖 **3 条入站 × 5 个出口里预览 mock 的那一档流量**；
   真实核心下的出口数/长度不同会不会改变量级，**未测**。
5. 用的是 **`?preview=1` 假后端**；且是 **headless Chrome**（真机 WKWebView 的合成/刷新时序可能不同）。
6. `fill` 只在分支切换时更新，所以「按通道分组」把**滑行帧归到了它正在送往的新分支**上 ——
   它衡量的是「哪条分支的回绕更明显」，不是「哪些车的身份」。
7. 我在同一窗口里只强制了一次 resize；更频繁的缩放（拖窗口）未测。
8. **未测**：`v0.8.29`（无 task-37 修复）上的同一指标 —— 用户看到的是那个版本，
   它的「回流 + 漂移」是叠加的；需要另发一版才有意义。
