## 为什么「车道」与「连线」曾经对不上

早期把两者分成两层：车道是带货车的容器（CSS 动画让车左右漂），连线是覆盖层。
结果是**货车只在自己那条车道里往返，和连线没有关系** —— 看着像两套不相干的东西。

现在一条路线就是**一条连续路径**（入口 → 分叉 → 各出口 → 回入口，首尾重合），
货车用 `getPointAtLength` 在这条路径上取位置；车道那一列只作为「道路」的视觉底衬。

⚠️ 但**车并不沿它从头走到尾**（那是历史 bug）：这条路径为了与可见线完全重合，
段序里**夹着回程段**（见下面「一轮覆盖哪几段」）。车的行程是「主干 + 某一条分支」，
按圈轮换分支，**一步也不走回程段**。

两个实现要点（都踩过）：

* 路径必须是**一条连续路径**：每段各写一个 `M` 会得到多段互不相连的子路径，
  而 `getPointAtLength` 只沿一条路径连续采样 —— 货车会在段与段之间跳。
* 动画的起始时刻要放在 ref 里：拓扑每 2 秒刷新一次会重建 effect，
  用局部变量会让货车**每 2 秒跳回起点**。

## 车道列为什么最后被删掉

用户要求「车道应该消失，线本身应该就是车道」—— 这反而让布局更简单：

* 从四列（入口 / 车道 / 扇形列 / 出口）变成**三列**（入口 / 流动区 / 出口）；
* 车不再「在车道里漂」，而是沿**连线本身**走（入口 → 分叉 → 某一条分支），
  连线与货车因此天然在同一层；
* 删掉了 `.lane` / `.lane-wrap` / `.highway__road` / `.highway__links` 等一批样式
  （那一段还遗留了三处同名规则互相覆盖）。

## CSS 上的两个硬教训（都是量出来的）

1. **同名规则的后者优先**：把 `grid-column` 追加到文件末尾，结果被后面的
   `.highway__legend` 覆盖 —— 图例占了第 1 列，入口卡片被挤到第 2 列，
   整幅图错位。定位必须写在**同一个规则块**里。
2. **整页有 `max-width: 820px`**：先用两个空白占位列（32px + 128px）给弧线留空间，
   流动区被压到 374px、卡片文字开始裁切。弧线空间要在**流动区内部**预留，
   不要单独占列。

## 为什么是「一个入口 → 全部出口」

用户指出「tun 入口的流量应该趋向很多出口，应该是一对多」。

早先按相邻切段分配（一个入口只连自己那几个出口），看起来像「每个入口有自己
独立的一组出口」—— 那不符合事实：所有入口的流量都经过**同一条规则链**，
规则链决定去向，所以任何入口都可能去任何出口。

现在每个入口对全部出口扇出（线条数 = 入口数 × 出口数，当前 3×6 = 18），
并且**每条扇出分支按目的地的出口类别着色**（蓝=经节点 / 绿=直连 / 红=拦截），
货车走到哪条分支就变成那个颜色 —— 这样图例对得上，也能看出「这条线通向哪类出口」。

代价是线多了会显得密，所以线的透明度压到 0.3、主干更暗（0.22），
主视觉留给货车。

## 一轮覆盖哪几段：为什么车「绝不走回程」（task-37 裁定）

导引路径（隐藏的 `path.flow__guide`）的段序是**交错的**（真浏览器 DOM 量的段长）：

```
seg0 主干[0,169.4]      seg1 去₁[169.4,484]     seg2 回₁[484,798.6]
seg3 去₂[798.6,1123.7]  seg4 回₂[1123.7,1448.8] seg5 去₃[1448.8,1802.1]
seg6 回₃[1802.1,2155.5] seg7 回主干[2155.5,2324.9]        整环 = 2324.9
```

回程段的存在是**有意的**：只有把「去一段 + 回分叉」成对插入，导引路径才与可见线完全
重合（否则车会有约 1/4 行程飞在空白处 —— 那是 B1）。**但车不该走回程段。**

`getPointAtLength(dist)` 是按**弧序**取点的，所以「对去程长度取模」这类前缀取模
一定会走进回程段，而且**永远到不了后面的出口**：

* 弦长 ≤ 弧长 → `span ≤ 169.4+314.6+325.1+353.4+169.4 = 1331.9`；
* 去₃ 的起点是 **1448.8 > 1331.9** → 第三个出口那条线上**永远没有车**（算术可证，与弦长具体值无关）；
* 而一圈的弧序前缀必然包含完整的 `回₁` `[484.0, 798.6]` → 车会沿出口 1 的原路倒着走回来。

**现在的做法（方案 C）**：一圈 = **主干 + 某一条分支**，送达一个出口后换下一条
（`(branch + 1) % 分支数`）。于是：

* 车在任何一帧都只落在「主干」或「某一条去程段」上（`<g data-arc>` = 该帧在 guide 上的弧长）；
* 每条分支跨圈都会被访问到，不再有「饿死的出口」；
* 从出口跳回入口那一帧语义就是「这趟货送到了」，位移由限速变成一段匀速滑行。

**护栏是语义断言**（`topologyAnimation.test.ts` 的 `measureArcInvariant`）：任何一帧的
`data-arc` 都必须落在「主干 ∪ 各去程段」内，且每条分支都被访问过。实测：

| 实现 | 落在回程段的帧 | 一圈 ÷ 整环 | 三条分支都有车 |
|---|---|---|---|
| 现在（主干 + 一条分支，按圈轮换） | **0** | ≈0.21 | 是 |
| 老行为（把交错段序的前缀当一圈） | **10 823** | ≈0.99 | 否（第三个出口恒为 0） |

辅助的比例断言（0.1–0.8）只作辅助：那条带子原本是**按已经错掉的基线**（`span ≈ 60%`）校准的，
区分不了「主干 + 一条分支」与「主干 + 一条分支 + 半段回程」—— 后者只有语义断言管得住。

## 一处刻意的口径

连线表达的是「车道与出口相连」这个**结构关系**（来自配置）。
核心只有按入口 / 按出口两类统计，**没有逐条规则的计数器**，
所以**不**声称「这辆车的货去了哪个出口」。出口怎么分给车道是为了画得清楚，
不代表真实流量走向。

## 教训

8 版才定下来的原因，多数是**凭观感调**而不是**先量**。
后来每次先量一次，就立刻发现一个具体数字问题（4px / 10px / 84px），
比反复看截图快得多。另外：自己写的路径解析正则会算错，改用 `getBBox()`。

## 为什么 dns-out / api 曾经显示 `0 B`（v0.8.24 修复）

用户问「dns-out 和 api 的流量是不是错误的，怎么会是 0」——**答案是：那是测量盲区，
不是真的没流量**。

| 出口 | 实测连接数 | `StatsService` 字节 | 为什么字节恒为 0 |
|---|---|---|---|
| `dns-out`（协议 `dns`） | **4769** 条 UDP | 0 | Xray 不统计 UDP 出站流量 |
| `api`（本机回环） | **5374** 条 TCP | 0 | Xray 不统计本机回环流量 |
| `block`（`blackhole`） | 201 条 | 0 | **真的 0** —— 连接被拒，本就没有字节 |

最小配置实验证实了这一点：一条 `accepted tcp:198.18.0.2:53 [socks -> dns-out]`
确实走了 dns-out，而计数器仍是 0。Xray 的[统计文档](https://xtls.github.io/config/stats.md)
只定义计数器名，没有说明这个限制。

而 `block` 的 0 是**真的 0** —— 于是「真 0」与「测不到」在界面上长得一模一样，
这正是本项目反复修掉的那类混淆（「查不到 ≠ 0」），这次出现在出口侧。

### 修法

1. **dns-out / api 单独分组**「内部通道」，**不再进流向图** ——
   混在 `node` / `direct` 旁边显示 `0 B`，会被读成「这两个出口没在用」；
2. 它们改用**连接数**表示活跃度 —— 这是唯一可得的指标。连接数从核心访问日志的
   `accepted ... [in -> out]` 行累计（`crates/xt-core/src/xray/access_log.rs`），
   在核心输出的**单点**（日志转发任务）解析，不另起 tail；
3. 合计**只算用户流向**，不把内部通道的占位 0 混进来；
4. `connections: null` 表示**没观察到**（核心没跑 / 日志里还没有连接行），
   显示「—」而不是 `0` —— 与字节字段同一口径。
