**顺带澄清一条我本来以为成立、但核实后**不成立**的怀疑**（写下来免得后人重查）：

> `COMPLEXITY-AND-PERF.md §3` 与 `VISUAL-AND-UI.md §3` 也有，交叉不重复。

1. **两阶段启动（建隧道 → 确认数据面 → 才 CommitRoutes）**：`07`/`02` 与 `supervisor.rs` 的设计目标
   是消除「默认路由已接管但数据面没起来」的**流量黑洞窗口**。顺序即正确性 —— 合并成一步会换来
   一个用户可感知的断网窗口。
2. **helper 的会话快照 + 启动回滚 + `/1` 拆分路由**：`README` 第一条约束就是「任何时刻都能完整还原」。
   快照落盘、增量更新、`restore_stale()`、`0.0.0.0/1 + 128.0.0.0/1` 这些看起来“重”的东西，
   换来的是「崩溃/断电/被 kill -9 之后网络还能回来」。**这是本项目最不能省的一层复杂度。**
3. **看门狗（10 s 真实探测 / 连续 2 次失败重建 / 失败退回直连）**：对应 J2（换网、唤醒）。
   它比「显示已连接就完事」复杂得多，但它是这个工具存在的理由之一。
4. **断网/换网的监控必须按 pid 去重（`MonitorGuard`）**：少了它会出现多个看门狗互相拆台
   （`docs/08 §B` 有真实事故）。看起来是额外机制，实际是**防重复执行的正确性**。
5. **DNS 四策略 + 哨兵 DNS + Fake-IP 缓存警告**：`04` 记录了多起「DNS 被接管导致全网不通」的现场；
   这部分的复杂度是**排障可见性**的代价。宁可在设置页占位，也不要变成「静默失效」。
6. **诚实的三个“做不到”在界面里的显式表达**（内部通道用连接数、字节不可用时显示「流量不可用」而不是 0、
   域名带 `*` 与配对时延）：这三处是本项目反复踩过的红线，**不允许为了简洁删掉解释**。
7. **设置页「只渲染当前分类」而不是 CSS 隐藏**（`Settings.tsx:150-155`）：多了一点渲染逻辑，
   换来 a11y 正确（读屏/Tab 不会进入隐藏内容）与可断言性。**不要为了「少几行」改回 CSS 隐藏。**

## 5. 案例：`auto_reconnect`（lead 指定的必查项，含三种方案的复杂度对比）

### 5.1 事实（全部可复核）

* 字段：`crates/xt-core/src/model.rs:766`；**默认 `true`**（`:809`）；serde `#[serde(default = "yes")]`（`:765`）。
* 判定：`apps/desktop/src/commands/core.rs:367` `should_auto_reconnect(was_connected, auto_reconnect, mode, already_running)`；
  启动路径 `reconnect_if_needed`（`core.rs:854`，设计理由写在 `:844-853` 的文档注释里）调用，
  失败时后台重试 `RECONNECT_ATTEMPTS = 24` 次（`core.rs:1068`）× `RECONNECT_INTERVAL = 5 s`（`:1070`）。
  > 行号以当前 `HEAD` 为准；lead 卡里给的 `core.rs:272` / `:750-759` 是更早 revision 的位置，**结论一致、位置已变**。
* `was_connected`：**只有用户手动点「停止」才清**（`core.rs:23`，注释明写「这是唯一会清掉『该连着』的地方」）；
  **退出应用不清**。
* 界面：`grep -rn "auto_reconnect" apps/ui/src` → **0 次**。设置页 4 个分类、10 个节、22 个控件里没有它。
* 设计理由（必须先读再判断）：`core.rs:844-853` 写明它服务于三件事 ——
  **自更新先退出 app 再替换再重启**、**崩溃后被系统重启**、**开机自启**。少了它，
  用户会看到「用着用着网停了」，而原因藏在一份日志里。
* 用户的真实处境（用户原话）：「断开或退出应用后网络就恢复了」——他把**退出应用**当成逃生手段；
  而下次启动会自动连回来，**这条逃生路不持久，且他关不掉**。

### 5.2 它到底属于哪一类？

**判定：`auto_reconnect` 属于「必须保留的复杂度」，不属于「为假设需求而建的机制」。** `[E3]`
理由：它有三个**已经发生过的真实触发场景**（自更新重启、崩溃重启、开机自启），
不是「以后可能要」；`core.rs:844-853` 的注释就是这三件事的现场记录。
真正的问题不是机制本身，而是**它的开关与语义对用户不可见**。

### 5.3 最小可行可见性：三种方案的复杂度成本对比 `[PJ]`

| 方案 | 要改什么 | 复杂度成本 | 副作用 / 风险 |
|---|---|---|---|
| **(i) 设置页加一个开关** | `types.ts` 的 `AppSettings` 加 1 个字段；在「系统与助手」分类里加 1 个复选框（这一分类当前总共只有 3 个控件）；`save_settings` 已经能存；从 `type_contract.rs:174` 的「界面刻意不暴露」例外表里删掉 `auto_reconnect` 这一条 | **小**：1 个类型字段 + 1 个受控复选框 + 1 条契约表改动。**没有新机制**（复用现有保存通路） | 设置页再多一个控件；用户要理解「自动重连」这个词 |
| **(ii) 只在自动重连的通知里给一个可点的出口** | 需要 (i) 的类型字段打底；在恢复态 UI 加一个「不要再自动连」动作，并调用一次保存 | **中**：还要处理**回不去**的问题 —— 关掉之后用户必须**另有一个地方能打开**，否则就是单向门 | 若不同时做 (i)，就是「一次性不可逆」：用户点掉之后只能改 JSON。**单独做 (ii) 比只做 (i) 更危险** |
| **(iii) 什么都不加，只在文案里说明** | 在恢复态文案 / 「其他」节提示里加一句：「自动重连默认开启，如需关闭请编辑 `settings.json` 的 `auto_reconnect`」 | **最小**：1 句话 | 要求用户改 JSON ——与「界面不让人碰 JSON」的现有方向相反；且**设置文件的位置只写在「规则」页的折叠区**，用户很难找到 |

**我的建议（标为产品判断，请 lead 定）**：**做 (i)，不做 (ii)。**
理由：用户上一轮的授权是「用更简单的方式去替代复杂的实现」——(i) 是**用 1 个已存在的设置 + 1 个复选框**，
把一条已经存在的行为变成可解释、可撤销的；(ii) 引入了一个「入口只在故障时出现」的新交互面，
而它必须依赖 (i) 才不至于变成单向门；(iii) 把复杂度推给用户（改 JSON），与项目方向相反。
**注意**：无论选哪个，**「退出应用不是断开」这件事本身需要一句说明**（退出不清 `was_connected`）——
这是用户把退出当逃生手段的根因，属交互文案范畴（`interaction-designer` 的领域），
本卡只登记事实与建议，不替交互定文案。

### 5.4 深度对照表里的一行（lead 要求的第 3 点）

| 功能 | 对用户的实际影响 | 界面可见性 | 差距 |
|---|---|---|---|
| `auto_reconnect`（是否在下次启动自动连回来） | **高**：决定「退出应用后网络会不会被自动接回去」，也决定应急逃生手段是否持久 | **0**：`grep auto_reconnect apps/ui/src` = 0；4 类 10 节 22 个控件里没有它 | **影响高 / 可见性零**，是本表里差距最大的一行 |
