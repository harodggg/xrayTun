> 用户报告（决定性补充）：**「断开或退出应用后网络就恢复了」+「国外可以，国内直接断掉」**
> （连接状态下整台 Mac 断网、所有应用都上不了网；一断开/退出就恢复；国外站点正常、国内必现。）
>

## 0. 复现方式与验证边界（先读，决定了下文每条证据的可信度）

**可用的复现入口**（都是 `?preview=1` 预览页；预览桥接拆成了 `preview*.ts` 模块）：

## 1. 断网场景 × 界面呈现 对照表

### S1「隧道还连着、实际已经不通」——**界面与健康状态完全一样**（★ 最要命的一处）

| 项 | 内容 |
|---|---|
| **现状证据** | 注入 `runtime = {running:true, recovery:{recovering:false, probe_failures:1, last_outcome:null}}` 后实测 DOM：<br>`{"badge": null, "dot": "dot dot--on", "dashState": "已连接 · 香港 · REALITY 01 53 ms", "topbarText": "… 断开", "banners": []}`<br>`probe_failures` 改成 `2` 后**逐字相同**（截图 `shots/drop-H-one-failure.png`） |
| **代码依据** | `ipc.ts:147-175` `recoveryView()` 只看 `recovering` 与 `last_outcome`，**完全忽略 `probe_failures`**；<br>`probe_failures` 类型/解析都在（`types.ts:199`、`ipc.ts:192`），后端也真的在下发（`core.rs:548-559` `sync_probe_failures()`，注释写着「界面可据此提前显示『连接不稳定』」）——**只差没接上**。 |
| **多久才变** | 看门狗 10 秒一跳（`core.rs:395`），**连续 2 次**失败才重建（`FAILURES_BEFORE_REBUILD = 2`，`core.rs:923`）→ 约 **20 秒**；刚睡醒只要 1 次（`SLEEP_THRESHOLD = 30s`，`core.rs:918`）→ 约 10 秒。<br>这 10–20 秒里界面是绿的。 |
| **用户会怎么误判** | 他看到的正是「已连接」+ 绿点。于是他会去**重启路由器、打运营商电话、骂节点**，而**不会想到先断开应用** —— 而用户自己已经验证过「断开就好了」。这一条**直接解释了他为什么觉得「没规律」**：唯一可见的变化发生在重建那一刻，而之前的探测节奏（10s/20s）对用户完全不可见。 |
| **缺什么** | ① `probe_failures ≥ 1` 时界面必须**可见地降级**（黄点 + 一句话），而不是继续显示绿的；<br>② 这句话里必须给出「整机断网时先断开」这个自救动作（见 §4 的「只改一句」）；<br>③ 不需要新增后端字段 —— 数据已经在事件里了。 |

| 项 | 内容 |
|---|---|
| **现状证据** | `?preview=1&state=connected&view=dashboard&recovery=recovering` 实测：<br>顶栏 badge = `正在自动恢复（第 2 次）`，圆点 `dot dot--warn`，顶栏按钮 = `正在恢复…` 且 `disabled: true`；<br>仪表盘状态词 = `正在自动恢复（第 2 次）`，副文案 = `看门狗正在重建隧道，不需要手动点「连接」（点了会打断它）`（截图 `shots/drop-E-recovering-switch.png`） |
| **代码依据** | `ipc.ts:152-158`；`App.tsx:223-227`（badge）、`:234`（`dot--warn`）、`:237,242-243,250`（按钮禁用 + title 说明）；`Dashboard.tsx:136`（副文案） |
| **用户看得懂吗** | 文案本身合格：「不需要手动点连接」「点了会打断它」都是给用户的话，不是给开发的话。**这一条 task-22 修得很好**（对比 v0.8.26 时只显示「未连接」，见 §2）。 |
| **漏在哪** | **仪表盘的主按钮仍然是可点的「连接」**：实测 `dashBtns: [{"t":"连接","dis":false}, …]`；代码 `Dashboard.tsx:139-146` 的 `disabled` 条件只有 `busy / mode==="direct" / !core.path`，**不含 recovering**。<br>于是同一屏上：顶栏说「正在恢复，别点，点了会打断」，仪表盘给了一个**可点的「连接」**，而它自己的副文案还在说「点了会打断它」。 |
| **用户会怎么误判** | 停留在仪表盘的用户**大概率会点那个按钮** —— 然后打断看门狗重建，看到「未连接」，再点一次…… 这正是用户描述的「没规律」。 |

### S3「重建失败 → 退回直连」——**告知明确，但状态会粘住**

| 项 | 内容 |
|---|---|
| **现状证据** | `?recovery=failed` 实测：<br>顶栏 badge = `自动恢复失败`，title = `自动恢复失败（第 2 次），已退回直连 —— 流量不再走代理`；<br>仪表盘状态词 = `自动恢复失败`，副文案 = `已退回直连：网络可用，但流量不再走代理 —— 可手动重连，或换一个节点`；主按钮恢复可点（截图 `shots/drop-F-failed-switch.png`） |
| **用户问的「有没有告诉他『已退回直连，你可以继续上网』」** | **有，而且写得对**：「网络可用，但流量不再走代理」正是用户需要的那句结论。这一条**不是缺陷**。 |
| **但有一个粘滞问题（代码依据，未在预览复现成功）** | `recoveryView`（`ipc.ts:160-167`）只要 `last_outcome === "direct_fallback"` 就返回 `phase:"failed"`，**不看 `running`**。<br>而后端**没有任何地方在手动重连成功后重置 `recovery`**：全仓 `core.rs` 里对 `recovery` 的写入只有 `begin / succeeded / fell_back_to_direct / set_probe_failures` 四处（`:502 / :513 / :537 / :554`），`start_core` 不在其中。<br>→ **用户手动点「连接」成功之后**，`last_outcome` 仍是 `direct_fallback`，界面会继续显示「自动恢复失败 / 已退回直连」，而隧道其实已经好了、流量也走代理了。<br>**为什么没在预览里复现**：预览的 mock 快照里 `runtime` 不含 `recovery` 字段，`parseRecovery` 返回 `null` → 手工重连那次刷新就把 badge 清掉了；真实后端返回的是完整 `CoreRuntime`（含 `recovery`），所以真机上会粘住。**这条标为「代码推断，需真机或 Rust 单测确认」。** |
| **缺什么** | 手动 `start` 成功后把 `last_outcome` 清回 `null`（或加一个 `cleared_at` 语义）；否则用户会以为「还在直连/还在失败」。 |

### S4「完全断网（DNS 哨兵残留）」——**有可操作提示，但只在启动时检测一次**

| 项 | 内容 |
|---|---|
| **现状证据** | 把哨兵 notice 注入快照并刷新后实测，仪表盘横幅原文：<br>`系统 DNS 还指着隧道内的哨兵地址 198.18.0.2（网络服务「Wi-Fi」），但隧道已经不在了，所有域名都解析不了。点「修复网络」，或执行：sudo networksetup -setdnsservers 'Wi-Fi' Empty` + 按钮 `去处理`；<br>点「去处理」→ 落到**设置**页，且该页有「修复网络（回滚遗留配置）」按钮（实测 `hasRestoreBtn: true`，`topbarTitle: 设置`）（截图 `shots/drop-D-sentinel.png`） |
| **代码依据** | 检测逻辑 `apps/desktop/src/lib.rs:263-289`；文案里带 `sudo networksetup -setdnsservers '{service}' Empty`；探测函数 `sentinel_dns_without_tunnel()` `lib.rs:334-346`（纯读，不要管理员权限） |
| **用户会怎么误判** | 文案质量高（说了现象 + 后果 + 两条动作）。**但它只在应用启动时跑一次**（条件 `if !runtime.running`，`lib.rs:274`）——「用着用着断了」这种**运行中残留**它检测不到。而用户的场景恰恰是「连着的时候断的」。 |
| **缺什么** | ① 检测时机扩到「每次 stop/断开之后」与「每次启动」，而不是只在启动；<br>② 给**一键修复**（现在要用户复制 `sudo` 命令，或跳到设置页再点一次）；<br>③ 多个 notice 并存时它会被折叠进「还有 N 条提示」（`Dashboard.tsx:168-172`），而这是最急的一条，排序应提到 rank 0/1。 |

### S5「节点不可达（被墙）」vs「整机断网」——**界面分不出来，而且会指向错误方向**

| 项 | 内容 |
|---|---|
| **现状证据** | 两条可能出现的文案（`core.rs:481` 看门狗、`core.rs:596-599` 连通性检查）：<br>「隧道连续 N 次不通（**熄屏/换网/节点抖动**，当前节点「X」），正在自动重建…」<br>「节点「X」已连接，但**流量出不去**（经它访问目标超时）。**请换一个节点。**」 |
| **结构性原因** | 全应用**只有一条探测通路**：`tunnel_probe()`（`core.rs:342-365`）用 `curl --socks5-hostname 127.0.0.1:<socks_port> http://cp.cloudflare.com/generate_204`（目标 `crates/xt-core/src/xray/probe.rs:46`）——**经本地 SOCKS 入站、也就是经隧道**。<br>本机网络本身是否通，应用**没有任何独立检查**：全仓 grep `NWPathMonitor` / `SCNetworkReachability` / `nw_path` / `offline` 均**未找到**。 |
| **用户会怎么误判** | 整机断网时，这条经隧道的探测**必然失败**，于是应用得出的结论是「隧道/节点有问题」→ 提示「请换一个节点」。用户于是去换节点（换一个还是不通），而真正的动作是**先修本地网络 / 先断开应用**。**这就是用户「不知道是应用、运营商还是节点」的根源**：界面对这三者只给出一种解释。 |
| **缺什么** | ① 一条**不经代理**的本地连通性探测（例如直连访问国内 DNS 或一个国内 HTTP 探针，走 `IP_BOUND_IF` 物理网卡）；<br>② 用它把失败分成三类文案：**本地网络不通**（「你的网络本身不通，先查 Wi-Fi/宽带；也可以先点断开」）/ **隧道不通但网络正常**（现文案）/ **节点被墙**（「换节点」）；<br>③ 分类结果要出现在**顶栏**（不是只在日志里）。 |

### S6「断开 / 退出后恢复」——**机制存在，但界面从没告诉过用户这个动作**

| 项 | 内容 |
|---|---|
| **现状证据（机制）** | 断开/退出时会向 helper 发 `Restore` 回滚系统网络配置：`tray.rs:150-200` `sync_cleanup()`（注释：「退出前**同步**回滚网络」，且 ⌘Q 走 `RunEvent::ExitRequested`，`lib.rs:128`）。这**正好解释**用户「断开或退出应用后网络就恢复了」。 |
| **现状证据（文案）** | 全仓 UII 文案 grep「先点断开 / 先断开 / 断开后」**未找到**面向用户的自救提示；唯一的「请断开后重新连接」在 `docs/04-routing-and-dns.md:740`，那是**开发者文档**，且触发条件不同（物理出口变化）。 |
| **用户会怎么误判** | 用户是**自己试出来**「断开就好」的。新用户/其他用户没有任何渠道学到这个动作 —— 安装说明、FAQ、设置页、首次连接提示里都没有（`site/**` 里 grep「断网/断开/上不了网」只命中 4 行、全部是**相反的承诺**「不会把你留在断网状态」，`site/index.html:287,294`、`site/llms-full.txt:51,53`，见 §6）。 |
| **缺什么** | 见 §4：在探测失败的那一刻把这句话说出来。这是**成本最低、收益最高**的一处（不新增后端字段）。 |

### 2.2 `docs/04-routing-and-dns.md`：**与「国内断掉」最接近的既有记录**（★ 优先看）

| # | 位置 | 现象 | 当时怎么修 | 是否真的解决了 |
|---|---|---|---|---|
| H11 | `docs/04` §6.5 | **宽泛的 `port: 53` 规则把内核自己的上游解析也吞了**：`from DNS accepted udp:223.5.5.5:53 [dns-module -> dns-out]` → 国内 DNS 被塞回 `dns-out`，TUN 下还会掉回 utun 形成「自己喂自己」→ **「国内解析这条腿永远出不了本机」**：国内域名查不到 → 回退到走节点的 DoH → 全压在节点上 | 规则**限定成哨兵地址**，内核自己的 `223.5.5.5:53` 不再被劫持 → 落到 `preset-cn-ip` → `direct`（绑物理网卡）→ 逃出隧道。实测 `[dns-module -> dns-out]` → `[dns-module -> direct]` | **是**（当时）。但它**正是「国外可以、国内断」的形状**：国外解析走节点 DoH 正常，国内直连解析这条腿断 → 国内域名全解析失败。**如果这条路径又坏了（规则漂移、哨兵地址变化、物理网卡绑定失效），症状就会与用户报告一模一样。** |

## 3. 用户最可能误解的三件事

### 误解 1：「界面显示已连接 = 网是好的」

* **为什么会这样**：`probe_failures = 1`（甚至 2）时，顶栏绿点、仪表盘「已连接 · 香港 · REALITY 01 53 ms」、按钮「断开」，
  与健康状态**逐字相同**（§1 S1 实测）。
* **后果**：整机断网时，用户去查路由器/运营商/节点，而不是先断开应用。用户自己后来学会了「断开就好」，但那是**试出来的**。
* **怎么消除（建议）**：探测失败一次就降级显示（黄点 + 计数），并在同一句里点出「整机上不了网时先断开」。
  数据已经在事件里（`recovery.probe_failures`），**不需要后端改动**。

### 误解 2：「提示『请换一个节点』= 问题在节点」

* **为什么会这样**：连通性检查失败时唯一的结论文案是「节点「X」已连接，但流量出不去（经它访问目标超时）。**请换一个节点。**」，
  而探测**只走隧道**，没有任何本地网络检查（§1 S5）。
* **后果**：整机断网、路由器挂了、Wi-Fi 没连上，都会被说成「换节点」。用户换了节点还是不通，于是认为应用坏了。
* **怎么消除（建议）**：加一条**不经代理**的本地连通性判定，把文案分成三类：
  「本地网络不通（先查 Wi-Fi / 宽带；也可以先点断开）」/「隧道不通但网络正常」/「节点可能被墙（换节点）」。
  纯前端做不到，需要后端加一个直连探针（属网络路径组）。

### 误解 3：「恢复失败 = 还停在坏状态」

* **为什么会这样**：`last_outcome === "direct_fallback"` 是**粘滞**的 —— 用户手动重连成功后，界面仍显示「自动恢复失败 / 已退回直连，可手动重连」（§1 S3，代码推断）。
  同时顶栏圆点保持 `dot--warn`。
* **后果**：用户以为还在直连/还没好，于是反复点连接、或去改配置。
* **怎么消除（建议）**：手动 `start` 成功后清 `last_outcome`；或在 `recoveryView` 里把「`running === true` 且 `last_outcome === 'direct_fallback'`」判为 `idle`（纯前端一行就能改，
  但更干净的是后端在 `start_core` 成功时重置 `recovery`）。

## 4. 如果只能改一句界面文案，改哪句

**改这一句（出现在探测失败、但看门狗还没开始重建的那 10–20 秒里）：**

> **「已连接，但这条隧道已探测失败 1 次；如果整台 Mac 都上不了网，先点「断开」即可恢复直连」**

**为什么是这一句（四条理由，都有证据）**：

1. **它落在唯一看不见的时间窗里**：`probe_failures ≥ 1 && !recovering` 这段时间界面是绿的（§1 S1 实测），
   而它恰好是用户决定「去查路由器还是查应用」的时刻。
2. **它给出了用户已经验证过、但界面从没说过的动作**：「先点断开」是用户自己试出来的（§1 S6）；全仓 UI 文案 grep 不到这句话。
3. **它不撒谎**：断开确实会回滚网络配置（`tray.rs:165` `sync_cleanup` → helper `Restore`），所以「恢复直连」是可兑现的；
   同时它用了**条件句**（「如果整台 Mac 都上不了网」），不会让只是节点慢的用户误操作。
4. **成本几乎为零**：`probe_failures` 已在 `RuntimePayload` 里、已在 `types.ts` 里、`recoveryView` 已经收到它，
   **只要改一个纯函数 + 一处渲染**。后端一行都不用动。

**呈现要求（避免变成新的噪音）**：

* 位置：顶栏（全局可见）+ 仪表盘状态行，**两处同一句**；
* 文案随次数变化：`1 次` → 保留「如果…先点断开」；`≥2 次` → 换成「隧道多次探测失败，正在准备自动重建」；
* 不要弹窗、不要红横幅（还没到失败）；用**黄点 + 一行字**；
* 一旦进入 `recovering`，立刻切到现有的「正在自动恢复（第 N 次）」文案（§1 S2），不要两句话并存。

**配套的一处（同批改，否则只改文案会漏）**：`Dashboard.tsx:139-146` 的连接按钮在 `recovering` 时必须和顶栏一样 `disabled`（§1 S2 实测漏点）。

## 5. 两条候选机制（来自历史记录；**属推断，需网络路径组验证**）

用户症状「国外可以、国内断掉、断开即恢复」在机制上至少有两条历史先例可对应。我**没有**真机环境验证，故只列**判别证据**：

**候选 A：TUN 下「国内直连解析」这条腿出不了本机（最像 —— 与 H11/H24 同形）**

* 机制：国内 DNS 用 `direct_servers[0]` + `IP_BOUND_IF` 绑物理网卡直连；一旦这条腿被劫持/绑定失效（规则漂移、哨兵地址变化、换网后网卡名变了），
  国内域名解析全失败 → 国内站点全断；而国外域名走节点 DoH，**照常解析** → 「国外可以、国内断」。
* 判别证据（网络路径组）：
  1. 核心日志里有没有 `from DNS accepted udp:223.5.5.5:53 [dns-module -> dns-out]`（被劫持）或大量 `context deadline exceeded`；
  2. **TUN 模式下** `networksetup -getdnsservers "Wi-Fi"` 是否 = 哨兵地址（`lib.rs:334` 的检测口径）；
  3. 生成配置里 53 规则的 `from` 是否**限定哨兵地址**（docs/04 §6.5 的修法）；
  4. 断网时 `dig @223.5.5.5 baidu.com`（不经隧道）是否正常 —— 若正常，说明本机网络没问题，问题在 TUN 的解析路径。

**候选 B：分流预设把国内流量也送进了节点（全局代理）**

* 机制：预设为「全局代理」时，国内站点也经境外节点；若节点出口回国被拒/被墙，就表现为「国外可以、国内断」，断开后直连恢复。
* 判别证据：拓扑页/规则页看当前预设；日志里国内域名命中的出站是 `node-…` 还是 `direct`；把预设切到「绕过大陆」是否立刻恢复。

**候选 C（附带）：`direct` 出站绑定的是换网前的旧物理网卡**

* 机制：`IP_BOUND_IF` 绑定的接口在换网后失效 → 所有 `direct` 流量（含国内域名解析）静默失败，而经节点的流量正常。
* 判别证据：对比换网前后的物理网卡名（`docs/04:740` 那条「每 5 秒比一次网卡+网关」的日志）；
  看有没有出现 `物理出口已变化` 提示。

**这三条的共同点**：都会让「国内」先坏、且断开即恢复。**建议网络路径组优先按 A 验证**（它有两条历史记录背书，且验证成本最低：一条 `dig` + 一个 `networksetup`）。
