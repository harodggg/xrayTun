黄推过滤器 · Jev：用 Jev 的类型化决策过滤 X 上的色情推广

这是一个 Chrome MV3 扩展。它在本地预筛、再用 Jev（TypeSafe System One）问几个类型化问题 （是/否、单选、评分），拿到概率与置信度之后才决定动作： 命中即隐藏，只有高置信度的色情/色情引流才会去动账号（静音/拉黑），而且 默认只演练、不真的点。它不是「关键词黑名单」—— 真正的判定在模型那一层，关键词只用来决定「值不值得花一次调用」。

它和 XrayTun 是什么关系：同一个作者的两个独立项目

本页介绍的是 黄推过滤器 · Jev，它与 XrayTun 是同一个作者的另一个独立项目：XrayTun 是 macOS 的 Xray 图形客户端， 本项目是一个浏览器扩展，两者不集成、不共享代码、不互相依赖， 也不能用本项目去配置或管理 Xray。放在同一个站点上，是因为它们出自同一作者， 而不是因为它们属于同一个产品。

它怎么判定：四层，逐层加钱

判定不是一次模型调用决定的，而是分层做：便宜的先做，贵的只在必要时做； 任何一层单独出现都不足以触发账号级动作。

层 做什么 成本
本地预筛 可读正则扫正文、显示名、卡片文案与图片 alt；白名单、自己发的、超短无媒体直接跳过 0 请求
预检（模型先行） 没被关键词命中的推文也会被问一句廉价单问（「是不是机器人式成人诱饵 / 性暗示自夸」）。≥0.75 再问完整四问；≥0.65 只隐藏成待确认 一次单问（约四问的 1/4）
文案农场 同一段无实质内容的话被 ≥3 个不同账号在 30 分钟内复制 → 全部隐藏 （含更早出现、当时被判放行的那几条）。归一会吃掉 emoji、标点与大小写 0 请求
Jev 类型化四问 色情？站外引流？类别（五选一，带置信度）？程度（四级评分）？—— 问题用英文写给模型，原文不翻译 一次调用
图片信号 Jev 是纯文本模型，看不了图：图片走本地肤色像素启发式 （Service Worker 里 OffscreenCanvas，不出网），只作为佐证 只下载缩略图

三条不变量（写进代码注释、也有单测守着）：① 只有 Jev 的强类别判定外加两道置信度闸门都通过，才可能触发账号动作；预检、文案农场、 肤色启发式、视觉模型单独出现最多到「隐藏」或「待确认」，永不拉黑； ② 模型不确定时降级，不做二次猜测；③ 每一档都写明原因（过滤条与审计日志里能看到概率、类别与原因）。

命中之后做什么，完全由你决定：默认是演练模式—— 只把「本应静音谁」记进审计日志，不点任何菜单。想让它真的动作，需要你在弹窗里显式打开 「自动静音」甚至「连『隐藏』档也静音」；拉黑这一档永远只认四问的高置信度判定。

安装与配置

扩展不需要构建，下载 zip 解压就是一个可直接加载的目录：

# 1) 下载并解压
unzip jev-x-filter-0.2.0.zip -d jev-x-filter

# 2) 打开 chrome://extensions → 右上角打开「开发者模式」
#    → 「加载已解压的扩展程序」→ 选中解压出来的 jev-x-filter 目录

# 3) 点扩展图标 → 打开设置 → 第 1 节「Jev 接入」
#    · 想用自己的 Key：预设保持 TypeSafe 官方，粘贴 API Key
#    · 想零成本试水：预设切到 OpenCode Zen（jev-1.13-free，免密钥）
#    · 点「测试连接」，确认能拿回类型化答案

# 4) 刷 x.com。看过滤条与设置页的「审计日志」，确认没有误伤再关掉演练模式

判定发生在扩展的 Service Worker 里，API Key 只存在 chrome.storage.local， 不会下发到页面上下文。设置页可以随时导出/导入账号黑名单（JSON）， 也可以把误判账号一键加入白名单。

真站反馈驱动了三轮修正，每一轮都留下了回归用例：显示名引流 （🍑真实同城约p🍑主页联系🔞免费 + 无害正文）、 完全不含关键词的骚式自夸（比我好看的没我骚🔧👏，乱码账号名）、 回复区文案农场（同一句被 4 个账号同一分钟刷出）。 其中两个是架构性漏洞：关键词表一旦成为「要不要问模型」的门槛， 表外的写法模型永远看不到 —— 这正是新增「预检（模型先行）」的原因。

已知边界（用它之前该知道的）

  • 会误杀。判定是概率性的，性教育、艺术、健身、擦边、方言黑话都可能被拦或被放过。 所有命中都能一键「显示」或「误判（加入白名单）」，请把默认的演练模式当成观察期。
  • 自动静音/拉黑是真实的账号操作（通过点击界面菜单完成，不调用私有 API）， 存在平台风控风险。扩展做了限速、幂等与默认演练，但不能保证不被风控。
  • Jev 看不了图。纯图片黄推只能靠本地肤色启发式 + 「只发图形态」隐藏成待确认； 它不会因为一张图就自动静音账号。需要更准的图片判定可以另配视觉模型端点。
  • 依赖 X 的 DOM。X 改版可能让菜单自动化失效；此时动作会记 action_failed 到审计日志，不会静默乱点。选择器集中在一个文件里，便于跟随更新。
  • 需要你自己的模型额度。候选推文与预检各花一次调用，扩展内有限速与每日预算， 超了会降级成「待确认」而不是乱拦。
  • 它只服务于你自己的时间线卫生：不提供批量举报、不针对他人账号发起攻击， 也没有任何「把某人挂出来」的能力。

常见问题

它会误杀正常内容吗？

会。判定本质是概率问题，任何过滤器都不可能零误伤，所以设计上把「误伤成本」压到最低：被拦的推文 随时可以点「显示」还原，点「误判（加入白名单）」会让该账号以后直接跳过，账号级动作默认只记录不执行。

自动静音或拉黑会不会导致我的 X 账号被封？

自动动作是通过点击界面菜单完成的真实账号操作，和手动点是一样的效果，因此存在平台风控风险。 扩展默认在演练模式下只记录、限制动作频率并保证同一账号只动作一次；建议先观察几天审计日志再关闭演练。

用这个需要花钱吗？

默认接入 TypeSafe 官方网关，需要你自己的 Jev API Key；也可以把预设切到 OpenCode Zen 的免费档 （模型 jev-1.13-free，免密钥）先零成本试水。扩展内有限速与每日预算上限， 超出后会降级为「待确认」而不是继续调用。

支持哪些浏览器？

支持 Chrome 120 及以上的 Manifest V3 环境，Edge、Brave 等同内核浏览器同样可以加载。 不支持 Firefox 与 Safari，因为它们的内容脚本与扩展 API 与 MV3 不同。

为什么图片的判定比文字弱？

因为 Jev 是纯文本决策模型，它的输入只能是文本，看不了图。所以图片走本地肤色像素启发式， 只有在「只发图/纯链接形态」下才用于隐藏成待确认，永远不会单独触发账号动作； 需要更强的图片判定可以在设置里另配一个支持图片输入的视觉模型端点。

我的数据会发到哪里？

只有推文文本与少量元数据（作者、位置、alt、卡片文案、本地肤色占比）会发给你自己配置的 Jev 网关； API Key 只保存在 chrome.storage.local 且只在后台 Service Worker 里使用；图片默认不出网； 可选的审计 webhook 默认关闭，开启后每条判定会 POST 一份事件。
