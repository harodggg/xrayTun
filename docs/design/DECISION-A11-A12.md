### 1.2 用户会在什么场景点它？`[判断]`（**没有用户调研，属推断**）

这个控件在**折叠的高级区**里（A11-F6），所以点它的人已经是在主动翻 TUN 高级设置的人。我的推断有三种：

1. **怕 v6 泄漏**：用户读到「选『不接管』会绕过隧道、可能泄漏真实出口」这句说明（A11-F5），
   于是去找一个「不泄漏」的选项 —— **说明文案本身正在把用户推向那个无效的选项**。
   这是最强的场景，也是 `[已核实]` 的（文案就在那里）。
2. **v6 半死不活的网络**：运营商 v6 通但慢/丢，或某些域名只有 AAAA 记录导致应用优先走 v6 超时；
   用户想「干脆把 v6 断掉，逼应用走 v4」（Happy Eyeballs 的典型用法）。这是真实存在的一类问题。
3. 隐私/指纹类考虑（少见）。

**结论 `[判断]`**：这不是「为假设需求建的开关」—— 场景 2 有真实价值，场景 1 是文案造成的。
所以**选项 2 不能简单理解成「把一个用户要的功能降级成说明」**：今天这个功能**本来就不存在**，
改文案丢掉的只是**一个不存在的能力的错觉**。

### 1.3 关键问题：若真的黑洞 v6，会把「只有 v6 地址的节点」自己断掉吗？

**答：`[推断]` 不会「必然」断，但有两个未验证的前提；前提不成立时会断。** 逐条给依据：

**(1) 节点地址确实会进 host 路由表 `[已核实]`**
`resolve_host` 对字面 IP（含 v6）直接返回 → `supervisor::resolve_server_addrs` → `bypass_hosts`
（`crates/xt-core/src/net.rs:16-19`、`apps/desktop/src/supervisor.rs:66-83`、`:898-903`）。
plan 的**第 2 步**为 `bypass_hosts` 里每个地址装 host 路由，**并且最先装**
（`crates/xt-tun/src/plan.rs:167-178`；`supervisor.rs:884` 注释：「必须是第一条被安装的路由」）。

**(2) 最长前缀匹配会让 `/128` 赢过 `/1` `[推断]`**
黑洞 `::/1` + `8000::/1` 的覆盖范围是整个 v6 空间，但节点那条是 `/128`，更长 ⇒ 内核选它。
**因此「黑洞 v6」不会直接把隧道断掉。**

**(3) 前提一（重要）：v6 的 host 路由可能本来就没生效 `[推断]` + `[未验证]`**
* `[已核实]`：`PhysicalUplink.gateway` 来自 `route::default_route()`（**IPv4**）；
  而 `default_route_v6()` 定义了却**全仓无人调用**（`crates/xt-tun/src/macos/route.rs:39-49`，
  `grep -rn default_route_v6` 只有定义处）。
* 于是对 v6 节点地址，`bypass_via()` 会退化成 `RouteVia::Interface{ en0 }` —— **没有网关**
  （`plan.rs:271-278`）。
* `[已核实]` 本项目自己的文档对「只有接口、没有网关」的路由有一句实测教训：
  内核把它当成「目标在本地链路」，**「包根本出不去」**（`crates/xt-proto/src/lib.rs:399-406`）。
  该结论是在 scoped default route 场景下实测的。
* `[推断]` 对全局 v6 单主机地址，`/128 -interface en0` 同样是 on-link 语义 ⇒ 可能发不出去。
  **这意味着问题不只影响选项 1：今天用 v6 节点 + `passthrough` 的用户可能同样受影响。**
* `[未验证]` 我没有 v6 环境，也没有在这台机器上做任何网络操作（任务边界禁止）。
  **上任何方案之前必须真机验证**：`route -n get -inet6 <节点v6地址>` 是否命中我们装的 `/128`、
  以及经隧道访问一个 v4 目标是否正常。

**(4) 前提二：节点用域名时的 AAAA 漂移 `[推断]`**
host 路由只在建立隧道那一刻按解析结果装一次。v4 侧有第二道保险 `IP_BOUND_IF`；
但本项目对 scoped 查找的结论是「不会回退，直接 `ENETUNREACH`」
（`crates/xt-proto/src/lib.rs:396-397`）⇒ 在全局 v6 黑洞下，域名漂移出的**新 v6 地址**会被黑洞吞掉，
`IP_BOUND_IF` 未必救得回来。v4 侧同类风险已被 `docs/07 §R3.5` 登记；v6 侧会更硬。

**(5) 附带必须先解决的清单问题 `[已核实]`+`[推断]`**
* `[已核实]` plan 里 **DNS 服务器只做字符校验、不装 host 路由**
  （`plan.rs:246-256`），而 DNS 地址允许 v6（校验里含 `:`）。
* `[推断]` 若用户把 v6 地址写进「远端/本地 DNS」或自定义解析器，全局 v6 黑洞会**连 DNS 一起断**。
  ⇒ 真做「禁用 v6」必须带一个「不可黑洞的必要地址」清单（节点地址、网关、正在使用的 v6 DNS）。

### 1.4 三个选项的成本与后果

> 选项 1 在卡里是一个方案，但它其实有两条**成本差一个数量级**的实现路径，我把它们拆开。

#### 选项 1a · helper 侧安全黑路由（卡里的原始方案）
新增 `RouteVia::Blackhole`（`crates/xt-proto/src/lib.rs:384-408` 目前只有 Interface / ScopedInterface / Gateway）
→ `route add -blackhole` 支持（`crates/xt-tun/src/macos/route.rs:157-212` 的 `build_args`）
→ plan 在 `Disabled` 时发 `::/1` + `8000::/1` 黑洞 → 回滚沿用现有反序删除（`route.rs:140-151` 已按 via 生成 delete）。

* **用户可见后果**：v6 立即不通、不泄漏；应用连 v6 目标会立刻失败并回退 v4（与「没有 v6 网络」同感）。
* **是否要重装助手**：**要**。路由的安装/回滚都在 helper 里（A11-F8/F9），
  且 `RouteVia` 是线协议类型（`server.rs:253-263`）⇒ 协议号必须 +1，否则旧助手收不到新变体
  （要么握手硬拒、要么反序列化失败）。已装用户会在设置页看到 `mismatch` 横幅并点一次
  「重新安装助手」（A11-F11，需管理员密码），**不重装就一直是旧行为**。
* **风险**：§1.3 的（3）（4）（5）三条**全部未验证**。
* **我的判断 `[判断]`**：**不建议**。它把一个「现在没生效的开关」换成「可能把用户断网的开关」，
  而收益（少数用户少一次泄漏）与风险（v6 节点的隧道、v6 DNS）不对称；
  还要所有用户重装一次特权助手。

#### 选项 1b · app-only：沿用 `override` 捕获 + 核心侧丢弃（**新增的第三条路**）
`ipv6 = override`（helper **今天就支持**，`plan.rs:233-236` 已抓 `::/1`+`8000::/1`，有单测
`plan.rs:349-354`）+ 在生成的核心配置里把 `::/0` 规则指向已有的 `block` outbound
（`crates/xt-core/src/xray/config.rs:522-526` 已有 `blackhole` 的 block 出站）。

* **用户可见后果**：v6 **真的不通**、不泄漏；差别是「连接超时」而不是「立即失败」（应用仍会回退 v4）。
* **是否要重装助手**：**不要**（helper 不动，纯 App/配置侧）。这是它相对 1a 的决定性优势。
* **前置验证 `[未验证]`**：utun 上**没有配 v6 地址**（`addresses` 只给 v4 隧道网段，
  `supervisor.rs:938`；而 `DEFAULT_TUN_NETWORK_V6` 在全仓**只有定义、无人使用**，`plan.rs:280`）
  ⇒ 必须先确认 `override` 模式下 v6 报文**真的能进 gVisor 栈**。如果连捕获都不生效，
  1b 同样是「看起来禁用、其实泄漏」。
* **我的判断 `[判断]`**：**如果 Lead 认为「真禁用」值得做，这是首选路径**；
  但它的第一步不是写代码，是**一次真机验证**（20 分钟量级）。

#### 选项 2 · 不实现，把标签与说明改成实话
两种改法（都可 app-only）：

* **2a 改标签**：`disabled` → 「保持 IPv6 直连（可能泄漏 v6 出口）」，并把说明补成
  「本选项与『不接管』当前行为相同」。**优点**：改动最小、不动枚举/设置迁移。
  **缺点**：界面上出现两个**行为完全相同**的选项 —— 与用户「用更简单的方式替代复杂」的授权相反。
* **2b 直接删掉这个选项**（我的偏好 `[判断]`）：下拉只剩「不接管 / 同样接管 IPv6」两个，
  已存的值 `disabled` 在读设置时映射为 `passthrough`（一次小迁移）。
  **优点**：少一个概念、少一个错误信念，且**没有丢任何真实能力**（A11-F2/F3：`disabled` 今天
  与 `passthrough` 逐字节相同）。**缺点**：要动 `xt-proto` 枚举或至少在 UI + 反序列化处做兼容；
  未来若真实现「禁用」，这个选项要再加回来。

* **是否要重装助手**：不要。两种改法都在 App 侧：2a 是纯 UI；2b 也不需要动线协议 ——
  建议**保留 `xt-proto` 里的枚举**（旧请求里可能带着 `disabled`），只在 UI 上不再提供这个选项，
  并在读取设置时把 `disabled` 归一成 `passthrough`。直接删枚举会破坏旧版本的请求兼容，不建议。

#### 三选项对照

| | 1a helper 黑路由 | 1b override + 核心 block | 2b 删选项（推荐立刻做） |
|---|---|---|---|
| 语义与标签一致 | ✅ 真不通 | ✅ 真不通 | ✅ 不再承诺（选项消失） |
| 用户可见后果 | v6 立刻失败 | v6 超时后失败 | 无（v6 仍直连，与今天相同） |
| 重装特权助手 | **要** | 不要 | 不要 |
| 依赖的未验证前提 | 3 条（v6 host 路由、AAAA 漂移、v6 DNS） | 1 条（override 的 v6 数据面） | 无 |
| 工作量 | 大（线协议 + helper + 测试 + 发版说明） | 中（配置侧 + 验证） | 小（UI + 一次归一化） |

### 1.5 A11 推荐 `[判断]`

1. **本轮**：做 **2b**（删掉选项 / 或退一步做 2a 改实话）。理由：它去掉的是一句**假承诺**，
   不减损任何现有能力；同时满足「更简单」的授权方向。
2. **本轮同时**：把 §1.3(3) 的验证列入待办 —— 因为**即使不做「禁用 v6」，
   v6 节点的 host 路由是否正确也是现存问题**（`default_route_v6` 从未被调用）。
3. **若 Lead 决定要「真禁用」**：走 **1b**，并把「一次真机验证 + 「不可黑洞的必要地址」清单」
   作为前置；**不要走 1a** —— 除非 1b 被证明不可行，且 1b 的验证顺带把 v6 数据面也确认了。

## 2. A12 ·「关闭嗅探」

### 2.1 事实（`[已核实]`）

| # | 事实 | 依据 |
|---|---|---|
| A12-F1 | 生成配置时嗅探的开关是 **`s.dns.sniffing \|\| s.fakedns.enabled`** —— 开了 Fake-IP，嗅探恒为真 | `crates/xt-core/src/xray/config.rs:346` |
| A12-F2 | 同一处：`destOverride` 在 Fake-IP 开时是 `["fakedns+others"]`，否则是 `["http","tls","quic"]`；`routeOnly` 固定 `false`，注释写明「打开 Fake-IP 时必须保持 false，否则假地址不会被还原」 | `config.rs:341-350` |
| A12-F3 | 复选框在 **DNS 分类**：「开启流量嗅探（按 SNI / Host 分流）」；提示写的是「关闭嗅探后，域名分流只能依赖 DNS 阶段的信息，对『直接用 IP 发起连接』的程序会失效」——**没有提 Fake-IP** | `apps/ui/src/pages/Settings.tsx:708-717` |
| A12-F4 | Fake-IP 的开关在**另一个分类**（连接），卡片里也没有提「会顶开嗅探」 | `Settings.tsx:722-746`（说明 `:724`、开关 `:735`） |
| A12-F5 | Fake-IP 卡片自己有一条警告：会污染本机 DNS 缓存，隧道关闭后一段时间可能「网络无法访问」，需等缓存过期或手动刷 `mDNSResponder` | `Settings.tsx:742-747` |
| A12-F6 | 设置是**草稿 + 显式保存**，且 Fake-IP/嗅探这类改动要重启核心才生效 | `docs/05-ui-spec.md §3.6`；「保存并重启核心」按钮在 `Settings.tsx:791` |

**结论 `[已核实]`**：勾掉「开启流量嗅探」在 Fake-IP 开启时**不生效**，而且界面**没有任何地方**
告诉用户「因为 Fake-IP 开着」。用户会得到一个错误的信念（「我关了嗅探」）。

### 2.2 两个选项

#### 选项 1 · 保持 `sniffing || fakedns` + UI 如实解释（推荐）
UI 侧要做满三件事（都只用现有字段，**不需要后端/helper 改动**）：

1. `fakedns.enabled` 为真时，把该复选框渲染成**已勾选 + 禁用**，并在旁边写明：
   「Fake-IP 已开启：嗅探被强制开启，用来把假地址还原成域名（取消勾选不会生效）」；
2. Fake-IP 卡片里加一句反向说明：「开启 Fake-IP 会同时把『流量嗅探』打开」；
3. 关闭 Fake-IP 时，嗅探复选框恢复可点，并按用户原有的 `dns.sniffing` 值显示。

* **用户可见后果**：不再有「关了没关」的错觉；**功能行为一行不改**，所以没有新的失败模式。
* **是否要重装助手**：不要。
* **成本**：小（一个受控复选框的条件渲染 + 两处文案）。

#### 选项 2 · 反过来实现「关嗅探 ⇒ 顺带关 Fake-IP」
